## 1. `docs/evidence/` 目录结构

```
docs/
└── evidence/
    ├── README.md                       # 操作速查（本波交付）
    ├── wave-<NN>/                      # 按“采集波次”分目录，如 wave-02/
    │   └── <TASK-ID>/                  # 按任务分子目录，目录名照抄任务 ID 原大小写
    │       ├── E1-<slug>.md            # 证据主文件（含文件头、复现命令、原始输出）
    │       ├── E3-<slug>.md
    │       ├── E3-<slug>.raw.log       # 超长原始输出旁存（可选，见 §3.3）
    │       └── E4-<slug>-01.png        # 截图附件（可选，见 §3.3）
    └── spot-checks/                    # TASK-P3-10 输出质量抽检记录（P3 分区既有约定，长期滚动）
```

规则：

1. **波次归属**：`wave-<NN>` 指证据**采集时所处的执行波次**（与 DISPATCH 回执登记的波次一致），不是任务 ID 里的波次编号。例：W1-P1-T04 若在第 2 波执行，其证据放 `wave-02/W1-P1-T04/`。跨波续做的任务，各波证据各归各目录，**不迁移旧证据**。
2. **任务目录**：目录名照抄 ready-tasks 中的任务 ID（`W1-P1-T04`、`TASK-P3-01`、`W2-PLAN-T03`……），保持原大小写，保证全库可 grep。无任务锚点的证据（如波次级基线复测）放 `wave-<NN>/_wave/`。
3. **`spot-checks/` 顶层保留**：`docs/evidence/spot-checks/` 是 P3 分区 TASK-P3-10 已登记的存档路径（抽检记录长期滚动、跨波累积），维持顶层不动，**本文不改其约定**；其内部记录格式由 TASK-P3-10 交付时定义。
4. **不建空目录**：目录随第一份证据一起创建，不预建占位；本波只落 `docs/evidence/README.md` 一个文件。
5. `runs/*.jsonl`（运行轨迹原始文件，TASK-P3-04）**永不进入** `docs/evidence/`，也不进 git（`.gitignore` 已由脚手架槽预留方向）；进入 evidence 的只能是脱敏摘要（见 §3.2 E4 与 §5）。

## 2. 命名规范

### 2.1 证据主文件

```
<证据类型>-<slug>[-<序号>].md
```

- **证据类型**：`E1`–`E5`（大写，与基线 §2 编号一致）。一个文件只承载一类证据；一次采集覆盖多类时拆多个文件（允许互链）。
- **slug**：小写 ASCII 字母/数字，短横线分隔，3 个词以内，描述证据对象。例：`E2-lint-typecheck.md`、`E3-vitest-suite.md`、`E4-init-walkthrough.md`、`E4-run-a1b2c3.md`（trace 摘要，取 run_id 前 6 位）、`E5-ttfs-bench.md`。
- **序号**：同一任务对同一对象**重采**时追加两位序号（`-02` 起），不覆盖旧文件（见 §2.3 冻结规则）。
- 文件名正则（供后续 lint 自动校验）：`^E[1-5]-[a-z0-9]+(-[a-z0-9]+)*(-[0-9]{2})?\.md$`。

### 2.2 附件

- 超长原始输出旁存：`<主文件名去 .md>.raw.log`（如 `E3-vitest-suite.raw.log`）。
- 截图：`<主文件名去 .md>-<两位序号>.png`。截图须为静态 PNG，单张 ≤ 300 KB；**录屏/视频不入库**（体积），以“步骤记录 + 关键帧截图”替代。
- 附件必须被同名主文件引用，不允许无主附件。

### 2.3 冻结规则（append-only）

证据文件一经被 DISPATCH 回执、W5 核验报告或 ready-tasks 状态行**引用**即冻结：不得修改、不得删除、不得移动路径。需要更正或重采时另立带序号的新文件，并在新文件头部注明“取代 `<旧文件>`，原因：……”；旧文件原样保留供审计。未被引用的草稿可以修改。

## 3. E1–E5 如何落盘

### 3.1 通用文件头模板

每个证据主文件以下表开头（缺任一必填项即不满足基线“证据三要素”，按证据无效处理）：

```markdown
# 证据：<一句话标题>

| 项目 | 内容 |
| --- | --- |
| 任务 ID | <如 W1-P1-T04；无任务锚点写 _wave 并说明> |
| 证据类型 | <E1–E5 之一，附基线 §2 的类型名> |
| 锚定 commit | `<分支名> @ <完整或 ≥12 位 SHA>` |
| 采集日期 | <YYYY-MM-DD>（UTC） |
| 采集环境 | <OS / Node 版本 / npm 版本，与复现相关的即可> |
| 采集人（槽位） | <槽位号或分支名> |
| 脱敏声明 | 已按约定 §5 自查，自查命令输出为零命中；<有例外须在此逐条说明> |

## 复现命令

<核验人可照做的完整命令或步骤序列>

## 原始输出

<粘贴输出（含退出码）；超长时按 §3.3 截断并旁存>

## 佐证（可选）

<CI run URL、相关 PR/commit 链接等旁证——不可替代上文的仓库内存档>
```

### 3.2 各类型落盘形态

以下只规定“落成什么样的文件”，类型定义与内容要求见基线 §2。

| 类型 | 落盘形态 | 要点 |
| --- | --- | --- |
| **E1 代码存在性** | 单个 md：`git ls-tree`/`git log`/目录树命令 + 原样输出 | 输出必须与文件头锚定 SHA 属同一提交；全称断言（“无 X”）须附探测命令（参照 W1-C §3.1 的 `git cat-file -e` 手法） |
| **E2 静态质量** | 单个 md：build/lint/typecheck 的完整命令 + 输出 + **显式退出码**（如 `echo $?` 或 CI 步骤结论行） | 三件套可合一个文件；CI 产出的输出摘录须注明 run URL 与 job/step 名，但**摘录本身必须存在文件里**（URL 会过期，不可离线核验，见基线三要素之“原始输出存档”） |
| **E3 自动化测试** | 单个 md：测试命令 + 摘要输出（框架给出的 `x passed / y failed / 文件数 / 用时`）+ 覆盖范围一句话 | 通过数必须可见；有覆盖率要求的任务附覆盖率报告摘要。失败后修复重跑的，存**最终绿色输出**，并在“佐证”节注明修复 commit |
| **E4 运行时行为** | 走查记录 md：编号步骤（命令 → 预期 → 实际输出）；模型调用记录 md：脱敏后的请求参数（模型名、采样参数、prompt 概要）+ 响应内容 + token 用量与延迟；trace 摘要 md：从 `runs/*.jsonl` 导出的脱敏摘要（文件名 `E4-run-<run_id 前 6 位>.md`） | 一律先过 §5 脱敏；剧本正文遵守 §5 第 3 条（夹具可全文、真实内容只存引用）。模型调用与 trace 摘要的字段细节以 TASK-P3-01/P3-04 验收标准为准，本文只定路径与脱敏底线 |
| **E5 量化指标** | 单个 md：指标定义 + 采集方法（命令/脚本路径）+ 数值表 + 采集时点 | 指标脚本本身入 `scripts/`（代码，走正常 CI），evidence 里只存“定义 + 方法 + 数值”；多次采集追加序号文件形成时间序列，不改旧值 |

### 3.3 原始输出体量规则

- **≤ 300 行且 ≤ 20 KB**：直接内嵌主文件代码块。
- **超过上限**：主文件内嵌“头 50 行 + 尾 50 行 + 一行截断说明（原始总行数/字节数）”，完整输出旁存同名 `.raw.log`（≤ 200 KB）。
- **旁存仍超 200 KB**：只存截断版 + 复现命令，并在脱敏声明下方注明“完整输出超限未存，复现命令见上”。核验人以复现为准。

### 3.4 与 W5 核验的衔接

W5 报告 §3“证据核查明细”表的“存档路径”列一律填 `docs/evidence/...` 仓库内路径。按基线判定规则：命令缺失、环境不满足或**输出未存档**即“无法复现”，证据无效、相关评级降级——外链（CI URL、gist 等）不算存档。

## 4. 归档流程（谁、何时、怎么引用）

1. **实现槽（产出方）**：每完成一个任务，对照该任务验收标准中标注的证据类型（E1–E5）**逐条**产出证据文件，归入 `docs/evidence/wave-<NN>/<TASK-ID>/`，与代码同分支提交。验收标准未标证据类型的老条目（如 P1 分区部分任务），按基线 §2 各级最低证据要求补齐（至少 E2+E3——见 §6 清单）。
2. **回执引用**：DISPATCH 回执的产出清单中列出本槽新增的证据文件路径（或任务目录路径）。ready-tasks 状态行标“完成”时，证据必须已在同一分支就位——**无证据不得标完成**（与 P3 分区“证据不合格视为未完成”一致）。
3. **W5 核验槽（消费方）**：按 W5 模板 §3 逐条核查，引用 evidence 路径；核验产生的新证据（独立复现输出）同样按本约定归档，任务目录用被核验任务的 ID，文件名加 `-w5` 后缀词（如 `E3-vitest-suite-w5.md`），与被核验方证据并存互不覆盖。
4. **合并纪律**：`docs/evidence/` 全目录按“并集合并”处理——不同分支各自新增的证据文件互不冲突时全部保留；同路径冲突说明有人违反了 §2.3 冻结规则，以先被引用的版本为准，另一份改名带序号保留。

## 5. 脱敏规则

进入 `docs/evidence/`（以及一切入 git 的文档）的内容必须满足全部五条。第 1、2 条同样约束代码、测试夹具与提交信息。

1. **凭据零容忍**：API key、token、secret、密码、私钥、会话 cookie 一律不得出现——包括“已失效的”。模型调用记录必须剥离 `Authorization` 等鉴权头与组织/账户标识，凭据来源只写“注入自环境变量 `<变量名>`”。此条与 TASK-P3-01 验收“仓库全文检索不到任何凭据明文”同口径。
2. **个人与环境信息**：绝对路径中的用户段统一替换（`/home/<user>`、`/Users/<user>` → `<HOME>`；仓库路径 → `<REPO>`）；真实邮箱、主机名、内网 IP、云账户 ID 不入档（git 提交人信息除外，其本就在仓库历史中）。
3. **剧本正文分级**：`tests/`、`templates/` 下的**夹具/模板文本**可全文引用，须注明夹具路径；**真实用户创作内容**在 trace 与 evidence 中默认只存引用——场号 + SHA-256 前 12 位 + 字数（与 P3 方案 §2.7 的脱敏原则同口径），全文存档仅限调试用途且不入 git。
4. **模型响应**：响应中的供应商侧元数据（账户配额、组织 ID、请求 ID 中的账户段）删除或打码；保留内容本体、模型名、token 用量、延迟。
5. **提交前自查**（结果写入文件头“脱敏声明”行）：

```bash
# 凭据类零命中即过；命中须逐条人工确认为误报（如文档中的占位符）并在脱敏声明中说明
# （-g '!README.md' 排除本目录速查文件自身的规则示例）
rg -n -i -g '!README.md' "(api[_-]?key|secret|token|passwd|password|bearer |sk-[A-Za-z0-9]{8,}|AKIA[0-9A-Z]{16}|-----BEGIN)" docs/evidence/
# 个人路径类零命中即过
rg -n -g '!README.md' "(/home/[a-z0-9_-]+|/Users/[A-Za-z0-9_-]+)" docs/evidence/
```

**违规处置**：脱敏不合格 = 证据无效（触发基线降级规则）；已推送的凭据泄露**立即轮换该凭据**并在回执登记事故，仅删除文件不算处置（git 历史仍在）。

## 6. CI 证据清单（实现槽红线）

### 6.1 基线快照

本清单以脚手架槽已推送的 CI 为基线快照：`cursor/w2-scaffold-ci-ccbf @ 39a0b30` 的 `.github/workflows/ci.yml` + `package.json` scripts——push 与 PR 触发，Node 20/22 矩阵，五步：`npm run lint`（eslint `--max-warnings 0`）→ `npm run typecheck` → `npm test`（vitest run）→ `npm run build` → `npm run smoke`（`sw --version` / `--help`）。该 CI 合入 `main` 后即为唯一执行版本；合入前后如与本清单不一致，**取更严格者**。

### 6.2 必须项（每个实现槽任务合入前逐条自查，并在回执声明）

| # | 检查项 | 合格标准（二值） | 证据归档 |
| --- | --- | --- | --- |
| C1 | Lint | `npm run lint` 本地与 CI 均通过，`--max-warnings 0` 不放宽 | E2，归 `wave-<NN>/<TASK-ID>/` |
| C2 | 类型检查 | `npm run typecheck` 通过；tsconfig 严格项（`strict` 族）不降级 | E2（可与 C1 合档） |
| C3 | 单元测试 | `npm test` 全绿；**套件通过数不低于改动前**（基线快照为 21 条，随主分支单调递增）；任务验收标准中标 E3 的条目均有对应测试 | E3，输出含通过数 |
| C4 | 构建 | `npm run build` 通过 | E2（可与 C1/C2 合档） |
| C5 | 冒烟 | `npm run smoke` 通过（CLI 入口可执行） | E2 或并入 E4 走查 |
| C6 | help 快照 | 见 §6.3 | E3 |
| C7 | CI 覆盖面 | push + PR 双触发保持；Node 版本矩阵不删减；五步一步不少 | 回执声明（改 CI 文件时附 E1 diff 证据） |
| C8 | 证据落盘 | 本任务验收标准要求的证据类型已按 §3/§4 归档，脱敏自查零命中 | 回执列路径 |

### 6.3 help 快照专项

- **T10 落地前（当前阶段）**：凡新增或修改子命令，必须在其单测中包含对 `--help` 输出的**结构性断言**——至少覆盖：命令描述存在、≥1 条可复制示例（或“规划中”标注，禁止虚假可用性承诺）、帮助旗标可用。参照脚手架槽 `tests/cli/program.spec.ts` 的既有模式。
- **T10 落地后**：全部子命令的 help 快照统一进 `tests/help-snapshots/`，新增命令未附示例即 CI 红（W1-P1-T10 验收②），原单测中的结构断言可迁移但不得净删。
- **断言口径**：按 T10 风险条款，快照锁**结构**（含示例段落、docs 链接、旗标说明），不锁全文，避免碎裂；但已锁的结构断言**只能增不能减**，缩小断言范围视同降低标准（走 §6.5 例外通道）。
- **快照更新纪律**：快照失败时先判定是预期变更还是回归；确属预期变更才允许更新快照，且须在 commit message 注明“help 快照更新原因”。为绿而盲更快照视同删测。

### 6.4 禁止清单（触碰任何一条即视为降低 CI 标准，调度器红线）

1. 删除或注释测试；提交遗留 `.skip` / `.only` / `xit` / `xdescribe` / `test.todo` 顶替真实测试。
2. 放宽 lint：调高 `--max-warnings`、降级或删除规则、大面积 `eslint-disable`（行内 disable 须附理由注释且仅限该行）。
3. 降低类型检查严格度（关闭 `strict` 族选项、滥用 `any` / `@ts-ignore` / `@ts-expect-error` 绕过——后两者须附理由注释）。
4. CI 步骤加 `continue-on-error`、命令加 `|| true`、吞退出码、把失败步骤改为仅告警。
5. 缩小 CI 触发范围（去掉 push 或 PR）、删减 Node 矩阵、砍掉五步中任何一步。
6. 为绿而盲目更新快照（见 §6.3）；调低任何既有验收阈值。
7. 借“重构”之名净减少测试数或断言数而不登记。

### 6.5 例外通道

确有正当理由的“看似降标”变更（如删除已废弃功能的过时测试、快照口径调整）：① 在 DISPATCH 回执登记理由、影响面与补偿措施；② 在 ready-tasks 对应条目追加修订记录（沿用 WAVE02-PLAN 分区 T05 的偏离登记先例）；③ 有争议时上报调度器裁决后再动。**静默执行 = 违规**，W5 核验发现未登记的降标按证据无效 + 评级降级处理。

### 6.6 CI 文件修改纪律

`.github/workflows/ci.yml` 合入 `main` 后，实现槽对它的修改只允许**新增步骤或收紧标准**（如 T06 追加注册表 lint、T10 追加 TTFS 与 help 快照步骤——均为既登记任务）；任何放宽须走 §6.5 例外通道。修改 CI 文件的提交须在回执单独列出并附改动前后对比（E1）。
