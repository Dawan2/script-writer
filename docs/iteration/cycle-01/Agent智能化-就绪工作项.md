## 0. 通用约定

### 0.1 完成判定

一个工作项算完成，必须同时满足：

1. 验收标准每一条都能给出"是"的判定，判定方式是自动化测试或可复现的操作步骤，不接受"人工试过了"；
2. 证据落盘到 `docs/iteration/cycle-01/evidence/<任务编号>/`，或以测试代码形式进入仓库；
3. `npm run check` 通过；`npm run test:agent` 与 `npm run test:api` 不得比领取时更差
   （领取时基线：Agent 81 项 5 失败、API 454 项 4 失败，失败清单见基线文档第 5 节）；
4. **凡涉及验收规则的改动，必须同时满足三处一致**：阶段验收清单、`check-*.mjs` 判定项、
   `foreign_review` 复核映射。三处任一未同步即视为未完成。这条对下述每一个工作项都生效。
5. 新增或修改的用户可见文案经用户视角复核：不含内部术语、文件路径、工具名、英文标识、错误码原文。

### 0.2 证据类型

| 类型 | 要求 |
| --- | --- |
| 自动化测试 | 测试代码入仓，测试名能读出被验证的规则；断言针对行为而非实现细节 |
| 一致性扫描输出 | 契约类改动须给出扫描前后的对照输出（如孤儿文件数从 6 变 0） |
| 留痕样本 | 涉及使用记录的项，须给出一次真实运行产生的记录样本（脱敏） |
| 操作走查 | 编号步骤 + 每步预期与实际，覆盖失败路径而非只有成功路径 |
| 录屏 | 仅用于用户可见的新能力（生成依据、证据跳转），须含"看不到"到"看得到"两端 |

### 0.3 脱敏

证据不得包含剧本正文、用户上传内容、模型凭据、账号口令。
剧本内容一律以摘要、集号或字符数代替原文。

### 0.4 梯队与并行

| 梯队 | 工作项 | 说明 |
| --- | --- | --- |
| 第 0 梯队 | T01、T02、T03 | 使能项。T01 建立唯一来源，T02 打通原则通过标准，T03 建立可回归的知识库夹具。三项互相独立，可同时开工 |
| 第 1 梯队 | T04、T05、T06、T07 | 依赖 T01 的清单结构；四项之间互不依赖 |
| 第 2 梯队 | T08、T09、T10、T11 | 契约与清理项，可与第 1 梯队并行，但 T09 须在 T05 之后（死代码清理不得先于能力重建） |
| 第 3 梯队 | T12、T13、T14 | 用户可见的新能力，依赖 T01/T02 已产出结构化的依据与判定结果 |

## C1-AG-T01 建立阶段验收清单，消除四处并存的验收规则

**覆盖缺口**：G-02（孤儿验收规则）、G-03（适用范围矛盾）、G-05（死规则）、G-06（未被引用的 reference）

**目标**：让每个创作阶段的"什么算做对了"只有一个定义处，其余位置只能引用。
这是本周期所有其他工作项的地基。

**范围**：
- 为 `world_view`、`outline_rewrite`、`character_rewrite`、`trial_generate`、`full_generate`、
  `dialogue_translate`、`foreign_review`、`humanizer-zh` 八个阶段各建立一份阶段验收清单，
  字段与结构按架构方案 §2.2；
- 删除 `SKILL.md` 中与清单重复的"内容额外要求"，改为引用；
- 处置 6 份孤儿 reference：并入清单或删除，不保留无引用关系的规则文件；
- 修正 `full_generate/references/全稿对抗性审稿原则.md` 的适用范围声明，
  使其与 `full_generate/SKILL.md:86` 的实际调用点一致（二者取一，不允许两种读法并存）；
- 删除 `foreign_review` 中无调用方的预审模式规则（`SKILL.md:3`、`:11`、`:13`），
  或在 `full_generate` 中补上真实调用点——二选一，不保留声明与实现不符的状态。

**不属于本项范围**：新增任何检测项（T05）；把知识库原则接入清单（T02）；
契约一致性检查的自动化（T06）。

**验收标准**：
1. 八个阶段各有一份阶段验收清单，每条规则四个字段齐全，无空缺。
2. `SKILL.md` 中不存在与清单重复的规则文字；抽查任一条规则，全仓库只有一个定义处。
3. `references/` 下不存在未被任何 `SKILL.md` 引用的文件（当前 6 个，须归零）。
4. `全稿对抗性审稿原则.md` 的适用范围声明与实际调用点一致，且不再同时禁止与要求跨单元回读。
5. `foreign_review` 的预审模式要么有真实调用点，要么规则已删除；不存在第三种状态。
6. 每条清单规则的"判定方式"取值只能是机器判定或语义判定，不存在未标注项。

**证据要求**：
- 一致性扫描输出：孤儿 reference 数量、`SKILL.md` 断链数量的改前改后对照；
- 自动化测试：清单结构校验（四字段齐全、判定方式取值受限）；
- 操作走查：任取三条规则，走查"从清单到 check 工具判定项到审稿映射"的引用路径。

## C1-AG-T02 把创作原则的通过标准贯通完成时、质量校验与 AI 审稿

**覆盖缺口**：G-01（原则通过标准三处均不判定）

**目标**：让知识库里的原则不再只影响模型"自觉"。这是本周期的核心工作项，
也是判断"Agent 智能化投入是否有效"的唯一入口。

**范围**：
- `Agents/.claude/skills/_shared/scripts/stage-execution-spec.mjs`：
  执行策略生成时，把每条原则的 `review_criteria` 连同原则 ID 与版本写入当前阶段验收清单的语义判定项；
- `check-*.mjs`（创作五阶段）：校验"每条语义判定项都有自查结论与证据定位"，
  缺失即不通过；把结果结构化写入 `quality_check`，替代当前
  `check-full.mjs:165-176` 只回显通过标准的做法；
- `apps/api/app/services/workspace_service.py`：阶段质量判定纳入语义判定项的完整性；
- `Agents/.claude/skills/foreign_review/`：建立"语义判定项 → 审稿维度检查项"的映射，
  审稿对每条语义判定项给出复核一致或不一致 + 正文证据，不一致项按现有 P0/P1 规则进入返修建议。

**不属于本项范围**：再引入一个模型给原则打分（架构方案 R1 已否决）；
原则的效果度量分析（T04 只要求数据可查）；修改原则本身的内容或策展流程。

**依赖**：T01（清单结构）、T03（否则无法回归）。

**验收标准**：
1. 执行策略中的每条原则，其通过标准都出现在当前阶段验收清单中，且标注了来源原则 ID 与版本。
2. 创作阶段的自查结论缺失任一条通过标准时，`check` 工具不通过，且返回的问题指名缺哪一条。
3. 自查结论中的证据定位可回到当前交付文件的真实位置（集号或行号），
   编造的定位（指向不存在的集或行）被检查拦截。
4. 审稿报告中对每条语义判定项都有复核结论；复核不一致项出现在修改建议里。
5. 知识库中新增一条原则后，无需改动任何 Skill 文本，它的通过标准就会出现在清单、
   在完成时被要求留痕、在审稿时被复核。
6. 知识库中没有可用原则时，清单只含 Skill 固定要求，流程不中断且不产生空的语义判定项。

**证据要求**：
- 自动化测试：第 2、3、5、6 条各至少一个用例（使用 T03 的知识库夹具）；
- 留痕样本：一次运行产生的语义判定自查结论与证据定位（脱敏）；
- 操作走查 + 对照：同一份稿件在原则接入前后，`quality_check` 与审稿报告的差异对照。
