## 4. 四条余量的落点与实现口径

### 4.1 余量 1：夹具覆盖面与数据驱动

现状是**两份并行的建库夹具**：`knowledge-library.mjs`（`dd10033` 新增，只有 `world_view` 数据）与 `stage-execution-spec.test.mjs` 内联的 `createKnowledgeDb`（另四个创作阶段，自带一份 schema 副本）。两份 schema 都不完整，且一条原则新增字段要改两处——「新增一条原则或公式只改夹具数据」这条在两份并存的前提下不可能成立。

落笔口径：

1. `knowledge-library.mjs` 是**唯一建库入口**，`stage-execution-spec.test.mjs` 改为调用它并把四个阶段的原则、公式作为入参传进去，删除内联 schema 与两条 `INSERT`。不得反向搬迁（把 helper 的结构改成内联那份），内联那份缺 `rationale` 列与全部 `NOT NULL` / `DEFAULT`。
2. 建表语句的列补齐到与生产库同名表一致：principles 15 列、formulas 14 列，列名与 `apps/api/app/db/session.py:673-689`、`:639-658` 逐列对齐。夹具列比生产库少，会让「查询引用了只有生产库才有的列」这类缺陷在测试里查不出来。
3. 覆盖面按六条补齐，每条对应一个用例名：五个创作阶段各有可命中的原则；公式的 `applicable_tags` 命中、不命中被过滤、为空视为无限制三种分支；原则靠 `skill_keys_json` 的 `stage:<阶段>` 命中（`stage-execution-spec.mjs:359` 的第二个条件）；原则缺通过标准时被 `assertCompletePrinciple`（`:339-346`）拒绝；库可读但零条已启用（`empty`）；库不可读（`unavailable`）。
4. 「数据驱动」的判定落在 diff 上：补覆盖面的改动里不得出现新的 `CREATE TABLE` 或 `INSERT` 语句，新增数据只能是传给 helper 的入参。

### 4.2 余量 2：测试绝不落到生产知识库

夹具在临时目录建库（`knowledge-library.mjs:75`），但默认路径仍指向 `stage-execution-spec.mjs:14` 的 `../data/workbench.sqlite3`；用例一旦忘记传 `knowledgeDbPath`，就会去读部署机上的真实库。现在靠的是每个调用点都记得传参这条约定。

落笔口径：涉知识库的测试文件在模块顶部把 `process.env.ORCA_SCRIPT_KNOWLEDGE_DB_PATH` 钉到本文件的临时库上，让忘记传参的用例也只能落到临时库；并新增一条**不传 `knowledgeDbPath`** 的用例，断言取到的是临时库里的知识（`knowledge_status` 为 `loaded`，`principle_count` 等于临时库的条数）。这条用例同时证明路径解析走的是显式配置而不是默认路径，在任何机器上结果都稳定。

不要用「断言默认路径不存在」来判定——开发机上 `data/workbench.sqlite3` 往往存在，判据会随机器变化。

### 4.3 余量 3：不可用与空库的如实归因（本包的主体余量）

分两侧，两侧的文案必须同口径，否则 Agent 读到的原因与运维看到的原因又会各说一套。

**知识层：三类「取不到知识」收敛为一种状态。** 实测有三条路径，行为却是三种：默认路径无库返回 `unavailable` 且不阻断（正确）；显式配置的路径不存在直接抛「剧本知识库不可用」（阻断）；库存在但缺知识表抛出英文 `no such table: script_library_principles`（阻断，且内部术语外泄）。后两条与裁定 4.1「不阻断」相反。落笔是把后两条也归为 `unavailable`：`resolveKnowledgeDbPath`（`:303-309`）不再抛错，`queryRows`（`:311-319`）对「表不存在 / 库打不开」容错后返回空集，状态由 `writeStageExecutionStrategy`（`:583` 起）统一给出 `unavailable`。执行策略文件的 `unavailable` 文案 `dd10033` 已写好，不动。

这不是把错误藏起来：`unavailable` 会写进执行策略文件（正文已要求「先联系管理员恢复剧本知识库」并说明成品质量会低于正常水平）、写进快照、写进运行记录事件。真正不可接受的是让用户的创作任务因为一件他无法处理的事而失败。

**服务端：两处 `else` 按状态分支。** `agent_runner.py` 的两个落点分别面向 Agent 与运维，都不是用户界面文案：

| 落点 | 行区间 | 面向 | 现状 |
| --- | --- | --- | --- |
| `stage_prompt` 的 `knowledge_summary` | `:3399-3413` | Agent（进提示词） | `loaded` 之外全部落进同一个 `else`（`:3406-3407`） |
| `prepare_stage_execution_strategy` 的 `knowledge_strategy_ready` 事件消息 | `:3859-3866` | 运维（进 `agent_events` 与 ZDebug 准备日志） | 同一个 `else`（`:3864-3865`） |

两处按同一张映射表落笔，文案沿用执行策略文件的既有说法，不造新词：

| `knowledge_status` | 归因 |
| --- | --- |
| `loaded` | 已获取 N 条创作原则和 M 条策略公式（`principle_count` 为 0 时不得说「已获取 0 条」，按 `empty` 归因） |
| `empty` | 创作知识库中还没有适用于本阶段和当前剧本标签的创作原则，本次按 Skill 固定要求执行 |
| `unavailable` | 创作知识库当前无法读取，本次按 Skill 固定要求执行 |
| `skipped_unresolved_profile` | 剧本标签尚未全部确定，本次不获取创作原则和策略公式 |
| 清单外取值或缺失 | 执行策略没有说明本次的知识获取结果，本次按 Skill 固定要求执行 |

事件的 `raw_json` 已经带着整个 payload，`knowledge_status` 本身可检索，不需要另加字段。

### 5.2 `agent_runner.py` 的行区间持有怎么登记

4. 只有这两个行区间可改。同一文件的其他行（含 `KNOWLEDGE_PREPARED_STAGES` 常量、`ZDEBUG_PREPARATION_TITLES`、`prepared` 的组装点 `:11693`、`:11767`）都不在持有范围内；确需改动时另行登记。

## 7. 与上游文档的差异

按裁定 9.6「发现冲突先登记勘误再动手」登记。编号、归属与文件边界一律不动。

### 7.1 后端调用路径上 `unavailable` 不可达，真正会发生的是 `empty`

余量 3.1 第 3 条把余量表述为「`unavailable` 计入任务运行记录」。实测三点：

1. 后端每次调工具都注入 `ORCA_SCRIPT_KNOWLEDGE_DB_PATH`（`agent_runner.py:3647`、`:3798`、`:4396`），取值是 `settings.database_path`——就是应用自己的库。
2. 配置了路径而文件不存在时，`resolveKnowledgeDbPath` 抛错、工具非零退出，后端走 `STAGE_STRATEGY_FAILED`，`unavailable` 根本传不回来。
3. 知识表由后端 `CREATE TABLE IF NOT EXISTS` 建好，全新部署的实际形态是「表结构齐全、零条已启用知识」，也就是 `empty`——正是 `dd10033` 的动机场景。

**结论**：第 3 条的收益主要落在 `empty` 上，`unavailable` 是命令行直调与测试环境下的形态。两者的归因都要改，但验收不能只盯 `unavailable`，第 6 节的验收 7、8 因此按四态逐一判定。这也是这条余量能在不接真实知识库的情况下二值验收的原因：两个落点都能直接单元测试（本槽已实测跑通）。

### 7.2 「库不可读」有两条会阻断的路径，与裁定 4.1 相反

余量与切片都只写「不得把知识库不可用改成阻断主链路」，默认现状已经不阻断。实测有两条路径确实阻断：显式配置的路径不存在（抛中文错误）、库存在但缺知识表（抛英文 `no such table`）。裁定 4.1 已定「不阻断，只要求状态真实且可见」，因此这两条收敛进本包的 4.3，落点全在本包首位持有的 `stage-execution-spec.mjs` 内，不扩范围：`get-execution-strategy.mjs` 五份只透传 `snapshot.knowledge_status`，一行都不用改。

### 7.3 夹具是两份，持有清单需补一个文件

裁定 8.2 给 `31` 的清单是 `stage-execution-spec.mjs`、`world-view-execution-spec.test.mjs` 与「新增夹具与建库脚本」，成文时 `knowledge-library.mjs` 还不存在，`stage-execution-spec.test.mjs` 里的内联建库也没被登记。余量第 1 条要求的「新增知识只改数据」在两份夹具并存时不可能成立，因此本规格把 `stage-execution-spec.test.mjs` 补进 5.1 的持有清单。归属不变、文件边界不动，补的是一个此前没人登记的文件；本批无他槽持有它（`29` 独占 `SKILL.md` 与 `references/`，`36` 的清单里没有它）。

### 7.4 余量记的行号仅在整合态成立，按函数名定位

余量 3.1 与 §6 记 `:3406-3407`、`:3864-3865` 与持有区间 `:3399-3413`、`:3859-3866`，本槽在整合态逐处复现一致（六个前置提交都不碰 `agent_runner.py`）。但 `42`、`37` 一旦在同文件落地，行号即漂移。**登记与评审按函数名加分支定位**（`stage_prompt` 的知识摘要分支、`prepare_stage_execution_strategy` 的事件消息分支），行号只作为当前快照的参考。

### 7.5 一处上游未登记的同源缺陷：`loaded` 却零条原则

`dd10033` 在门禁侧加了「标记已获取却零条原则不放行」，但提示词侧没有对应保护：实测传 `loaded` 且 `principle_count` 为 0 时，提示词照样写「已获取 0 条创作原则和 0 条策略公式。」这与门禁的判定互相矛盾，且同属「状态必须真实」这条裁定，落点也在本包持有的行区间内，因此并入 4.3 的映射表与验收第 8 条，不另开工作项。
