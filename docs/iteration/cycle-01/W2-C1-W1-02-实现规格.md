## 0. 这一项要解决的问题

用户在界面上看到的每一条失败，现在有三种互不兼容的形状、两种语言、零个可对账的标识。同一句红字既可能是"会话过期了"，也可能是"后端整个不可用"，用户无法区分，客服也无法反查。

本项做三件事，做完之后其余失败路径的工作项才有共同的地基：

1. **一种形状**：任何接口的失败响应都是同一个错误信封，包含用户能读懂的"发生了什么"与"下一步怎么办"。
2. **一个出处**：错误码注册表是前后端唯一的定义处，后端改措辞不会静默破坏前端。
3. **一条追踪线**：用户看到的提示里带一个可复制的追踪号，能在日志与审计里查到对应的内部原因，而内部原因本身不出网。

本项**不做**呈现方式、不做重试与超时、不做会话失效后的恢复流程。边界见第 10 节。

## 2. 错误信封

### 2.1 字段与约束

字段名、含义、约束全部照抄总控 2.6，本规格只补"由谁填"与"缺省怎么办"两列，供实现时逐字段落地。

| 字段 | 含义 | 约束 | 由谁填 / 缺省 |
| --- | --- | --- | --- |
| `code` | 稳定错误码 | 必填，注册表中唯一 | 抛错点显式给出；未显式给出时由异常处理器按状态码回落到兜底码（见 4.2） |
| `category` | 失败类别 | 必填，取值见 2.4 | 抛错点给出；未给出时按 2.4 的状态码映射表推导 |
| `retryable` | 是否可重试 | 必填。为真时界面给出显式重试入口；请求核心不得隐式自动重发写操作 | 由注册表条目声明，抛错点可覆盖 |
| `message` | 发生了什么 | 必填，中文用户视角，不含内部术语、英文标识、HTTP 状态码 | 注册表条目；抛错点可传入同样满足约束的具体文案 |
| `hint` | 下一步怎么办 | 必填，中文用户视角，不得把"刷新页面"作为唯一出路 | 注册表条目 |
| `traceId` | 追踪号 | 必填，可在错误提示中复制，与日志和审计记录对应 | 异常处理器统一填入，值等于本次响应 `x-request-id` 头 |
| `details` | 结构化明细 | 可选。校验失败等场景在此结构化传递，客户端不得从文案里解析 | 抛错点给出，形状按场景约定（2.5） |
| `root_cause` | 内部原因 | **不出网**，只进日志与审计，通过 `traceId` 关联 | 抛错点给出；异常处理器负责在序列化时剥离 |

`traceId` 是全仓唯一的驼峰字段名，与后端其余字段的下划线风格不一致。这是总控 2.6 的原文，本规格照此实现以免两侧各猜一套；命名一致性的处置见勘误 E-11。

### 2.2 响应形状与兼容策略

失败响应体：

```json
{
  "error": {
    "code": "STAGE_FILE_MISSING",
    "category": "input",
    "retryable": false,
    "message": "这个阶段的文档还没有生成，暂时打不开。",
    "hint": "回到阶段列表，先完成前一个阶段，再回来查看这一份。",
    "traceId": "3f9c1a7e5b2d4c80",
    "details": {}
  },
  "detail": "这个阶段的文档还没有生成，暂时打不开。"
}
```

`detail` 是 `error.message` 的**兼容镜像，恒为字符串**。保留它有两个不可回避的理由，实现时不得省略：

1. `C1-W1-03` 尚未开工，`api-client.ts` 与 `admin-api.ts` 当前都读 `payload.detail`。保留镜像后，本项一落地用户立刻看到中文提示，W2 出口条件"服务端错误文案无纯英文"当场成立，不必等前端请求核心。
2. `/openclaw/v1/*` 是对外机器接口，`docs/OpenClaw批量任务API.md` 描述的调用方在仓库外。改形状等于破坏外部契约；加字段不破坏。

`detail` 的退场条件写在第 9 节：`C1-W1-03` 全量改读 `error` 之后，由 W3 的收口项移除，**不在本项内移除**。

### 2.3 三种现存形状如何收敛

实测第 5 节记录了同一层失败的三种形状。收敛方式逐条落定：

| 现状形状 | 出现场景 | 收敛后 |
| --- | --- | --- |
| `{"detail": "一句话"}` | 401 / 404 / 405 / 409，共 397 处字面量 `detail=` | 由 `HTTPException` 处理器包成信封；`detail` 镜像保持原位 |
| `{"detail": [ {type, loc, msg, input}, … ]}` | 422 校验失败，140 个接口中 138 个可触发 | 由 `RequestValidationError` 处理器改写：`input` 一律剥离，逐项进 `details.fields`，`message` 汉化 |
| 空响应体、无 `content-type` | 后端不可用时代理层的 500 | **服务端侧无法修复**，代理层归 `C1-W1-03`，本项在第 9 节锁定它必须合成的信封 |
| 框架自带的 `{"detail":"Not Found"}`、`{"detail":"Method Not Allowed"}` | 路由不存在、方法不允许 | 注册 `StarletteHTTPException` 处理器一并汉化，不留框架默认文案 |
| 未捕获异常的 500 | 任何内部异常 | 注册兜底处理器：响应只有信封，`root_cause` 只进日志 |

### 2.4 `category` 取值与状态码映射

总控 2.6 写「沿用 `AgentExecutionError` 的类别取值」。`main` 上实际在用的是 5 个：`runtime`（70 处）、`quality`（40 处）、`input`（34 处）、`capacity`（1 处）、`billing`（1 处）。这 5 个不足以承载 HTTP 侧的分支需要——401、403、409 落进任何一个已有取值，客户端都无法据此决定该显示"重新登录"、"申请权限"还是"并排对比"，而这三条正是 `C1-W1-04`、`C1-W1-06`、`C1-W1-10` 各自的入口。

**本规格扩充三个 HTTP 专用取值，共 8 个，不再增加。** 这是对 2.6"沿用"表述的扩充，已按裁定 9.6 在勘误 E-9 登记。

| `category` | 含义 | 客户端典型分支 | 默认状态码 |
| --- | --- | --- | --- |
| `auth` | 身份未确认或已失效 | 就地重新登录（`C1-W1-04`） | 401 |
| `permission` | 身份有效但无此权限 | 说明缺哪项权限，给出申请路径 | 403 |
| `input` | 用户提供的内容不满足要求 | 定位到对应输入项 | 400 / 404 / 413 / 422 |
| `conflict` | 与服务端当前状态冲突 | 并排对比与三选一（`C1-W1-10`） | 409 |
| `capacity` | 容量、并发或限流 | 稍后重试，可自动退避 | 429 / 503 |
| `billing` | 额度不足或计费受限 | 引导查看额度 | 402 / 403 |
| `quality` | 产物未通过质量判定 | 展示未通过项（`C1-W1-42`） | 422 / 409 |
| `runtime` | 服务端执行失败 | 显式重试入口 + 追踪号 | 500 / 502 / 504 |

映射表只是抛错点未显式声明时的推导缺省值，显式声明优先。`retryable` 不由 `category` 推导，逐码声明。

### 2.5 `details` 的形状约定

`details` 只承载客户端需要按结构分支的数据，**不承载任何供人阅读的完整句子**——句子在 `message` 与 `hint` 里。本项要落地两种形状，其余场景由各自工作项在需要时追加。

**校验失败**：

```json
"details": { "fields": [ { "path": "body.username", "label": "登录账号", "reason": "必填" } ] }
```

- `input` 字段一律不出现（FM-17）。
- `path` 是后端字段路径，**只供程序使用**，界面不得直接渲染；渲染方式归 `C1-W1-06`。
- `label` 来自字段标签表；**查不到标签时省略 `label`，绝不回落成 `path`**——回落等于把英文字段名重新送到用户眼前（FM-18）。
- `reason` 来自 Pydantic 错误类型到中文说明的映射表，不是 Pydantic 原文。

**阶段检查未通过**：

```json
"details": { "issues": ["第 3 集台词与人物小传冲突", "第 7 集缺少场景标题"] }
```

这一项是 `page.tsx:193-208` 那段"从错误文案里 `indexOf("{")` 再 `JSON.parse`"写法的服务端前提，来源见 3.7。

## 3. 必须收敛的失败路径

以下八条全部来自实测的运行时取证，不是源码推断。每条给出实测事实、本项要做什么、以及在第 6 节里对应哪条验收。**没有对应验收编号的条目不算做完。**

### 3.1 FM-17 校验失败把用户提交的内容原样回显，包含口令 · 严重

实测：`POST /api/auth/login` 只传 `{"password":"super-secret-value"}`，响应体是

```
{"detail":[{"type":"missing","loc":["body","username"],"msg":"Field required","input":{"password":"super-secret-value"}}]}
```

密码明文经代理层原样到达浏览器，并进入前端错误处理链路；`page.tsx:193-208` 还会把错误文案里的 JSON 解出来展示，任何采集前端错误的手段都会一并采走。140 个接口中 **138 个**声明了 422，都可触发。

本项要做：注册 `RequestValidationError` 处理器，构造 `details.fields` 时**只取 `loc` 与错误类型，不取 `input`**。剥离必须发生在构造侧而不是序列化侧——把 `input` 读进内存再指望后面删掉它，就会在下一个改这段代码的人手里漏回去。

→ 验收 A-1、A-2。

### 3.2 FM-18 与 GATE-01 盲区一：校验失败的文案是英文字段名加英文说明 · 高

实测：`apiErrorMessage()` 把 422 每一项拼成 `loc.join(".")：msg`，用户看到 `password：Field required`。终端用户是编剧，这两样都读不懂，也不知道该改哪个输入框。

**这条路径完全不在 GATE-01 的检测范围内**：GATE-01 只扫 Python 源码里的 `detail=` 字面量，而这些文案由 Pydantic 生成。把 43 条英文 `detail=` 全部改完，命令输出 0 条，138 个接口的校验失败仍然是英文（实测 3.4 节）。

本项要做两件事：

1. 建 Pydantic 错误类型 → 中文说明的映射表，覆盖 `missing`、`string_type`、`string_too_short`、`string_too_long`、`int_parsing`、`int_type`、`greater_than_equal`、`less_than_equal`、`enum`、`value_error`、`json_invalid`、`literal_error` 等实际出现的类型；映射缺失时回落为一句不点名类型的中文说明，**不回落成 Pydantic 原文**。
2. 建字段标签表，至少覆盖用户真正会填表的五个入口：`POST /auth/login`、`POST /auth/change-password`、`POST /projects`、`PUT /projects/{id}/files/{stage}`、`POST /batch-tasks`。这五个入口的任一字段校验失败时，`message` 里出现的是"登录账号"这样的中文标签，不是 `username`。

→ 验收 A-3、A-4。

### 3.3 GATE-01 盲区二：框架自带的英文文案

实测记录里两条与源码无关：

| 请求 | 响应 |
| --- | --- |
| `GET /completely/unknown` | `{"detail":"Not Found"}` |
| `GET /projects/1`（该路径只有 `DELETE` 与 `PATCH`） | `{"detail":"Method Not Allowed"}` |

这两条由 Starlette 产生，`detail=` 检索永远抓不到，未捕获异常的 500 同理。本项要做：注册 `StarletteHTTPException` 与 `Exception` 兜底处理器，让 404、405、500 也走同一个信封，文案是中文。

→ 验收 A-5。

### 3.4 GATE-01 盲区三：非字面量 `detail=`，含 13 处把子进程 stderr 直送用户

`detail=` 后面不是字符串字面量的抛错点共 **33 处**（17 处 `detail=str(...)`、8 处 `detail=detail`、其余为变量与调用），检索命令一处都抓不到。其中 **13 处**把子进程的 `stderr` / `stdout` 直接当成用户文案：

| 文件 | 行 | 抛出方式 | 兜底文案 |
| --- | --- | --- | --- |
| `services/workspace_service.py` | `:762`、`:810`、`:1079`、`:1358`、`:2352` | `HTTPException` | 中文 |
| `services/workspace_service.py` | `:3759` | `HTTPException` | **英文** `Agent project initialization failed` |
| `services/memory_sync_service.py` | `:1006` | `HTTPException`（经 `_approval_conflict`） | **英文** `f"{stage} check failed"` |
| `services/script_library_service.py` | `:373`、`:403` | `HTTPException` | 中文 |
| `services/novel_analysis_admission.py` | `:63` | `HTTPException` | 中文（已从工具 JSON 里取 `message`，是正确做法的样板） |
| `services/system_agent_evolution_service.py` | `:515` | `RuntimeError` | **英文** `f"exit code {result.returncode}"` |
| `services/preference_summary_service.py` | `:311` | `RuntimeError` | **英文** 同上 |
| `services/ai_skill_runner.py` | `:113` | `RuntimeError` | **英文** 同上 |

两重问题：英文兜底文案在验收命令的盲区里；子进程 stderr 属内部原因，按 2.1 约束**不得出网**，实测 FM-26 已抓到同类载荷里带服务器绝对路径。

本项要做，按抛出方式分两档：

- **10 处 `HTTPException`**：改为 `root_cause=` 承载 stderr / stdout、`message` 取注册表文案。`novel_analysis_admission.py:63` 的写法（解析工具 JSON 的 `message` 字段、失败回落中文）是本仓库已有的正确样板，其余各处按它对齐。
- **3 处 `RuntimeError`**：这三条走的是后台任务失败通道，不产生 HTTP 响应，**不套信封**。只做两件事：英文兜底文案 `exit code N` 改中文，stderr 从消息里移出改为写日志。它们最终呈现给用户的措辞归 `C1-W1-42`，本项只负责让这里不再吐英文与内部输出。

→ 验收 A-6、A-7。

### 3.5 FM-19 后端不可用时代理层返回空响应体的 500 · 高

实测：停掉 API 后请求 `/api/projects` 与 `/api/auth/login`，两者都是 `HTTP 500` + 空响应体、无 `content-type`。57 个 `route.ts` 中只有 2 个有 `try`；`parseJson` 解不出内容就回落到状态码文案，用户看到"请求失败（500）"。产品对"后端整体不可用"这一最常见的运维故障没有任何专门表述，与"某个项目不存在"共用同一句红字。

**本项修不了这一条**：代理层的 `apps/web/src/lib/server/backend.ts` 与 57 个 `route.ts` 都是 `C1-W1-03` 的持有文件（落地切片 4.10）。本项能做且必须做的是把代理层该合成什么写死成契约，见第 9.3 节；`C1-W1-03` 照此实现即可，无须再回来对齐。

→ 本项无验收项；`C1-W1-03` 的验收项在 9.3 节列出，本项只负责锁定形状。

### 3.6 FM-21 追踪号丢在代理层，而最需要号的 500 本来就没有号 · 中

实测：同一个 404，后端响应带 `x-request-id`（命中 1），代理层响应不带（命中 0）。全仓 `apps/web/src` 对 `x-request-id` 的引用为 0 处。

这条裂缝有两半，分属两侧：

- **代理层丢弃**：`backend.ts:36-41` 的 `proxyJson` 构造响应时只复制 `content-type`。归 `C1-W1-03`，契约见 9.3。
- **服务端自己就缺一半**：`main.py:59-69` 的中间件把 `response.headers["x-request-id"] = request_id` 写在 `try/finally` **之外**。`call_next` 抛出未捕获异常时这一行根本不执行，**最需要追踪号的 500 响应反而没有号**。这一半归本项。

本项要做：让 `x-request-id` 在任何出口都存在——正常响应、`HTTPException`、校验失败、未捕获异常四条路径的响应头与 `error.traceId` 取同一个值。实现上把号的生成与绑定留在中间件，由异常处理器从审计上下文取用，不要在两处各生成一次；否则用户复制的号与日志里的号不是同一个，追踪线依然断着。

→ 验收 A-8、A-9。

### 3.7 FM-05 的源头：前端反解 `issues` 是因为服务端把 CLI 的 JSON 塞进了句子

实测记录了前端"从错误文案里 `indexOf("{")` + `JSON.parse` 反解 `issues`"这个写法（`page.tsx:193-208`），但没有定位服务端出处。本规格定位到了：

```
memory_sync_service.py:1006  detail = (process.stderr.strip() or process.stdout.strip() or f"{stage} check failed")[-2000:]
memory_sync_service.py:1007  raise _approval_conflict(f"阶段检查未通过：{detail}")
```

阶段检查脚本的 stdout 是 JSON，于是一整段 JSON 被拼进一句中文里发给浏览器，前端只能把它抠出来再解析。**只删前端那段反解写法会让用户彻底看不到未通过原因**，所以服务端必须先把它结构化——这是本项的活，前端移除反解是 `C1-W1-03` 的活，两者顺序不能倒。

本项要做：`:1005-1013` 区间改为解析检查脚本的 JSON 输出，未通过项进 `details.issues`（形状见 2.5），`message` 用注册表里的一句中文，脚本原始输出进 `root_cause`。

`memory_sync_service.py` 在裁定 8.2 的文件锁队列里只登记了 `C1-W1-34`（`:63-73` 受保护文件名）与 `C1-W1-38`（指纹清单），漏了本项。改动区间互不重叠，登记后可并行，已在勘误 E-10 登记。

→ 验收 A-10。

### 3.8 会话过期时用户看到的是 `Invalid token`，不是 `Session expired`

实测 3.3 节纠正了一处方向性误解。`dependencies.py:53-64` 的判定顺序是：

| 情况 | 现文案 | 行 |
| --- | --- | --- |
| 没带凭据 | `Not authenticated` | `:54` |
| 签名不对**或令牌已过期** | `Invalid token` | `:58` |
| 用户被停用 | `Inactive user` | `:61` |
| `auth_version` 变了（改密码、强制下线） | `Session expired` | `:64` |

`decode_access_token()` 对"签名错误"和"已过期"都返回 `None`，两者合并成 `Invalid token`。实测用一个 `exp` 已过期的合法签名令牌请求，得到的确实是 `Invalid token`。也就是说：**最常见的 7 天自然过期，文案是 `Invalid token`；`Session expired` 只在改密码这类场景出现。**

后果直接落在 `C1-W1-04` 上——它要区分"会话失效"与"账号不匹配"，而现有文案分支是错的，按文案分支会把两种情况判反。裁定 5.2 第 5 项已划定边界：**这 4 条 401 文案由本项一并中文化并给出 `code`**，`C1-W1-04` 只负责语义区分与前端重新登录流程。本规格进一步落定：语义分开的动作也在本项完成，因为它不是"处理流程"，而是"后端能不能把这两件事说成两件事"。

本项要做：让 `decode_access_token()` 的失败原因可区分（过期 / 签名或格式无效），四条路径各给一个独立错误码：

| 情况 | 错误码 | `category` | `retryable` | `message` 意图 |
| --- | --- | --- | --- | --- |
| 没带凭据 | `AUTH_REQUIRED` | `auth` | false | 还没有登录 |
| 令牌已过期 | `SESSION_EXPIRED` | `auth` | false | 登录状态已经到期 |
| 签名或格式无效 | `SESSION_INVALID` | `auth` | false | 登录状态无法识别 |
| 用户被停用 | `ACCOUNT_DISABLED` | `permission` | false | 账号已被停用 |
| `auth_version` 变了 | `SESSION_SUPERSEDED` | `auth` | false | 账号在别处改过密码或被强制下线 |

五个码对应四条现有抛错点加一条新分支（过期与无效拆开）。文案按 AGENTS.md 原则 3 从用户视角写，不出现"令牌"、"签名"、`auth_version` 这类词。

`dependencies.py` 的持有顺序是 `02` → `04`（裁定 8.1），本项是队列首位。

→ 验收 A-11。

## 4. 错误码注册表

### 4.1 位置与形状

| 项 | 决定 |
| --- | --- |
| 唯一出处 | `apps/api/app/core/error_codes.json` |
| 为什么是 JSON 而不是 Python 模块 | "前后端共用单一出处"（总控 2.6）要求两侧都能读。Python 模块前端读不了，跨 app 直接 import 会把 `apps/web` 的构建绑到 `apps/api` 的目录结构上 |

单条条目：

```json
{
  "STAGE_FILE_MISSING": {
    "status": 404,
    "category": "input",
    "retryable": false,
    "message": "这个阶段的文档还没有生成，暂时打不开。",
    "hint": "回到阶段列表，先完成前一个阶段，再回来查看这一份。"
  }

```

### 4.2 命名、兜底码与"不许裸字符串"

- 码名用大写下划线，与 `AgentExecutionError` 现有 71 个码同一风格，不引入第二套风格。
- 每个状态码有一个兜底码（如 `REQUEST_INVALID` / `SERVER_ERROR`），供尚未逐条改写的抛错点使用。兜底码**不是长期归宿**：本项完成时，43 条英文文案与 13 处 stderr 直送路径必须都有专属码，剩余的中文 `detail=` 字面量可暂用兜底码，其收口不在本项范围（第 12 节）。
- `Unknown stage`（12 处）与 `Stage file not found`（7 处）是同一个问题的 19 次复制。按领取表做法要点，收敛为共用的抛错辅助函数，**不逐处硬编码**——否则下一个人加第 13 处 `Unknown stage` 时不会想到还要改文案。

### 4.3 校验脚本与接入 `npm run check`

新增 `apps/api/app/scripts/check_error_registry.py`，判定项：

1. 每个条目的 `message` 与 `hint` 都非空。
2. `message` 与 `hint` 里不出现英文单词——判定方式是拉丁字母串必须落在注册表文件自身声明的允许清单内（`Word`、`AI` 这类确实要给用户看的词写进清单，其余一律不通过）。这样规则本身也是单一出处，不散落在脚本里。
3. `category` 取值在 2.4 的 8 个之内。
4. 全仓 `AgentExecutionError(...)` 用到的码都在注册表里（现存 71 个），杜绝第二份注册表。
5. `apps/web/src/lib/error-codes.ts` 与 JSON 一致。
6. 抛错点不出现裸字符串错误文案（对应领取表验收第 7 条）。

接入点：根 `package.json` 的 `check:api` 与 `check` 两行各追加一段调用。这两行在 `C1-W1-13` 的持有文件里，处置见 8.2 与勘误 E-8。

### 4.4 和 71 个 Agent 失败码的关系

`AgentExecutionError` 已有 71 个码，各自带中文 `user_message`，都没有 `hint`。本项**不给这 71 个码补 `hint`**——那是"检查未通过时给用户一句能看懂的原因"（`C1-W1-42`，W3）的活，提前做会和它撞在 `agent_runner.py` 上。

本项对它们只做一件事：把码、`category`、`retryable` 登记进同一份注册表，`message` 直接取现有 `user_message` 不改写，`hint` 允许为空并标记归属 `C1-W1-42`。校验脚本因此能拦住"新增一个不在注册表里的失败码"，而 HTTP 侧的 `hint` 必填约束不受影响。这条依赖已在勘误 E-12 登记，供 `C1-W1-42` 领取时对照。

## 6. 验收

十八条（A 组 11 + B 组 3 + C 组 4）全部是二值判定（做到 / 没做到）。**这是本项唯一的验收出处**：完成时自检、内容质量校验、AI 审稿、W5 独立核验都按同一批编号取用，不得各自另立标准，也不得由实现槽自行放宽。

### A 组 · 服务端错误契约

| # | 判定 | 方式与基线 |

## 9. 与 `C1-W1-03` 的接口形状约定

`C1-W1-03` 尚未开工。总控 4.2 要求"接口先行即可并行"，落地切片 4.10 要求它开工首个提交就落下四个接入位。**本节是这四个接入位中"错误对象形状"这一位的定稿**，`C1-W1-03` 直接照用，不需要再和本项对齐一次；另三位（幂等键注入签名、会话拦截钩子、连接状态信号出口）不属本项，由 `C1-W1-03` 自行定义。

### 9.1 错误对象形状（本项交付，`C1-W1-03` 消费）

`apps/web/src/lib/api-error.ts` 导出：

```ts
export type ApiErrorCategory =
  | "auth" | "permission" | "input" | "conflict"
  | "capacity" | "billing" | "quality" | "runtime";

export class ApiError extends Error {
  readonly code: string;
  readonly category: ApiErrorCategory;
  readonly retryable: boolean;
  readonly hint: string;
  readonly traceId: string;
  readonly status: number;
  readonly details?: Record<string, unknown>;
}

export function apiErrorFromResponse(
  status: number,
  body: unknown,
  traceIdHeader: string | null
): ApiError;
```

约定五条，双方都不得单方面改：

1. `ApiError` 继承 `Error`，`message` 即信封的 `message`。现有 `catch (error) { error instanceof Error ? error.message : ... }` 的调用点因此**无需改动即可继续工作**，`C1-W1-03` 不必为了引入类型化错误而一次性改完全部调用点。
2. 前端按 `code` 分支，读不到 `code` 时回落 `message`，**禁止对错误文本做字符串匹配**（总控 2.6）。
3. `traceId` 优先取 `x-request-id` 响应头，头缺失时取 `error.traceId`；两者都没有时置空字符串，不自行编号。
4. `details` 原样透传给调用方，请求核心不解释其内容。
5. 信封解析失败（响应不是 JSON、或没有 `error` 字段）时构造 `code: "RESPONSE_UNREADABLE"`、`category: "runtime"`、`retryable: true` 的对象，`message` 是一句中文，**不含 HTTP 状态码**。

### 9.2 `detail` 兼容镜像的退场

本项保留 `detail` 字符串镜像（2.2）。`C1-W1-03` 全量改读 `error` 之后，`detail` 只剩 `/openclaw/v1/*` 的外部契约需要。**移除时机不在 W2**：由 W3 的收口项按"`rg -n 'payload\.detail' apps/web/src` 输出 0 条"判定后，再决定是否只在 `/openclaw/` 路由族保留。本项与 `C1-W1-03` 都不移除。

### 9.3 代理层必须合成的信封（`C1-W1-03` 交付）

本项修不了代理层（3.5、3.6），但形状必须现在定，否则 `C1-W1-03` 会另造一套，用户又会遇到两种失败长相。下面三条是 `C1-W1-03` 的义务，本规格首提即锁定；`C1-W1-03` 的验收槽按此核对。

| 场景 | 代理层必须返回 |
| --- | --- |
| 后端连不上（FM-19，基线：空体 500、无 `content-type`） | `code: "BACKEND_UNREACHABLE"`、`category: "runtime"`、`retryable: true`、`message`/`hint` 说明是服务暂时连不上而不是用户操作有问题、`traceId` 由代理层生成并带可区分前缀 |
| 后端超时 | `code: "BACKEND_TIMEOUT"`、`category: "runtime"`、`retryable: true` |
| 后端有响应 | 原样透传响应体与状态码，**并把 `x-request-id` 响应头一并复制**（`backend.ts:36-41` 现在只复制 `content-type`） |

前两条要求 57 个 `route.ts` 有统一兜底（现在只有 2 个有 `try`）。代理层生成的 `traceId` 与服务端的不同源，前缀必须可区分，否则客服拿号去后端日志里查会查不到而误判为丢日志。
