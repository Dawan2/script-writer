## 4. 七条勘误

### E-1 裁定第 7 节漏登记 `dd10033`（阻塞）

裁定第 7 节把 `cursor/w1-failure-path-contract-mapping-058e` 列为第六项前置，但内容只写「`apps/api/requirements-dev.txt` 与 README 测试依赖说明」，即只覆盖该分支的 `6a68305`。该分支的第二个提交 `dd10033` 未被登记。

`dd10033` 的内容正是 `C1-W1-31` 的主体：`knowledge_status` 从「只看剧本标签是否齐备」改为如实反映查询结果的三态（`loaded` / `empty` / `unavailable`）、门禁新增「标记已加载却零原则不放行」、执行策略按状态给出各自说明、并补上最小知识库夹具 `Agents/tests/helpers/knowledge-library.mjs`。行为与裁定 4.1「不阻断，但状态必须真实」的裁定完全一致——阶段仍可完成，完成记录写明本次没有可用的创作原则与策略公式。

它同时改了 `apps/api/tests/test_script_output_contracts.py`，补进 `2.1-world-view.json` 夹具，这落在 `C1-W1-36` 的持有文件内。

**建议**：裁定第 7 节补登第七项 `dd10033`，阻塞的工作项记 `C1-W1-31`、`C1-W1-36`。理由与其余六项相同——不先并入就会重做或被覆盖，而它的改动面比六项中任何一项都大。原稿 3.3 已把它列为 IN-6，本文的实测支持这一处理。

### E-2 裁定 4.5「装后 454 项 4 失败」漏了 8 项错误

裁定 4.5 的基线表把 `test:api` 现状记为「未装测试依赖时 450 项可执行 + 9 项模块加载错误；装后 454 项 4 失败」，即把 9 项错误全部归因于没装依赖。

实测的分解不是这样。9 项错误由两部分组成：**1 项**是 `test_openclaw_api` 整个模块因缺 `httpx` 无法导入，装依赖即消失；**8 项**是 `test_script_sync_service` 的 `_utc_now_iso` 未定义名，装多少依赖都在，只能由 `12c9ef7` 解掉。所以「装后」的真实状态是 **454 项 4 失败 + 8 错误**。

**建议**：该单元格改为「未装测试依赖时 450 项可执行 + 9 项错误（1 项模块加载 + 8 项 `NameError`）；装后 454 项 4 失败 + 8 错误」。「集成槽并入既有修复后」一栏的「454 项 4 失败」经实测正确，不改。

### E-3 `C1-W1-31` 与 `C1-W1-36` 的存量失败承接量已变

裁定 6.1 给 `C1-W1-31` 写「解 `test:agent` 4 项存量失败，越早越好」，给 `C1-W1-36` 写「解 `test:api` 4 项存量失败」；第 7 节又写 `16cc256` 是「`C1-W1-31` 完成判定的起点」；6.4 第 2 条据此排出口条件。

`dd10033` 并入后这三处都不成立：`test:agent` 的 4 项失败已归零（且用例数从 81 增至 83），`test:api` 的 4 项失败降为 2 项，**且剩余 2 项的失败原因已经变了**——不再是「世界观产物缺失」，而是夹具工作区里没有执行策略文件，`check-trial` / `check-full` 返回「执行策略缺失或已失效」。剩余两项为 `test_full_generation_normalizes_legacy_trial_episode_headings` 与 `test_trial_and_full_checks_allow_optional_target_dialogue`。

**建议**：

- 裁定 6.1 中 `C1-W1-31` 的「开工前提与验收要点」改为：前置含 `dd10033`；本项只做余量（夹具覆盖度、测试不触生产库路径、知识库路径与不可用行为的显式契约、`unavailable` 计入任务运行记录），完成判定改为「干净检出上 `test:agent` 不少于 83 项且 0 失败」。
- 裁定 6.1 中 `C1-W1-36` 的完成判定从「解 4 项」改为「从整合后的 454 项 2 失败降为 0 失败」，并写明须补齐夹具的执行策略文件而不是削弱断言——这 2 项覆盖的正是单集字数下限与可选目标语台词两条规则，放宽断言等于拆掉回归网。
- 裁定 6.4 第 2 条改为：`test:agent` 由集成前置解至 0 失败并由 `C1-W1-31` 保持不回退；`test:api` 由集成前置解至 2 失败、`C1-W1-36` 解余下 2 项。
- 裁定第 7 节中「`16cc256` 是 `C1-W1-31` 完成判定的起点」删去。`16cc256` 解的是单剧蒸馏夹具那 1 项，与知识库无关；`C1-W1-31` 的起点是 `dd10033` 之后的 83 项 0 失败。

### E-4 `C1-W1-28` 标「无前提」，但前置第六项正在改 `README.md`

裁定 6.1 给 `C1-W1-28` 的独占文件是「`README.md`、`docs/` 三份历史 Agent 文档的失效标注」，开工前提写「无前提。纯文档」。

但集成前置的第六项 `6a68305` 正是往 `README.md` 插入一节「测试」（说明先装 `requirements-dev.txt` 再跑 `npm test`）。`C1-W1-28` 若先开工，这一节要么被它的改写覆盖，要么在并入时撞车；本文实测的并入落盘文件里，`README.md` 是仅有的两个之一。

**建议**：`C1-W1-28` 的开工前提从「无前提」改为「须先并入 `6a68305`」，并在其范围里追加一条——核对新增的「测试」章节与修订后的首次安装说明一致（安装说明需补 `cd Agents && npm install`，根 `package.json` 的 `workspaces` 只含 `apps/web`，本槽已核实）。原稿 4.5 的 P-04 同样把前置记为「无」，一并适用。

### E-5 「撤回 `requirements.txt` 改动」只在整分支合并时才需要

裁定 4.4 要求「集成槽并入时撤回对 `requirements.txt` 的改动」，第 7 节同样写「按 4.4 同时撤回 `248c1f6`」。

按第 3.1 节逐个 cherry-pick 时没有可撤回的东西：`248c1f6` 从不进入序列，实测并入后 `apps/api/requirements.txt` 中 `httpx` 出现 0 次、`requirements-dev.txt` 中出现 1 次，4.4 的裁定自动成立。只有当集成槽选择整分支合并 `cursor/w1-agent-intelligence-plan-058e`（那会连带 `248c1f6` 与三份 Agent 智能化文档）时，才需要一次显式的 revert。

**建议**：裁定 4.4 与第 7 节的表述改为条件式——「按第 3.1 节逐个 cherry-pick 时无需撤回；若整分支合并，须显式 revert `248c1f6` 对 `requirements.txt` 的那一行」。这条不改结论，只是避免集成槽为一个不存在的改动去找撤回点。

### E-6 「78 个 `.mjs`」是非测试脚本口径

裁定 6.4 第 8 条写「`npm run check` 覆盖全部 78 个 `.mjs`」。实测全仓 `.mjs`（不含 `node_modules`）共 107 个，`Agents/` 下 97 个。78 这个数字的口径是 `Agents/.claude` 74 个加 `Agents/skills` 4 个，**不含 `Agents/tests` 的 19 个测试文件**。

裁定 4.6 已经为 Skill 计数立过同一类规矩：两个数都对，指的不是一回事，所以不写单一数字。`.mjs` 计数需要同样处理，否则 `C1-W1-34` 的验收槽按 97 或 107 取数时必然判为不达标。

**建议**：该条改为「覆盖全部 78 个非测试 `.mjs`（`Agents/.claude` 74 + `Agents/skills` 4）」。原稿 4.12 已按「78 个非测试 `.mjs`」表述，口径正确。

### E-7 `G-10`、`G-11` 的处置与原稿表述需对齐

裁定 3.2 的覆盖核对写明：`G-01…G-19` 中 `G-10`、`G-11` 按架构方案 `D7`、`D8` 记入下一周期，其余 17 项均有承接 ID。

**建议**：以裁定 3.2 为准。工作槽核对缺口覆盖时，`G-10`、`G-11` 不计入周期 1 的承接范围。本条只影响 W5 核验槽的覆盖核对口径，不影响任何工作项的领取。
