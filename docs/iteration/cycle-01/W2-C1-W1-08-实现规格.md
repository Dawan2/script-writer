## 3. 设计裁定

### D1 续传契约补三样，游标仍是 `after_id` 那一个

沿用 B-05 的事件游标，不改事件存储、不改 `public_event`、不引入消息队列（领取表做法要点与架构方案 R2 已排除）。后端补三样：

| 帧 | 内容 | 带 `id:` |
| --- | --- | --- |
| 流开始 | `retry: 3000`，一次 | — |
| 事件 | `id: {事件 id}` + `event: agent-event` + `data: {事件 JSON}` | 是 |
| 保活 | `event: agent-heartbeat` + `data: {}` | **否** |
| 结束 | `event: agent-done` + `data: {"status": ...}` | **否** |
| 出错 | `event: agent-error` + `data: {"message": 中文话术}` | **否** |

只有事件帧带 `id:`，因为 `Last-Event-ID` 必须始终等于「已收到的最后一个真实事件 id」。保活、结束、出错三种帧不对应任何 `agent_events` 行，给它们发 `id:` 会污染游标。

### D2 保活用具名事件，不用注释帧

FM-09 记的是「不发注释心跳帧」。注释帧（`: keepalive`）能防中间层按空闲掐断，但**对 JS 完全不可见**——`EventSource` 不会为注释派发任何事件，客户端因此无法用它判活。本包改用具名事件 `agent-heartbeat`：同样是持续流量，同时给客户端一个可观测的活信号，一件事解决两个用途（勘误 E-08-4）。

- 间隔：**距上一次输出任何帧满 15 秒**就发一个心跳。
- 心跳不写入 `agent_events`，因此永远不会进活动列表，`16` 不需要为它写话术（§5）。

### D3 游标来源三档，优先级写死

后端取游标的顺序：

1. 请求头 `Last-Event-ID`，且能解析为非负整数；
2. 查询参数 `after_id`；
3. 都没有则为 0。

三档不是冗余，它们对应两条不同的重连路：**浏览器自动重连**只会带 `Last-Event-ID`，不会更新 URL 里的 `after_id`（F2），走第 1 档；**客户端自己重建**（D8）会把当前游标写进新 URL，走第 2 档。第 1 档压过第 2 档，F2 的重放就此消失。头非法（空串、非数字、负数）时**回落到第 2 档而不是报错**——重连是恢复路径，不能因为一个头解析失败就把流打掉。

### D4 代理层只做三件事，不自己造帧

| 做 | 怎么做 |
| --- | --- |
| 透传 `Last-Event-ID` | 路由自己从 `request.headers` 读出，经 `backendFetch(path, { headers })` 传下去。`backendFetch` 会把 `init.headers` 合并进最终请求头（`backend.ts:14`），**因此本包不改 `backend.ts` 一行**，也不动 03 定下的请求头白名单 |
| 声明不缓冲 | 响应头补 `cache-control: no-store, no-transform` 与 `x-accel-buffering: no`；`content-type` 固定 `text/event-stream; charset=utf-8` |
| 逐块直通 | 继续把 `response.body` 原样交出去，不 `await response.text()`、不重新分块、不套任何包装流 |

**代理层不得自行产生保活帧**（勘误 E-08-3）。后端卡死时，代理层的自造心跳会让界面一直显示连接正常，把一个可发现的故障变成一个不可发现的故障。领取表说的「代理层保活」由上表三件事兑现：不缓冲、不设总超时（03 的 D3 已落）、透传游标。

不设 `connection` 之类的逐跳请求头——那是运行时自己管的，在 `Response` 上写它没有作用。

### D5 后端轮询节流：静默期退档，状态查询只在无事件时做

F10 的 2 次/秒是固定的，与任务是否活跃无关。改为两条规则：

| 规则 | 内容 |
| --- | --- |
| 间隔按静默时长退档 | 静默 0–10 秒：1000 ms；10–30 秒：2000 ms；≥30 秒：3000 ms（上限）。**取到任何新事件立刻回到 1000 ms** |
| 状态查询按需 | 只有在本轮事件查询**没取到任何事件**时才查任务状态。有新事件时任务显然还在推进，终态最多晚一轮被发现 |

两条都落在一个纯函数 `next_poll_interval(idle_ms)` 与循环的一个分支上，判据是 AT-10 的表驱动用例。**延迟上限因此被定死为 3 秒**：事件写入到帧输出最坏晚 3 秒。领取表第 5 条要求「频率下降且不影响用户感知的及时性」——3 秒是本规格给「及时性」的具体口径，实现槽不得自行放宽到更大的档位。

### D6 客户端一个漏斗，去重靠单调游标

事件 id 在同一任务内严格递增（`list_events` 按 `id ASC`），因此**单调游标就是去重**：新增 `appendEvents(incoming)` 一个函数，丢掉 `id <= cursorRef.current` 的项，按 id 升序合并，再更新游标。

进展流、`agent-done` 的补拉、轮询降级三条来路全部经这一个漏斗。整合态有 2 处直接追加（`:927`、`:935`），改完后 `rg -c 'setEvents\(\(current\)' agent-panel.tsx` 必须为 0（AT-05）。整批替换的三处（`:908`、`:1074`、`:1235`）保留原样，但改为在替换的同时把游标重置为该批的最后一个 id。

### D7 连接状态四态，全部放在面板内，不经错误横幅

| 状态 | 界面说法 | 触发 |
| --- | --- | --- |
| 正常 | 不显示额外内容 | 45 秒内收到过任何帧（事件或心跳） |
| 重连中 | 连接已断开，正在重连 | `error` 事件，或 45 秒收不到任何帧 |
| 已降级 | 连接不稳定，正在改用较慢的方式获取进展 | 重连三次都没成功 |
| 需重新登录 | 登录状态已失效，请重新登录后查看进展 | 探测请求返回 `category === "auth"` |

呈现位置是工具条 `:1306-1309` 的 `agent-live-activity` 旁边，**新增一个独立元素**，不改 `runStatusText`（`:601-629`）一个字——那是 `07` 与 `16` 的内容（§5）。同时把 `:1307` 的状态点从「转轮」改为可区分的断开态，避免文字说断了、图标还在转。

**不经 `onError`**：工作台错误横幅 5 秒自动消失（F11），走它等于让第 3 条验收假通过。判据是 AT-06 里 `onError` 的调用次数为 0。

### D8 自愈重连三次，然后降级轮询

`EventSource` 在非 2xx 响应上永久关闭（F6），因此客户端必须有自己的重建逻辑，不能只依赖浏览器自动重连。

| 阶段 | 行为 |
| --- | --- |
| 判定失效 | 收到 `error` 且 `readyState === CLOSED`；或 45 秒（3 个心跳周期）没收到任何帧 |
| 重建 | 关掉旧流，按 1 s、3 s、9 s 三档间隔重建，URL 带当前游标 |
| 降级 | 三次都没成功则停止重建，改为每 15 秒调一次 `getAgentEvents(jobId, 游标)`；每 60 秒再试一次建流，成功即回到正常态 |
| 结束 | 任务转终态后停掉全部定时器与流 |

轮询间隔 15 秒 > 03 的读档预算 12 秒，保证上一次轮询到期后才发下一次，不会叠加在途请求（03 的 F4 就是被叠加咬到的）。同一时刻只允许一个轮询请求在途。

**全部状态放在 `useRef` 里，不进 effect 依赖**：进展流 effect 的依赖是 `[job?.id, job?.status, loadServerHistory]`，任务状态一变就会重建 effect，把重连计数放进 state 会被这次重建清零。

### D9 结算恰好一次

终态可以从三条路到达：`agent-done` 帧、轮询拿到的任务状态、重建后补拉的结果。三条都要触发同一批收尾动作（补齐事件、刷新文档、失败时报错、刷新额度、刷新历史），但**合计只能触发一次**。

做法：抽一个 `settleJob(job)`，用 `settledJobIdsRef` 按 jobId 记账，已记账的直接返回。判据是 AT-08 里 `onCompleted` 的调用次数恰好为 1。

这条兑现的是领取表第 4 条：断流期间任务已完成时，界面自己回到终态，用户不用手动刷新。F7 说明了为什么非做不可——进展流是同一次会话里唯一的活信道。

### D10 会话失效不叫「正在重连」

`EventSource` 的 `error` 事件不携带状态码，客户端无法区分「网络抖了一下」和「登录已失效」。做法：判定失效后先发一次探测请求 `getAgentEvents(jobId, 游标)`，它经 03 的请求核心返回类型化错误：

- `category === "auth"`：进入「需重新登录」态，**停止重连**，并让 03 的 `onAuthFailure` 广播照常生效（本包不实现就地重新登录，那是 `C1-W1-04`）。
- 其余：按 D8 继续重连。

探测成功时它本身就是一次有效的进展补齐，不浪费一次请求。

### D11 `agent-error` 帧改成用户话术，并补监听

F5 的英文 `{"message":"Job not found"}` 改为中文话术，客户端补 `agent-error` 监听器并把它显示为一次明确的终止（不是「正在重连」——任务已经不存在了，重连没有意义）。

**不新增错误码**：错误码注册表由 `02` 独占，且 SSE 帧不是 HTTP 错误信封，套一层码没有消费方。见勘误 E-08-6。

### 5.3 两处必须写清的交界

**交界一：「可能已停滞」和「连接已断开」是两个判断，不能互相顶替。**
`07` 的领取表第 3 条要求「超过预期时长且长时间无新事件时，提示仍在运行或可能已停滞」；本包 D7 要求「连接断开时提示正在重连」。前者判的是**任务侧**没有推进，后者判的是**连接侧**断了——同一时刻可以只成立一个，也可以两个都成立。两条文案必须分开，任何一包都不得用自己的提示盖掉另一包的。判据：本包的连接判定不读任何事件内容（只看帧是否到达），因此与 `07` 的判定天然独立。

**交界二：`agent-heartbeat` 不是活动条目。**
心跳帧不写入 `agent_events`，也不经 `appendEvents`，因此永远不会到达 `activityCandidate`。`16` 不需要为它写话术，也不得把它当成一类执行事件登记。

**交界三：`07` 与 `16` 在 `activityCandidate` 上撞车，本包不参与但要先说清。**
领取表给 `07` 的改动范围含 `agent-panel.tsx:310`，而裁定 5.5 把 `:309-346`（`activityCandidate` 整个函数）追加给了 `16`。队列是 `07` → `16`，因此 `07` 先动这一行、`16` 随后重写整个函数——两包须在 `:309-346` 上按行区间双方登记持有，否则 `16` 会把 `07` 刚加的分支覆盖掉。本包是队列首位，对该区间一行不动（勘误 E-08-10）。
