## 1. 目标与不变量

本周期 Agent 智能化只解决一个问题：**让"什么算做对了"这件事在系统里只有一个定义，
并且这个定义能被度量。** 生成质量的提升是结果，不是本周期的直接施工对象。

四条不变量，任何改动不得破坏：

| 编号 | 不变量 | 现状 |
| --- | --- | --- |
| I-1 | 一条验收规则只有一个定义处；其余位置只能引用，不得复述 | 未成立，A 类 6 项缺口 |
| I-2 | 任何进入执行策略的创作原则，其通过标准必须在完成时被留痕、在审稿时被核对 | 未成立（G-01） |
| I-3 | 阶段 SOP 归 Skill，运行编排归后端，两者不互相复述 | 已成立，`agent_runner.py:3365-3369` 明确此约定，须保持 |
| I-4 | 跨项目固定阈值只能作为缺省值，不得覆盖发行任务书里的显式约定 | 未成立（G-04） |

## 2. 目标架构：验收规则的单一来源

### 2.1 现状问题的本质

当前一条规则可能同时出现在四个地方：`SKILL.md` 的"内容额外要求"、
`references/*验收规则.md`、`check-*.mjs` 的判定分支、`foreign_review` 的维度检查项。
四处都能改，没有一处是权威，也没有任何检查发现它们不一致——这就是
`全稿验收规则.md` 变成孤儿文件、`预审` 变成死规则、`对抗性审稿原则` 适用范围自相矛盾的直接原因。

### 2.2 目标结构

每个创作阶段引入一份**阶段验收清单**，作为该阶段全部验收规则的唯一定义处。
清单里每条规则必须声明四个字段：

| 字段 | 含义 |
| --- | --- |
| 规则内容 | 一句话说清"什么算做对了" |
| 判定方式 | `机器判定`（由 check 工具执行）或 `语义判定`（由创作 Agent 自查并留痕、审稿核对） |
| 判定位置 | 机器判定写出 check 工具中的具体判定项；语义判定写出留痕字段与审稿核对点 |
| 来源 | `Skill 固定要求` 或 `知识库原则 <原则 ID>` |

三处引用关系随之固定为：

- **Skill 完成时**：`SKILL.md` 不再罗列验收规则，只引用清单，并说明"未通过时只修复命中项"。
  `check-*.mjs` 执行清单中所有 `机器判定` 项，并把清单中所有 `语义判定` 项连同
  Agent 的自查结论与证据定位一起写入 `quality_check`。
- **内容质量校验时**：阶段 `quality_check` 的通过判定 = 全部机器判定项通过 **且**
  全部语义判定项都有自查结论与证据定位（不判定结论正确性，只判定"是否真的查过"）。
- **AI 审稿时**：`foreign_review` 的维度检查项与清单中的语义判定项建立映射；
  审稿必须对每条语义判定项给出"复核一致 / 复核不一致 + 正文证据"，
  不一致项按现有 P0/P1 规则进入返修建议。

### 2.3 为什么不做自动语义判官

否决方案：再引入一个模型专门给每条 `review_criteria` 打分。理由有三：
一是成本与时延翻倍；二是判官本身不可回归，会把"不可度量"从一层推到两层；
三是本仓库已经有一个语义判官——`foreign_review`，正确做法是把原则接进它，而不是再造一个。

## 3. 裁决清单

### D1 阶段验收清单是唯一来源（对应 G-01、G-02、G-03、G-06）

创建阶段验收清单后，`SKILL.md` 中重复的"内容额外要求"删除并改为引用；
孤儿 reference 二选一：并入清单，或删除。禁止保留"没有引用关系的规则文件"。

### D2 创作原则的通过标准必须贯通三处（对应 G-01）

执行策略中每条原则的 `review_criteria` 自动进入当前阶段验收清单的 `语义判定` 项，
来源标注为该原则 ID 与版本。`check-*.mjs` 校验"每条通过标准都有自查结论与证据定位"，
缺失即不通过；`foreign_review` 按映射逐条复核。
**这条裁决是本周期的核心，其余裁决都是为它清障。**

### D3 审稿准入阈值改为任务书驱动（对应 G-04）

集数达标一项的判定基准改为发行任务书中的目标集数：
达到目标集数即通过，显著低于目标集数为部分通过或不通过。
只有任务书未提供目标集数时，才回退到当前的 30/10 缺省阈值，并在报告中说明这是缺省口径。
其余九项准入维持现状。

### D4 原则与公式的使用必须留痕（对应 G-07）

`get-strategy-formula.mjs` 每次读取写一条使用记录（任务、阶段、剧情单元或集号、
公式名称与版本）；执行策略生成时记录本次可用原则的 ID 与版本。
留痕落在项目运行目录下的运行台账中，与现有小说原文读取留痕同构。
效果度量（读过某公式的项目审稿分布）本周期只要求数据可查，不要求做出分析页面。

### D5 复盘闭环做最小接入，不做自动改 Skill（对应 G-08）

审稿阶段结束后自动运行 `agent-retrospective`，产出仅进入"待人工评审"队列。
明确否决：让复盘结果自动修改生产 Skill。系统进化仍必须经管理员审阅，
沿用 `system-agent-evolution` 现有的"只允许改 `.claude/skills/`、失败整树恢复"边界。

### D6 知识库依赖显式化并可回归（对应 G-09）

两条同时做：
一是知识库路径与"知识库不可用时的行为"写成显式契约——
不可用时执行策略明确产出"本次没有可用原则与公式"，而不是静默返回空;
二是为原则与公式链路提供入仓的测试夹具（建库脚本 + 少量固定原则与公式），
现有 4 个断言真实生产文案的用例改为断言夹具内容。
明确否决：把生产 `data/workbench.sqlite3` 纳入仓库或纳入测试依赖。

### D7 后台知识 Skill 按任务模式裁剪注入（对应 G-10）

`direct_skill_runner` 已支持 `exclude_references`，改为**白名单**：
每个后台 Skill 声明每种任务模式需要哪几份 reference，只注入这些。
明确否决：在无工具调用能力的后台链路里强推"渐进式按需读取"——
那需要给纯模型调用补一个检索通道，投入远大于收益，本周期不做。

### D8 兼容字段由工具生成，不进模型输出契约（对应 G-11）

`creative_decision`、`creative_problem`、`expected_effect` 三个"必须与另一字段完全一致"的
兼容字段改由校验/入库工具复制填充，从模型输出契约和 `SKILL.md` 的必填清单中移除。
`core_formula` 长度上限统一到一处并由校验器为准。

### D9 生产完整性检测按新契约重建，不恢复旧实现（对应 G-16）

跨集重复与近重复、正文密度坍缩、缺集这三类检测在 `check-full.mjs` 中重建，
判定项进入全稿阶段验收清单。
明确否决：恢复 `full-draft-tool.mjs`、Canon/Context Pack、大场景并发审读那套旧编排——
它依赖的共享库已整体不存在，恢复成本高于按当前契约重写，且会重新引入两套并行链路。
死代码分两步处置：先冻结（禁止新增引用、在入口标注不可达），
再按调用图分批删除，每批必须证明 `run_full_worker` 等仍在使用的函数未受影响。

### D10 契约一致性检查进入 `npm run check`（对应 G-19、G-13、G-12、G-15、G-18）

新增一项契约检查，至少覆盖：
`SKILL.md` 的链接与工具路径全部可解析；不存在未被引用的 reference；
每个阶段的输出文件名在 Skill 侧与后端侧一致；`CLAUDE.md` 的 Skill 清单与
`.claude/skills/` 实际目录一致；不存在无调用方的元数据文件。
同时把 `precheck` 串接进 `check`，并补齐 5 个漏掉语法检查的脚本。

### D11 质量契约版本恢复为真实指纹（对应 G-14、G-15）

删除 `memory_sync_service.py:161-162` 的常量短路，指纹文件清单按当前树重建
（去掉 10 个已不存在的文件，补上现行 `check-*.mjs` 与共享脚本），
`APPROVAL_PROTECTED_FILES` 同步到现行文件名。
改完之后，Skill 或校验器一变，历史批准即失效并要求按新契约重新校验——这是这条机制的本意。

### D12 阶段状态以产物为准（对应 G-17）

阶段被标为 `completed` 时必须存在其声明产物；
初始化工具遇到"状态已完成但产物缺失"时给出明确的用户可执行提示，
而不是抛出面向内部的 JSON 解析错误。

## 4. Skill / Agent 改动边界

任何改动先归类，再动手。

| 类别 | 范围 | 要求 |
| --- | --- | --- |
| 自由改 | reference 正文措辞、`SKILL.md` 的表达精简 | 不改文件名、不改引用关系、不改任何验收判定 |
| 必须三处同步 | 新增/修改/删除任何验收规则 | 同时更新阶段验收清单、`check-*.mjs` 判定项、`foreign_review` 映射；三处不一致视为未完成 |
| 需评审 | 删除 reference 或工具；改阶段输出文件名；改 `评分表.json5` 权重与阈值；改准入判定 | 需在工作项中说明影响面并给出回归证据 |
| 禁止 | 把具体项目的角色、台词、情节写成 few-shot；在 `SKILL.md` 里复述工具内部实现或文件格式；新增没有引用关系的规则文件；用扩写 reference 替代重构 | 违反 `docs/Agent设计规范.md` 与 `AGENTS.md` 原则 4 |

补充两条来自 `docs/Agent设计规范.md` 的硬要求，本周期所有工作项都适用：

- 结构化内容（JSON、表格）由工具先生成空框架并自动填充固定字段，模型只填内容；
- 工具返回值必须是确定性结论：失败说明原因与修复动作，成功说明下一步做什么，
  不返回需要模型二次判断的模糊信息。

## 5. 与兄弟槽位的边界

| 议题 | 归属 | 说明 |
| --- | --- | --- |
| 租约、任务恢复、事件游标、额度幂等、草稿保护、会话失效、离线感知 | 交互可靠性槽（`C1-IR-T01…T10`） | 本槽不涉及，不重复立项 |
| 界面文案、按钮可用性、URL 状态、通知与错误呈现 | 前端交互测绘（`T-01…T-09`） | 本槽只在"让用户看见本次生成依据"处新增能力，不改既有交互 |
| 服务端统一错误信封 | 交互可靠性 `C1-IR-T01` | 本槽的工具返回值要求与其兼容：Skill 工具的失败原因将成为该信封的一种输入 |
| 目录归属（`docs/iteration/cycle-01/` 与 `docs/wave-01/` 并存） | 总控槽 | 本槽产出统一放 `cycle-01` |

## 6. 本周期明确不做

| 编号 | 不做 | 理由 |
| --- | --- | --- |
| R1 | 再引入一个模型给创作原则打分 | 成本翻倍且判官不可回归；正确做法是把原则接进现有审稿 |
| R2 | 恢复 Canon / Context Pack / `full-draft-tool` 旧体系 | 依赖的共享库整体不存在，恢复成本高于重写，且会重新出现两套链路 |
| R3 | 把历史事故项目写进 Skill 作为示例 | 违反 `AGENTS.md` 原则 4；事故稿只用于检测器回归 |

| R5 | 给纯模型后台链路补检索通道 | 投入大于收益，先用白名单裁剪注入解决 |
| R6 | 一次性删除全部死代码 | 与在用函数交织，须按调用图分批并逐批举证 |
