## 3. 推荐修法

### 3.1 走真实生成路径，不要手写快照

夹具缺的是 `runtime/{阶段}/执行策略.md` 与 `execution-strategy.json` 两个文件。手写这份快照极脆：门禁要同时校验 `stage` 对应、`执行策略.md` 的 sha256 与快照的 `markdown_sha256` 一致、正文不含「成立原因」、`execution_spec_sha256` 与执行规范的 `markdown_sha256` 一致、`project_fingerprint` 与 `script_profile` 与输入一致、`knowledge_status` 取值合法、使用公式的阶段 `formulas_resolved` 为 `true`。任一项算错就换一条失败，而且以后门禁一改，手写快照就整片失效。

**正确做法是在夹具里调用真实的执行策略工具**，让它按当前门禁自己生成一份合规快照：

```
node .claude/skills/{stage}/scripts/get-execution-strategy.mjs --workspace <夹具工作区>
```

在 `init-full.mjs` 之后、`check-full.mjs` 之前插入这一步，并断言它返回 0。

### 3.2 这份代码已经存在，先取来验证，不要重写

`cursor/w1-failure-path-contract-mapping-058e` 在 `dd10033` 之后还有一个提交 `50f0ce4`，它给 `test_script_output_contracts.py` 加的 17 行正是 3.1 描述的写法：一个 `prepare_execution_strategy(stage)` 辅助方法，加两处调用点。

本槽实测：在整合态上**只取这 17 行**，`test_script_output_contracts.py` 8 项全过、`npm run test:api` 由 `454 项 2 失败` 变为 `Ran 454 tests / OK`，未新增失败项。

`36` 应当直接采用这段改动，把工作量放在验证、补齐和其余三条验收上，不要另写一版。

**`50f0ce4` 的另外两个文件一律不取：**

| 文件 | 为什么不取 |
| --- | --- |
| `Agents/.claude/skills/full_generate/SKILL.md` | 八阶段 `SKILL.md` 由 `C1-W1-29` 独占（裁定 8.2）。而且本槽实测在整合态上 cherry-pick `50f0ce4` 时，这个文件与 `01b9fb7` 冲突（`UU`），必须人工处置——那是 `29` 的活 |
| `docs/iteration/cycle-01/交互可靠性-失败路径实测与契约裂缝.md` | 失败路径测绘槽的产物，`36` 不持有 |

正确取法是只挑 `.py` 那个 hunk，不要整提交 cherry-pick。

### 3.3 顺带补上第二项的失败可读性

给整合态 `:276` 那个 `assertEqual` 补 `msg`（把 `check-full` 的 `stderr` 带出来），与第一项对齐。这是**增强诊断**，不是放宽判定：断言的期望值仍是 `returncode == 0`，一个字都没松。

## 6. 与上游文档的差异

按裁定 9.6「发现冲突先登记勘误再动手」登记。编号、归属、文件边界一律不动，动的只是修法依据与前置说明。

### 6.1 修法不是 `dd10033` 的白名单打开的

余量 3.2 写：「在不设 `ORCA_SCRIPT_KNOWLEDGE_DB_PATH`、也没有 `data/` 的隔离环境下，生成结果的 `knowledge_status` 是 `unavailable`，而该取值被 `dd10033` 新增的白名单接受……**这个修法是 `dd10033` 打开的**。」

实测三点，都与此不符：

1. 用夹具同款输入跑 `get-execution-strategy.mjs`，生成的 `knowledge_status` 是 **`skipped_unresolved_profile`**，不是 `unavailable`。原因是夹具的 `distribution_brief` 不含剧本标签，`unresolvedProfileFields` 非空，`writeStageExecutionStrategy` 在 `:600` 直接取这个初值，`:601` 的知识库查询整段都不执行。
2. 门禁侧同理：`stageExecutionStrategyIssues` 在 `:697` 就分流进 `unresolvedFields.length` 为真的分支，只校验「状态是 `skipped_unresolved_profile` 且原则公式为空」，`:701` 那条三值白名单在这条路径上压根不参与判定。
3. **把 `dd10033` 对 `stage-execution-spec.mjs` 的 27 行改动整体 revert 掉，再取 `50f0ce4` 的夹具改动，8 项仍然全过。** 修法与白名单无关。

**结论**：`dd10033` 对 `36` 的作用只有一项——补 `2.1-world-view.json` 夹具，解掉原 4 项里的 2 项。剩余 2 项走的是 `skipped_unresolved_profile` 这条 `dd10033` 之前就存在的路径。

这条差异是有后果的，不是措辞问题：它意味着 `36` 与 `stage-execution-spec.mjs` 之间**连间接依赖都没有**，5.2 的禁区因此可以按最严的口径执行——一行都不用改，也不必等 `31` 释放。
