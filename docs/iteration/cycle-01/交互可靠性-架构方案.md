## 1. 方案取向

现状基线（同目录文档 §1）显示：**服务端长任务可靠性已经成熟，缺口集中在用户编辑链路与请求链路**。因此本方案不是新建一套可靠性框架，而是：

- **升级两个已经存在的收口点**，不新增分层；
- **把已经存在但只服务单一场景的能力提升为通用契约**（错误分类、幂等收据）；
- **明确做减法**：本产品不需要的机制（乐观更新、CRDT 分块存储、多步向导会话、隐式自动重试）在本周期内不建，理由见 §4。

减法与加法同等重要。空仓期的设计文档按"通用 Web 产品"假设列出了完整机制表，其中若干项对本产品是净负担，如不显式作废，工作槽会照单实现。

## 2. 三条不变量

所有工作项都必须服务于这三条，且只服务于这三条。

### 不变量一：用户已输入的内容不会因为任何失败而消失

判定：从"用户敲下第一个字"到"服务端确认落盘"的整条链路上，任意一点失败（网络断开、会话过期、内容冲突、进程重启、误关页面），用户的修改都必须仍然可取回，且界面必须告诉用户它在哪。

推论：
- 编辑草稿必须落到本地持久化，键按"项目 + 阶段 + 基线内容摘要"划分；
- 任何失败提示都不允许把"刷新页面"作为唯一出路；
- 离开有未保存修改的文档（关闭、刷新、切换阶段、切换项目）必须先确认。

### 不变量二：每一次写入的结果都是可判定的

判定：一次写请求返回后，用户与系统都能明确知道它"生效了/没生效/与他人冲突了"，不存在"可能写了一半"。

推论：
- 写请求带前置条件（内容摘要）且**不可省略**；
- 落盘走原子替换，不允许目标文件出现中间态；
- 文件系统与数据库的双写有固定顺序与显式补偿，且事后可被自检发现分叉；
- 提交类写操作带幂等键，重试不产生第二个实体、不产生第二次计费。

### 不变量三：失败必须带类型，且每种类型有对应出路

判定：界面对失败的处理不再是"显示一段红字"，而是按类型给出用户能执行的下一步。

推论：
- 错误在跨层传递中保持结构（错误码、类别、是否可重试、面向用户的说明、追踪号）；
- 会话过期 → 原地重新登录并重放，不丢草稿；
- 内容冲突 → 提供保留/采用/对比三种选择；
- 离线 → 明示连接状态与"待发送"状态；
- 所有面向用户的文案从用户视角编写，不出现内部术语与英文。

## 3. 架构落点

### 3.1 收口点 A：前端请求核心（`apps/web/src/lib/`）

浏览器侧的网络出口已经事实上收拢在 `api-client.ts` 与 `admin-api.ts`（基线 B-12），业务组件零裸 `fetch`。方案是把这两处共用的裸 `fetch` + `parseJson` 升级为一个请求核心，而**不是**再叠一层客户端。

请求核心承担：

| 能力 | 说明 |
| --- | --- |
| 分级超时 | 按操作类型声明：读 8s、写 15s、上传按体积、进展流不设总超时 |
| 取消 | 组件卸载信号与超时信号合并，卸载后不回写状态 |
| 幂等键注入 | 提交类写操作携带客户端生成的幂等键，键在"用户意图产生"时生成，重试沿用 |
| 错误信封解析 | 解析服务端结构化错误，向上抛出带 `code / category / retryable / userMessage / traceId` 的错误对象，替代当前的 `Error(字符串)` |
| 会话拦截 | 收到会话失效时进入单飞续期/重新登录流程，成功后原样重放（幂等键不变） |
| 追踪号透传 | 每个用户意图生成追踪号，随请求下传并可在错误提示中复制 |

明确不承担：**隐式自动重试**。理由见 §4 对 D14 的修正。

### 3.2 收口点 B：服务端错误出口（`apps/api/app/`）

服务端已有完整的失败分类语义 `AgentExecutionError(code, category, retryable, user_message, root_cause, details)`（基线 B-06），但它只用于 Agent 任务落库；HTTP 层仍是 `HTTPException(detail=字符串)`。

方案是把这套语义提升为**全 API 的 HTTP 错误契约**：注册统一异常处理器，输出固定形状的错误体（错误码、类别、是否可重试、面向用户的说明、追踪号、可选明细）。`root_cause` 只进日志与审计，不出网。

这一步同时解决 FM-05（结构丢失）与 FM-12（英文术语外泄）：`user_message` 成为必填字段，意味着新增失败路径时"写一句用户看得懂的话"是硬要求，而不是可选项。

### 3.3 收口点 C：幂等收据（`apps/api/app/db/`）

幂等收据表 `(user_id, idempotency_key)` + 请求指纹 + 首次响应留存已经存在，但只被外部 OpenClaw API 使用（基线 B-09）。方案是把它提取为可复用的请求依赖，接入第一方的提交类写操作（优先级：新建项目、批量任务创建）。

不引入"客户端生成主键 + upsert"的替代路线：本仓库实体主键均为 SQLite 自增整数，改造面过大且收益重复。

### 3.4 分层示意

```
┌──────────────────────────────────────────────────────────────┐
│ 界面层  保存状态与连接状态指示 · 冲突三选一 · 原地重新登录      │

├──────────────────────────────────────────────────────────────┤
│ 草稿层  编辑草稿本地持久化（键=项目+阶段+基线摘要）· 脏态跟踪   │
├──────────────────────────────────────────────────────────────┤
│ 请求核心 分级超时 · 取消 · 幂等键 · 错误信封解析 · 会话单飞     │

├──────────────────────────────────────────────────────────────┤
│ 代理层  Next 路由处理器：逐跳超时（内层小于外层）· 追踪号透传   │
│         进展流保活                                            │
├──────────────────────────────────────────────────────────────┤
│ 服务端  统一错误信封 · 幂等收据依赖 · 前置条件必填 · 原子落盘   │
│         文件与数据库双写顺序与补偿 · 进展流心跳                │
├──────────────────────────────────────────────────────────────┤
```

### 3.5 关键设计裁决

**裁决 1：冲突以内容摘要为准，不引入版本号字段。**
现有 `expected_hash` 已能检测冲突，且阶段文档是 `Agents/workspaces` 下的真实 Markdown 文件、由 Web 与 Agent 技能脚本共同读写。引入独立 `version` 列会让"文件是事实源"这一前提破裂（外部脚本改文件不会递增版本号），而内容摘要天然对任何写入者成立。本周期只做"必填化 + 覆盖全部写接口"。

**裁决 2：冲突的默认动作是保留用户修改，而不是采用服务端版本。**
当前提示"请刷新后再保存"隐含了"放弃你的修改"这一默认值，方向是错的。正确默认值是：先把用户修改保住（草稿层已落盘），再让用户在保留/采用/对比之间选择。没有任何自动覆盖。

**裁决 3：不做隐式自动重试；重试必须由用户触发或由幂等保护兜底。**
写操作在本产品普遍带额度成本与 Agent 执行成本，隐式重试会放大计费风险和重复生成。方案是：失败带 `retryable` 标记 → 界面给出显式"重试"按钮 → 重试沿用原幂等键。只读请求可在请求核心内做有限次退避重试。

**裁决 4：长任务与页面生命周期解耦已经达成，保持现状。**
Agent 任务已是"提交即返回 + 事件游标 + 租约恢复"的异步模型（B-01…B-06），关闭页面不影响执行、重开可续读。本周期只补进展流的心跳与重连契约（FM-09），不改任务模型。

**裁决 5：文件系统是事实源，数据库是索引；补偿方向单一。**
双写不一致时以文件内容为准，数据库侧的版本历史与变更记录负责追上。这决定了补偿逻辑的方向（重建索引，而非回滚文件），也决定了自检工具的判定基准。
