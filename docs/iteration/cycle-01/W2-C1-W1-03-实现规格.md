## 3. 设计裁定

### D1 一个出口，不叠客户端

新增 `apps/web/src/lib/request-core.ts` 作为浏览器侧唯一的 `fetch` 出口，`api-client.ts` 与 `admin-api.ts` 的 126 个函数各自改为调用它。**不新增第二层封装、不引入请求库**（领取表做法要点：升级两个文件共用的裸 `fetch` + `parseJson`，不再叠一层客户端）。

调用方零改动：`ApiError` 继承 `Error`，F12 的 114 处兜底写法继续成立；本包不为了引入类型化错误去改 22 个组件文件。

### D2 三档预算 + 按接口登记的覆盖档

预算按操作类别分档，后端有分钟级子进程的接口按接口登记覆盖值。**每一行的三个数都写在同一张表里，不用公式推**，判据是 AT-01 的表驱动用例。

| 档 / 覆盖项 | 浏览器 | 代理层 | 后端实测上限 |
| --- | --- | --- | --- |
| 读（默认） | 12 s | 7 s | — |
| 写（默认） | 45 s | 40 s | — |
| 上传（默认） | 240 s | 235 s | 180 s（项目初始化子进程） |
| 阶段保存 `PUT /projects/{id}/files/{stage}` | 330 s | 325 s | 300 s（阶段校验） |
| 阶段审批 `POST /projects/{id}/stages/{stage}/approve` | 330 s | 325 s | 300 s |
| 重新初始化 `POST /projects/{id}/reinitialize` | 120 s | 115 s | 90 s（简报 60 + 语种 30） |
| 发行简报保存 `PUT /projects/{id}/distribution-brief` | 90 s | 85 s | 60 s |
| 剧本名同步 `PUT /projects/{id}/outline-title` | 90 s | 85 s | 60 s |
| 重新开启项目 `POST /projects/{id}/reopen` | 90 s | 85 s | 60 s（记忆状态工具） |
| **发行简报读取** `GET /projects/{id}/distribution-brief` | 45 s | 40 s | 30 s（语种契约，仅旧布局工作区） |
| **记忆状态读取** `GET /projects/{id}/memory` | 90 s | 85 s | 60 s（仅旧布局工作区） |
| 进展流 `GET /agent/jobs/{id}/stream` | 不设 | 不设 | — |

三条不变量，任一条不成立即 AT-01 失败：

1. **浏览器 > 代理层**：领取表验收第 3 条。代理层先到期，用户拿到的才是一个带追踪号的信封，而不是浏览器无声掐断。
2. **代理层 > 后端子进程上限**：否则正常的慢写入永远显示「等待太久已经中断」，用户看不到后端给出的真实原因。这一条决定了覆盖表必须存在——把阶段保存按写档的 45 秒发出去，等于把一次合法的 5 分钟阶段校验判成失败。
3. **读档 12 秒的依据是 F4**：卡住的读请求在途数从「无上限」降为 `12 ÷ 3 = 4` 个。本包不做同路径读请求合并——那会让「操作后立刻刷新」并进上一次轮询的在途请求，用户看到刚改过的数据没变。该项登记为 W3 收口，不在本包。

**表里两行读档覆盖是这次测绘新发现的**：`GET /projects/{id}/distribution-brief` 与 `GET /projects/{id}/memory` 在旧布局工作区上会各起一个 30 秒 / 60 秒的 node 子进程（`workspace_service.py:1119`、`projects.py:1079`）。按读档 12 秒发出去，这两个读接口在旧项目上会稳定超时。

**落表前必须先跑一遍清点**，把浏览器可直接触发的慢接口全部登记，漏一个就等于给用户造一个稳定失败：

```bash
rg -n 'subprocess\.run\(' -A 8 apps/api/app --glob '!tests' | rg 'timeout='
```

整合态实测：全仓 37 处 `subprocess.run`，26 处在调用点显式写了 `timeout=`。本槽已回溯出上表 8 个浏览器可达接口；剩余命中大多落在后台任务与 Agent 执行链上（不经本包的请求核心），但**管理台的两条要由实现槽自己确认是否同步执行**：Agent 进化执行（`system_agent_evolution_service.py:515`，90 s）与剧本库文档提取（`script_library_service.py:370/390/400`，120 s / 180 s，走上传档已覆盖）。清点输出进证据（§7 第 8 条）。

### D3 代理层预算的传递：一个请求头 + 一条换算

浏览器把本次预算写进请求头 `x-client-timeout-ms`，代理层按 **`代理层预算 = 浏览器预算 − 5000`，下限 5000** 换算。理由是 F7：58 个路由不转发浏览器请求头，只有 `backendFetch` 能拿到原始请求（`next/headers`），因此换算与透传都收在 `backend.ts` 一处，57 个路由零改动。

- 头缺失、非数字、≤ 0：按读档处理（7 s）。服务端组件调用 `backendFetch` 时不带头，走这一支。
- **「不设超时」只能由服务端代码显式传参**，不能由请求头声明。进展流路由是唯一一处（`stream/route.ts` 传入不设超时），因为 `EventSource` 发不出自定义头，也因为进展流本就不该有总超时。
- 这条换算把「覆盖档漏声明」的后果定死为**代理层在 7 秒把慢接口掐掉**。因此覆盖表的每一行必须在 `api-client.ts` 里有且只有一个声明点，判据见 AT-01 第三项。

### D4 取消：超时与卸载共用一条信号，但结果不同名

核心内部合并两个来源：本次预算的定时器与调用方传入的 `signal`。两者都通过 `AbortController` 中断同一个 `fetch`，但结束方式必须分开——否则卸载会在界面上留下一条「等待太久已经中断」的红字。

| 中断来源 | 抛出 | 是否给用户看 |
| --- | --- | --- |
| 预算到期 | `ApiError`，`code: "BACKEND_TIMEOUT"` | 是 |
| 调用方 `signal`（组件卸载、用户切走） | `RequestCancelledError`（`name: "RequestCancelled"`），**不是 `ApiError`，不带错误码** | 否 |

取消不占错误码：注册表里不新增 `REQUEST_CANCELLED`，因为它不是一次失败，用户也不需要看到任何提示。核心导出 `isRequestCancelled(error)` 供调用方判定。

新增 `apps/web/src/lib/use-request-scope.ts`：`useRequestScope()` 返回 `{ signal, run }`，`run` 在卸载后吞掉 `RequestCancelledError` 并且不回写。各热点文件的逐点接入由其持有槽完成（§9），本包只交付钩子与用例。

### D5 只读退避：两次，写操作零次

| 项 | 值 |
| --- | --- |
| 适用范围 | 只有读请求（`GET`） |
| 触发条件 | 只有两种：一次响应都没拿到（网络失败），或网关级 502 / 503 / 504 |
| 不触发 | 429 限流（重试只会加重限流，按 `retryable` 与 `hint` 交给调用方提示用户）；4xx；已经拿到信封的 5xx |
| 间隔 | 500 ms、1500 ms 两档常量，不写公式，用例逐档断言 |
| 预算关系 | 全部尝试共享同一个截止时间。预算耗尽即停，**超时之后不再重试** |
| 写操作 | 上传、`POST`、`PUT`、`PATCH`、`DELETE` 在任何情况下都不被核心自动重发，**带幂等键也不重发**——键是给调用方发起的显式重试用的（`C1-W1-09`），不是给核心自动重发用的 |

写操作零重发是本包的硬约束：本产品的写操作普遍带额度与生成成本，一次静默重发等于一次重复扣费。

### D6 传输层失败合成信封，文案不另写一份

`fetch` 抛错或预算到期时，浏览器侧没有响应体可解析，本包按 02 规格 §9.3 合成信封：

| 场景 | `code` | `category` | `retryable` |
| --- | --- | --- | --- |
| 一次响应都没拿到（断网、DNS 失败、连接被重置、代理层空体 500） | `BACKEND_UNREACHABLE` | `runtime` | `true` |
| 预算到期 | `BACKEND_TIMEOUT` | `runtime` | `true` |

文案不新写：`message` 与 `hint` 逐字取 `error_codes.json` 的 `client_codes`，与 02 已在 `api-error.ts` 写下 `RESPONSE_UNREADABLE` 那一条同一批措辞、同一个位置。**注册表是唯一事实源**，`api-error.ts` 是镜像，由 AT-11 的用例逐字对比防漂移。注册表生成器只生成码名不生成文案，改由生成器一并产出属 W3（勘误 E-03-6），本包不动 02 的生成器。

### D7 追踪号：浏览器生成，全链沿用，代理层合成时加前缀

服务端中间件已经会沿用请求头里的 `x-request-id`（`main.py:62`）。据此定：

1. 浏览器为每个请求生成一个号，写进 `x-request-id`；
2. 代理层把该头透传给后端（D3 的同一处白名单）；
3. 代理层把后端响应的 `x-request-id` **复制回浏览器**（补 F5）；
4. 代理层自己合成信封时，`traceId` 写成 `web-` + 原号（没有原号则新生成）。

`web-` 前缀的口径要写进客服说明：**带前缀表示这次请求没有拿到后端响应，去后端日志查时去掉前缀**。02 规格 §9.3 要求「前缀可区分」但未给取值，本槽定为 `web-`（勘误 E-03-5）。

### D8 批量操作按项呈现

`runBulk` 改三件事，一件不做则 AT-07 不成立：

1. `delete` 分支从 `Promise.all` 改为 `Promise.allSettled`，一项失败不吞掉其余项的结果；
2. 失败按项展示（每项一行，含任务名与原因），不再 `join("；")`；
3. 结果表述按实际计数：成功 n 项、失败 m 项，**成功项不因为存在失败项而被表述为失败**，也不再在有失败时仍弹出一句无条件的「已暂停所选任务」。

逐项失败当前只有文案没有错误码（`batch_tasks.py:153` 回填的是 `str(exc.detail)`），本包按文案展示，不做按码分支；补码要改 `batch_tasks.py`，那是 `C1-W1-09` 的持有文件。

### D9 删掉反解，改读 `details.issues`

`saveErrorMessage` 的整段反解删除，改为：`details.issues` 有内容就按项列出，没有就展示信封 `message` 全文（不截断、不做任何字符串匹配）。

旧版工作区布局仍有一条没结构化的分支（`memory_sync_service.py:1057`、`:1066` 把子进程输出拼进句子），本包不改后端；那条分支拼的是 `warnings` 与 `next_action`，删掉反解不会让信息消失，但它值得登记为余量（勘误 E-03-7）。

### D10 `AgentJob` 补三个可选字段

`lib/types.ts` 的 `AgentJob` 增加 `error_code?: string`、`error_category?: string`、`error_retryable?: boolean`（F11）。**只加类型，不改任何消费方**——Agent 失败怎么说给用户听归 `C1-W1-16` 与 `C1-W1-42`。
