## 2. 故障模式清单

严重度定义：
- **严重**：会造成用户已产出内容不可恢复地丢失，或产生重复计费/重复实体。
- **高**：用户被卡死在无出路的状态，或数据可能处于不一致但未被发现。
- **中**：用户需要额外操作或自行猜测才能继续，体验受损但数据可挽回。
- **低**：资源浪费或可观测性缺失，用户可感知度低。

### FM-01 编辑草稿只存在于内存，冲突后按提示刷新即丢稿 · 严重

用户在编辑器里的修改保存在 React state（`draft`），没有任何本地持久化。当保存遇到内容已变（例如 Agent 任务刚写过同一文件），服务端返回的唯一指引是"请刷新后再保存"——而刷新恰好会丢弃全部未保存修改。

- 证据：本地持久化仅用于面板宽度与 Agent 对话记录，编辑草稿无落盘（`apps/web/src/app/workspace/page.tsx:1142`、`:2105`；`components/workspace/agent-panel.tsx:434`；全仓 `localStorage|indexedDB` 无编辑草稿命中）
- 证据：`workspace_service.py:3437` 冲突文案为"文档已被其他操作更新，请刷新后再保存，避免覆盖较新的内容"
- 触发路径：编辑长文档 → Agent 任务完成写回同一阶段文件 → 保存 → 409 → 按提示刷新 → 修改全部消失

### FM-02 无离开保护，关闭页面或切换阶段静默丢弃未保存修改 · 严重

全仓没有 `beforeunload` 或路由离开确认；切换阶段的加载函数直接用服务端内容覆盖 `draft`，不检查脏状态。

- 证据：`rg beforeunload apps/web/src` 零命中
- 证据：`apps/web/src/app/workspace/page.tsx:1444-1445` 直接 `setDocument` / `setDraft` 覆盖当前草稿
- 触发路径：编辑中误点其他阶段、关闭标签页、误刷新，均无任何提示

### FM-03 新建项目无幂等键，超时重试产生重复项目与重复额度预留 · 严重

`POST /projects` 无请求去重，客户端唯一防线是按钮 `busy` 置灰——它挡不住"请求已到达服务端但响应丢失"的场景。审稿/翻译/润色类项目在创建时即校验并预留额度，重复创建等于重复消耗。

- 证据：`apps/api/app/routers/projects.py:272-325` 无幂等键、无去重查询
- 证据：`:292-302` 创建即 `ensure_concurrent_job_capacity` + `ensure_sufficient_credits`
- 证据：客户端仅靠 `disabled={!canSubmit}`（`components/workspace/new-project-form.tsx:420`）
- 反差：幂等收据表已存在（B-09），但只服务外部 OpenClaw API，第一方 Web 路径未复用

### FM-04 全链路无超时与取消，接口卡住即按钮永久"处理中" · 高

浏览器侧与 Next 代理侧都没有超时或取消信号。`AbortController` 在整个 web 应用中只出现在 zdebug 转发路由。长任务提交、文件上传、文档保存一旦上游无响应，界面停在"处理中"且没有任何退出方式。

- 证据：`rg 'AbortController|AbortSignal' apps/web/src` 仅 1 处（`app/zdebug/[port]/[[...path]]/route.ts`）
- 证据：`apps/web/src/lib/server/backend.ts` 的 `backendFetch` 无 `signal`、无超时
- 证据：`api-client.ts` 全部 65 处 `fetch` 均未传 `signal`
- 附带影响：组件卸载后在途请求仍会回写状态

### FM-05 错误信封在跨层传递中降级为字符串，前端被迫从文案里反解结构 · 高

服务端用 `HTTPException(detail=...)`，前端 `parseJson` 把它拍成 `new Error(字符串)`。结构化信息（错误码、类别、是否可重试）在这一步全部丢失，以致于业务代码需要在错误**文案里找 `{`、截子串、再 `JSON.parse`** 才能拿回校验明细。

- 证据：`apps/web/src/lib/api-client.ts:40-73` 错误统一退化为 `Error(message)`
- 证据：`apps/web/src/app/workspace/page.tsx:193-208` 从 `error.message` 里 `indexOf("{")` + `JSON.parse` 反解 `issues`
- 直接后果：401（会话过期）、409（内容冲突）、422（校验失败）在界面上是同一种"红字提示"，无法各自给出正确出路
- 反差：服务端已有完整分类语义（B-06），但仅用于 Agent 任务落库，未提升为 HTTP 错误契约

### FM-06 会话过期无恢复路径，编辑中过期即丢稿 · 高

访问令牌 7 天硬过期，没有续期机制；前端没有 401 拦截、没有内嵌重新登录层。过期后所有写请求失败，用户看到的是 FM-05 的通用红字，唯一自救方式是重新登录——这会重载页面并触发 FM-01/FM-02 的丢稿。

- 证据：`apps/api/app/core/config.py:15` `access_token_expire_minutes = 60 * 24 * 7`
- 证据：`apps/api/app/core/security.py:72` 过期即判失效，无 refresh token 相关实现
- 证据：`api-client.ts` 无 401 分支、无重放队列

### FM-07 文档主写入路径非原子，进程中断可留下截断文档 · 高

同一文件里已有 `_atomic_write_text`（临时文件 + `replace`），但阶段文档的主保存路径与其回滚路径都用裸 `write_text` 直写目标文件。写入中途进程被中断（API 重启、OOM、部署）会留下半截文档。

- 证据：`workspace_service.py:3445` `file_path.write_text(content, encoding="utf-8")`
- 证据：`:3458-3459` 回滚路径同样直写
- 证据：原子写工具就在同文件 `:537-543`，并已用于 `:454`、`:924-925`、`:3714-3715`
- 加重因素：README 明确说明 `npm run dev:watch` 会重启 API 并中断在途 Agent 子任务，即"写入期间进程消失"是常规操作而非极端场景

### FM-08 文件系统与 SQLite 双写没有统一提交点 · 高

保存文档的顺序是：写文件 → 记录版本 → 写变更表 → 写审计 → 由依赖统一 commit。文件系统的改动无法参与 SQLite 事务，中途任何失败都会让"实际文件内容"与"版本历史"分叉，且分叉不会被任何检查发现。

- 证据：`workspace_service.py:3445`（写文件）→ `:3462-3473`（`record_file_version`）→ `:3474-3491`（`artifact_changes`）
- 证据：`:3457-3460` 的补偿只覆盖"阶段状态更新失败"这一种异常，且补偿动作本身非原子（FM-07）
- 用户可见后果：版本历史里缺少某一次保存，"恢复到上一版本"会恢复到错误的内容

### FM-09 进展流无心跳与重连契约 · 中

SSE 端点每秒轮询数据库推事件，但不发送 `id:`、不发送 `retry:`、不发注释心跳帧。浏览器原生的 `Last-Event-ID` 续传因此不可用；连接被中间代理静默掐断时，客户端只能依赖 `onerror` 回退到一次性轮询，界面上的进展会停住而不报错。

- 证据：`apps/api/app/routers/agent.py:331-352` 仅输出 `event:` 与 `data:` 两行，终态才结束流
- 证据：`apps/web/src/components/workspace/agent-panel.tsx:922-936` 客户端自行维护 `lastEventIdRef`，`onerror` 时补一次 `getAgentEvents`
- 证据：Next 代理层直通 `response.body`（`app/api/agent/jobs/[jobId]/stream/route.ts`），不做保活

### FM-10 检测到冲突却没有可用出路 · 中

服务端具备冲突检测能力（B-07），但前端不存在任何冲突处理界面：没有"保留我的修改 / 采用服务器版本 / 并排对比"，唯一指引是刷新。检测到的冲突因此等价于"让用户自己承担损失"。

- 证据：`rg '409' apps/web/src` 在业务代码中零处按状态码分支（唯一命中是导出路由自己返回 409）
- 关联：与 FM-01、FM-05 叠加后构成完整的丢稿链路

### FM-11 写入前置条件可选且覆盖不全 · 中

`expected_hash` 在多个写接口上是可选参数，缺省即无条件覆盖。是否传值由每个调用点自行决定，缺乏统一约束。

- 证据：`api-client.ts:373` `saveFile(..., expectedHash?: string)`、`:484` `approveStage(..., expectedHash?)`、`:191` `archiveProject(..., expectedHash?)`
- 证据：`apps/api/app/routers/projects.py:101/140/145/168` 多个模型中 `expected_hash: Optional[str] = None`
- 对比：`:128/132/184` 已有强制 64 位摘要的写接口，说明"必填"在本仓库是可达标准

### FM-12 技术性英文报错直接展示给终端用户 · 中

多条面向用户的失败路径返回内部术语或英文，违背仓库规范"界面内容必须从用户视角编写"。

- 证据：`agent_runner.py:2091`、`:2182` `Project already has running job #{id}`
- 证据：`agent_runner.py:2076` `Unsupported stage`、`:2084-2086` `Unsupported stage for review task` 等
- 证据：`workspace_service.py:3421` `Unknown stage`、`:3431` `Stage file not found`
- 传导链：这些 `detail` 经 FM-05 的字符串通道原样落到界面红字上

### FM-13 无离线感知与写入重放 · 中

断网时保存表现为一次普通失败，之后不再尝试；界面没有连接状态指示，也没有"未保存·离线"这一状态。用户可能在断网状态下持续编辑很久而毫不知情。

- 证据：`rg 'navigator.onLine' apps/web/src` 零命中；无本地写入队列
- 证据：编辑器状态只有"已保存 / 保存中 / 有未保存修改"三种（`components/workspace/markdown-workspace.tsx:1574-1575`、`:1744-1745`），无离线态与失败态

### FM-14 多标签页与多设备之间无协调 · 中

同一用户在两处打开同一文档时，双方都不知道对方存在。没有 `BroadcastChannel`、没有"该文档正在别处编辑"的提示；两侧靠内容摘要相互竞争，后保存的一方落入 FM-10。登出、切换账号也不会在标签页之间同步。

- 证据：`rg 'BroadcastChannel|navigator.locks' apps/web/src` 零命中

### FM-15 前端可靠性无法回归 · 中

`apps/web` 只有类型检查，没有测试运行器、没有测试文件、没有端到端框架。这意味着 FM-01…FM-14 中所有客户端侧的修复都无法被自动化验证，改好之后也没有防回归的手段。

- 证据：`apps/web/package.json` 的 `scripts` 只有 `dev / build / start / check`，`devDependencies` 无任何测试依赖
- 证据：`find apps/web -name '*.test.*' -o -name '*.spec.*'` 零命中
- 对照：服务端已有 39 个测试文件与 `npm run test:api`，具备可复用的证据基线

### FM-16 轮询无可见性门控与失败退避 · 低

工作台同时挂着多个固定周期的刷新定时器，标签页隐藏时照常运行，请求失败也不退避。

- 证据：`apps/web/src/app/workspace/page.tsx:1162`（30s）、`:1181`（4s）、`:1288`（3s）、`:1318`
- 后果：无用请求持续消耗后端；后端不可用期间以固定频率重试，放大故障

## 3. 严重度汇总

| 严重度 | 编号 | 共同主题 |
| --- | --- | --- |
| 严重 | FM-01、FM-02、FM-03 | 用户产出会丢；重复提交会产生重复实体与重复计费 |
| 高 | FM-04、FM-05、FM-06、FM-07、FM-08 | 请求链路无边界、失败无类型、写入无原子性 |
| 中 | FM-09、FM-10、FM-11、FM-12、FM-13、FM-14、FM-15 | 失败后无出路、状态不可见、修复不可回归 |
| 低 | FM-16 | 资源浪费与故障放大 |

三个"严重"项互相咬合：内容只在内存（FM-01）+ 离开无保护（FM-02）+ 失败即需重来（FM-03），构成本产品当前最短的丢稿路径。架构方案因此把"不丢稿"列为第一不变量。
