## 1. 问题事实（逐条对应代码位置，非推断）

| 编号 | 事实 | 位置 | 后果 |
| --- | --- | --- | --- |
| F1 | 请求级事务的提交点在处理函数正常返回之后；异常时跳过 `commit()` 直接 `close()`，数据库回滚 | `apps/api/app/db/session.py:18-24` | 文件已落盘、数据库回滚 → 磁盘内容新、版本/变更/审计记录旧 |
| F2 | `write_stage_file` 先写文件（`:3445`），随后的 `record_file_version`、`artifact_changes` 插入、`UPDATE projects`、`record_audit` 全部无 SAVEPOINT 保护 | `workspace_service.py:3445`、`:3462-3511` | F1 在文档保存主路径上必然发生 |
| F3 | `write_stage_file` 的补偿回滚只覆盖 `mark_semantic_edit_in_progress` 一步，其后的数据库段完全无补偿 | `workspace_service.py:3446-3460` | 补偿窗口小于真实失败窗口 |
| F4 | `write_structured_stage_file`（world_view / novel_analysis 入口）结构同 F2，补偿窗口覆盖 mark / validation / memory sync 三步，但其后数据库段（`:3307-3360`）同样无 SAVEPOINT | `workspace_service.py:3277-3303`、`:3307-3360` | 同 F2 |
| F5 | 存在原子写辅助函数 `_atomic_write_text`，但仅用于 progress / user_input 少数写入点；阶段正文写入使用裸 `Path.write_text` | 辅助：`workspace_service.py:537-543`；裸写：`:2756`、`:3277`、`:3445` | 进程在写入中途终止会留下截断的正文文件 |
| F6 | `_atomic_write_text` 无 fsync（既不同步文件也不同步目录） | `workspace_service.py:537-543` | 掉电后可能得到空文件或短文件，`replace` 的原子性不覆盖持久化 |
| F7 | 补偿回滚自身可能失败：`except` 分支内再次 `write_text`，若这一步抛异常，原始异常被替换，且现场停在"半回滚"状态，无任何记录 | `workspace_service.py:2815-2816`、`:3296-3300`、`:3458-3459` | 故障不可诊断，用户看到的原因与真实原因不一致 |
| F8 | 唯一正例：`restore_file_version` 使用 `SAVEPOINT` + `ROLLBACK TO SAVEPOINT` + `RELEASE`，数据库侧一致性成立（文件侧仍靠补偿） | `workspace_service.py:2754`、`:2817-2820` | 可直接作为统一范式模板 |

结论：一致性缺口不是零散 bug，而是"文件先写、数据库后写、二者不在同一失败域"这一统一写序造成的。修法应统一写序，而不是逐点加补偿。

## 2. 可靠性方案（`C1-IR-T06`）

统一原则：**先库后文件、单点原子落盘、失败必留痕。**

| 编号 | 规则 | 说明 |
| --- | --- | --- |
| R1 | 统一写序 | 所有"文件 + 数据库"复合写入必须按顺序执行：① 进入 SAVEPOINT；② 完成全部数据库写入；③ 最后一步做原子文件落盘；④ RELEASE。落盘失败则 ROLLBACK TO SAVEPOINT，此时磁盘尚未改变，无需补偿动作。 |
| R2 | 原子落盘唯一入口 | 将 `_atomic_write_text` 加固为：同目录临时文件 → 写入 → fsync 文件 → 原子替换 → fsync 目录。加固后它是阶段正文落盘的唯一入口，签名不变。 |
| R3 | 提交点不下移 | 请求级 `commit()` 仍归 `get_db`，服务层不得自行 commit。复合写入靠自身 SAVEPOINT 自洽，不依赖请求是否最终提交。 |
| R4 | 补偿只作兜底且必须留痕 | 仅当业务上确实无法做到"库先文件后"时才允许保留补偿回滚；此时补偿失败必须写一条 `severity='error'` 的审计记录，并以 `raise ... from` 保留原始异常。 |
| R5 | 返回体自证 | 成功响应中的内容与哈希继续经 `read_stage_file` 重新读盘产生，不得改为回显入参。 |

方案不引入新组件：不加进程外锁、不换存储引擎、不加重试队列。

## 7. 禁止事项

1. 禁止用"失败后自动重试写入"替代一致性修复。
2. 禁止吞异常，禁止空 `except`，禁止用异常替换丢掉原始原因。
3. 禁止在服务层写 `conn.commit()`（提交点归 `get_db`）。
4. 禁止改动接口路径、方法、字段名、状态码。
5. 禁止更换存储引擎、引入新第三方依赖、引入进程外锁服务或消息队列。
6. 禁止在用户可见提示中出现函数名、表名、SQL、异常类名、文件绝对路径。
7. 禁止顺手重构 §3.2 列出的任何写入路径。
8. 禁止改动 `routers/projects.py` 与 `db/session.py`（互斥让位）。
9. 禁止自行新编 `FM-` / `IR-` / 事项编号。
10. 禁止把范围扩大为"全仓库写入原子化"。

## 9. 失败路径：导出因审计失败整包丢弃（`FM-23`）

**状态**：总控未立项。本事项不新编号、不改代码，仅在此登记二值建议。

| 问题 | 二值结论 | 一句理由 |
| --- | --- | --- |
| 是否交总控立项处理 | 是 | 审计是旁路记录，其失败不应吞掉用户已可获得的交付物，且影响面在导出主路径上。 |
