结论：一致性缺口不是零散 bug，而是"文件先写、数据库后写、二者不在同一失败域"这一统一写序造成的。修法应统一写序，而不是逐点加补偿。

## 2. 可靠性方案（`C1-IR-T06`）

统一原则：**先库后文件、单点原子落盘、失败必留痕。**

| 编号 | 规则 | 说明 |
| --- | --- | --- |
| R1 | 统一写序 | 所有"文件 + 数据库"复合写入必须按顺序执行：① 进入 SAVEPOINT；② 完成全部数据库写入；③ 最后一步做原子文件落盘；④ RELEASE。落盘失败则 ROLLBACK TO SAVEPOINT，此时磁盘尚未改变，无需补偿动作。 |
| R2 | 原子落盘唯一入口 | 将 `_atomic_write_text` 加固为：同目录临时文件 → 写入 → fsync 文件 → 原子替换 → fsync 目录。加固后它是阶段正文落盘的唯一入口，签名不变。 |
| R3 | 提交点不下移 | 请求级 `commit()` 仍归 `get_db`，服务层不得自行 commit。复合写入靠自身 SAVEPOINT 自洽，不依赖请求是否最终提交。 |
| R4 | 补偿只作兜底且必须留痕 | 仅当业务上确实无法做到"库先文件后"时才允许保留补偿回滚；此时补偿失败必须写一条 `severity='error'` 的审计记录，并以 `raise ... from` 保留原始异常。 |
| R5 | 返回体自证 | 成功响应中的内容与哈希继续经 `read_stage_file` 重新读盘产生，不得改为回显入参。 |
| R6 | 多文件写入的残余不原子性 | 一次保存要动两个文件（阶段正文 + `progress`，后者经 `mark_semantic_edit_in_progress` 写），两个文件无法一次原子替换。规则：`progress` 先落盘（失败即中止，正文未变），正文后落盘（失败则按 R4 复原 `progress` 并留痕）。残余风险窗口因此只剩"`progress` 已更新、正文未更新"一个方向，且该方向可由 `progress` 中已有的 `previous_hash` / `source_hash` 与正文实际哈希比对自检出来，不会产生正文损坏。 |

方案不引入新组件：不加进程外锁、不换存储引擎、不加重试队列。R6 是本方案承认的残余项，不试图用分布式事务或双写日志消除它。

## 7. 禁止事项

1. 禁止用"失败后自动重试写入"替代一致性修复。
2. 禁止吞异常，禁止空 `except`，禁止用异常替换丢掉原始原因。
3. 禁止在服务层写 `conn.commit()`（提交点归 `get_db`）。
4. 禁止改动接口路径、方法、字段名、状态码。
5. 禁止更换存储引擎、引入新第三方依赖、引入进程外锁服务或消息队列。
6. 禁止在用户可见提示中出现函数名、表名、SQL、异常类名、文件绝对路径。
7. 禁止顺手重构 §3.2 列出的任何写入路径。
8. 禁止改动 `routers/projects.py` 与 `db/session.py`（互斥让位）。
9. 禁止改动 M6 的四行英文抛错（`:2711`、`:2733`、`:3421`、`:3431`），它们归 `C1-W1-02`。
10. 禁止自行新编 `FM-` / `IR-` / 事项编号，包括不为 FM-23 造承接编号。
11. 禁止把范围扩大为"全仓库写入原子化"。
