### 0.3 本规格的边界

本规格只回答一件事：**一个跑 15–90 分钟的生成任务，界面上要用哪些数字让用户判断「到哪了、还要多久、是否卡住」**。不回答：每条事件该显示哪句步骤名（`C1-W1-16`）、连接断了怎么续（`C1-W1-08`）、打开文档时的加载分级（`C1-W1-05`）、失败原因怎么改写（`C1-W1-42`）、提示条与横幅长什么样（`C1-W1-06`）、跨项目的进度汇总（`C1-W1-20`）。逐项边界见 §9。

## 3. 设计裁定

### D1 一个进度模型，两个模块

新增两个文件，都在 `lib/`，不放组件内部——`agent-panel.tsx` 已 1584 行且是四槽争抢的热点：

| 文件 | 职责 |
| --- | --- |
| `apps/web/src/lib/agent-progress.ts` | **纯函数**。从 `job` + `events` + `history` 算出一个进度快照；含时长换算、剩余外推、兜底校准、停滞判定。零 React 依赖，可单测 |
| `apps/web/src/lib/agent-progress-store.ts` | **跨组件读取通道**。面板发布快照，等待界面订阅（React 19 的 `useSyncExternalStore`，服务端快照返回 `null` 以保证首屏与客户端一致）。带 `projectId` + `jobId`，终态或切项目即清 |

快照形状（`AgentProgressSnapshot`）：

```ts
{
  projectId: number;
  jobId: number;
  stage: string;
  stepTitle: string;            // 来自 16 的 agentEventCopy()，本模块不生产
  completed: number | null;     // 无结构化进度时为 null
  total: number | null;
  unit: "集" | "部分" | null;
  elapsedMinutes: number;       // 由 started_at 起算，parseDateTime 归一
  remainingMinutes: number | null;
  estimateSource: "measured" | "history" | "static";
  state: "queued" | "running" | "overrun" | "stalled" | "settled";
}
```

**为什么要 store 而不是传 props**：三处等待界面的 props 全部由 `page.tsx` 提供，而 `page.tsx` 的持有队列是 `17` → `05` → `01` → `03` → `06` → `12` → 其余，本项排不进去；三个宿主组件（`novel-analysis-workspace.tsx`、`world-view-workspace.tsx`、`markdown-workspace.tsx`）也各有持有者。发布/订阅让本项在**不改 `page.tsx`、不改三个宿主组件、不改 `page-loading.tsx`、不改任何 CSS** 的前提下把进度送到三处界面（判据 AT-13）。

### D2 进度只由结构化字段驱动，绝不从文案抓数字

两种读取来源，按优先级：

1. `raw_json.progress` = `{ unit: "episode" | "block", completed: number, total: number }`——**新契约**，后端此后新增进度字段一律用它（批次 B 的 6 处按此写）。`unit` 到界面的映射：`episode` → 「集」，`block` → 「部分」。
2. `raw_json` 顶层的 `completed` + `total`——小说解读既有 5 类沿用，单位固定为「部分」（与后端消息「共 38 部分」同词）。

`part`、`level`、`card_count`、`review_chunk`、`issue_count` 一概不进分数：它们是序号或计数，不是「已完成/总量」。

**不解析 `event.message`。** 一个字符都不解析。理由与 `16` 的 D4 同源：一旦从文案抓数字，后端改一个字前端的数字就错，而错的数字比没有数字更糟。判据是 AT-01（进度模块内零 `message` 引用）。

因此 `agent-panel.tsx:15-28` 的事件类型集合在本项落地后不再决定任何事——进度看字段，步骤名看 `16` 的表——**由本项删除**（含幽灵项 `novel_reading_repair`，F5）。

### D3 已用时长：从 `started_at` 起算，一律走 `parseDateTime()`

- 排队中（`started_at` 为空）不显示已用时长，沿用既有话术「等待执行资源」。
- 时间字段是 SQLite 无时区 UTC 文本（F11），**禁止 `new Date(job.started_at)`**，一律 `parseDateTime()`。判据 AT-05 用东八区时区跑一次。
- 显示粒度到分钟；不足 1 分钟显示「已用不到 1 分钟」，不显示 0 分钟，不显示秒。
- 只挂一个运行期计时器（30 秒一跳，够分钟粒度），终态与卸载即清，**不发任何请求**（判据 AT-14）。轮询门控归 `C1-W1-12`，本项不新增轮询。

### D4 预计剩余：按本次任务的实际速度外推，静态估时只兜底

| 条件 | 剩余算法 | `estimateSource` |
| --- | --- | --- |
| 有分数且 `completed ≥ 1` | 单位耗时 = 已用 ÷ `completed`；剩余 = 单位耗时 ×（`total` − `completed`），向上取整到分钟，下限 1 分钟 | `measured` |
| 无分数或 `completed = 0`，且同项目同阶段有 **≥ 3 条**已完成任务 | 取这些任务实际耗时（`finished_at` − `started_at`）的中位数，减去已用 | `history` |
| 其余 | 取 `agent-loading-estimates.json` 的静态值，减去已用 | `static` |

三条附加裁定：

1. **剩余只在新进度事件到达时重算**；两次事件之间随时钟递减，下限 1 分钟。这样数字不会来回跳。
2. **算出的剩余 ≤ 0 时不显示负数也不显示 0**，改为 `state: "overrun"`，文案「已超过预计时间，仍在运行」（领取表验收第 4 条：不出现空白或错误数值）。
3. **历史校准取同项目同阶段**。跨项目校准需要新接口，不在本项范围，登记为余量（§10 E-07-4）。

`agent-loading-estimates.json` 因此**改动 0 行**：静态值继续做最后一层兜底，校准发生在运行时。上游把该文件列入本项持有清单是**上限不是必须**，本项即刻释放（同 `05` 对 `page-loading.tsx` 的处置）。

### D5 停滞判定：阈值必须大于后端的自恢复窗口

后端三处停滞阈值都是 600 秒，超时后自动恢复（§0.2）。前端阈值取 **12 分钟**（600 秒 + 2 分钟缓冲）：小于它就会在后端正常自恢复期间误报停滞。

| 状态 | 触发 | 文案 |
| --- | --- | --- |
| `overrun` | 已用 > 预计总时长，但事件仍在推进 | 已超过预计时间，仍在运行 |
| `stalled` | 最近 12 分钟没有任何新事件 | 最近 12 分钟没有新进展，可以继续等待，也可以取消后重新执行 |

- 可执行动作用**既有的停止按钮**（`:1518-1526`，运行中的 `title` 已是「取消当前任务」）。**不新增按钮、不新增提示条与横幅**——反馈形态归 `C1-W1-06`。
- 停滞文案不断言原因（§2.3 第 2 条）。
- 事件时间同样走 `parseDateTime()`。

### D6 分数只前进，总量以最新值为准

`novel_reading_*` 会重播、乱序到达，`continuation_replan` 还会在运行中改变总量（`agent_runner.py:8487-8495`）：

- `completed` 取历史最大值，**不回退**。
- `total` 取最后一条带总量事件的值（可能变大）。
- 进入无分数步骤（如 `novel_analysis_synthesis`「正在形成小说解读」）时**保留最后一次分数**，与步骤名并列显示，不清零。

### D7 显示位置：等待界面给全量，状态行给两项
