## 0. 复用的框架与独立性要求

### 0.1 复用（不得另立标准）

沿用历史成熟度基线文档 §1–§2 的框架（来源 `cursor/w1-d-maturity-baseline-b2eb`，处置为"复用"，见总控看板 2.3）：

- **L0–L5 六级量表**：L0 未起步、L1 骨架、L2 可用、L3 稳定、L4 成熟、L5 卓越。
- **三维度分级细则**：A 功能易用性、B 交互可靠性、C Agent 智能化。
- **E1–E5 证据类型**：E1 代码存在性、E2 静态质量、E3 自动化测试、E4 运行时行为、E5 量化指标。
- **合格证据三要素**：可复现命令或步骤、原始输出存档、锚定 commit SHA。缺一即视为证据无效。
- **各级最低证据要求**：L1 需 E1+E4；L2 需再加 E2+E3；L3 需 E3 覆盖主要场景；L4/L5 需 E5。
- **评级只认证据**：某级别的全部准入条件都有合格证据支撑才能评到该级，缺任何一条降到下一级。

**作废、不得沿用**：该文档 §5–§8 对 `deda75a` 空仓的三维度全 L0 自评、证据缺口清单、`GOAL-W1-01…03`，以及 §3 的 `BLK-W1-01`（仓库无代码）、`BLK-W1-02`（模型凭据未定）。评估对象是空仓，结论对真实产品不成立。阻塞按本提纲第 4 节以 `BLK-C1-*` 重新登记。

**报告格式**沿用 `docs/templates/w5-verification-report.md`，两处调整：报告落 `docs/iteration/cycle-01/`（不是 `docs/wave-01/`）；§3"存档路径"列填 `docs/iteration/cycle-01/evidence/...`。

### 0.2 独立性要求

- 从**干净检出**开始复现，不复用被核验方的构建产物、数据库文件与工作区。
- 只按被核验方声明的命令与步骤操作。命令缺失、环境不满足、输出未存档，一律判"无法复现"，证据无效并触发降级——外链（CI 地址等）不算存档。
- 核验产生的新证据按同一约定归档，任务目录用被核验任务的编号，文件名加 `-w5` 后缀词，与被核验方证据并存互不覆盖。
- 核验评级与自评不一致时，以核验评级为准，并在差异说明中给出判定依据。

### 1.2 基线级别的判定要点

W5 的第一项工作是**为 `abb779e` 定出基线级别**——历史文档给出的"全 L0"基于空仓，已作废，没有可用的起点。定基线时必须区分两件事：

- **能力面**：代码里实际有什么。
- **证据面**：这些能力有没有合格证据支撑。按"评级只认证据"，最终级别取两者中较低者。

各维度定基线时至少要核对以下事实（均可在 `abb779e` 上复现）：

**维度 A 功能易用性**
- 支撑升级的事实：8 条用户可达路由、6 类创作任务、10 个阶段文件、完整的项目生命周期（新建 → 逐阶段推进 → 导出 → 归档 → 回收站）、README 有使用说明、禁用态附逐条中文原因的 tooltip。
- 压低级别的事实：产品内零引导、界面直接使用内部术语、主编辑区空态只有一行标题、`apps/web` 无任何自动化测试（E3 在前端为空）、无运行时走查记录（E4 全缺）。
- 判定要点：L3 要求"新用户按文档可独立完成核心任务"，须有 E4 走查证据才能声称；无 E4 时按最低证据要求，级别上限受限。

**维度 B 交互可靠性**
- 支撑升级的事实：服务端长任务可靠性成熟（B-01…B-06：任务单飞、执行租约与抢占回收、重启恢复、额度预留幂等状态迁移、事件游标续读、失败结构化分类），39 份 API 测试可作 E3。
- 压低级别的事实：三项"严重"级故障模式共存——编辑草稿只在内存（FM-01）、无离开保护（FM-02）、新建项目无幂等键（FM-03）。
- 判定要点：L2 的准入条件明确包含"用户数据不会因常见错误丢失"。上述三项在 `abb779e` 上均可复现，因此该条件不满足。这是一个二值判定，不因服务端成熟度高而放宽。

**维度 C Agent 智能化**
- 支撑升级的事实：`Agents/` 是可独立运行的 Claude Code 子项目，20+ Skill 带 `references/` 与校验脚本，19 份测试，`system-agent-evolution` 有执行记录与报告契约，后台有"Agent 进化"与"剧本蒸馏"分区，失败分类带 `retryable` 兜底（B-06）。
- 需核实的事实：L3 要求"有输出质量抽检记录"——`abb779e` 上是否存在、存在于何处，须由 W5 取证确认，不得推定。
- 判定要点：本波无 Agent 智能槽做过基于 `main` 的能力核对（见总控看板 2.3 的"待定"），维度 C 的基线完全依赖 W5 自行取证。

### 1.3 判定纪律

- 三维度各自独立判定，不做加权平均，不给"总体级别"。
- 一次最多升一级。声称升两级时，报告须说明为何不是分两个周期完成，并附两级的完整准入证据。
- 不使用"基本完成""明显改善""接近 Lx"这类表述。级别是二值的：够或不够。

## 3. 证据核查

### 3.1 逐条明细表

对每条支撑评级或支撑"任务已完成"的证据声明填一行：

| 序号 | 维度 | 任务编号 | 证据类型 | 声明内容 | 复现命令或步骤 | 核验结果 | 判定 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| | A/B/C | `C1-W1-xx` | E1–E5 | | | 实际输出摘要 + 存档路径 | 通过 / 不通过 / 无法复现 |

判定规则：**通过**——按声明的命令复现，结果与声明一致；**不通过**——可复现但结果与声明不符（须附实际输出）；**无法复现**——命令缺失、环境不满足或输出未存档，按证据无效处理并触发相关评级降级。

### 3.2 脱敏核查

逐份证据核查是否含剧本正文、用户上传内容、令牌、账号口令、真实用户路径。脱敏不合格即证据无效。发现凭据泄露须立即轮换该凭据并单独上报——仅删除文件不算处置，git 历史仍在。

### 3.3 证据能力约束（W5 必须如实记录）

`abb779e` 上存在两项会限制取证的现实约束，W5 报告须说明本次核验受其影响的程度：

- **无 CI**：仓库无 `.github/` 目录，全部检查只能本地执行，E2/E3 没有独立的第三方执行记录。
- **运行时证据依赖凭据与浏览器**：E4 需要启动前后端并登录，涉及模型调用还需供应商凭据。W1 三个槽全部因此未能产出任何运行时证据（无截图、无录屏、无真实交互记录）。W5 若同样无法取得，须明确写出"E4 缺失"并按此触发相应降级，**不得以源码走查代替 E4**。
