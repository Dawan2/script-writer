## 0. 通用约定

### 0.1 完成判定

一个工作项算完成，必须同时满足：

1. 验收标准中每一条都能给出"是"的判定，且判定方式是自动化测试或可复现的操作步骤，不接受"人工试过了"；
2. 证据已落盘到 `docs/iteration/cycle-01/evidence/<任务编号>/`，或以测试代码形式进入仓库；
3. `npm run check` 通过；涉及后端逻辑的项 `npm run test:api` 通过；涉及前端逻辑的项 `npm run test:web` 通过（该命令由 `C1-IR-T10` 建立）；
4. 新增或修改的界面文案经用户视角复核：不含内部术语、英文标识、错误码原文。

### 0.2 证据类型

| 类型 | 要求 |
| --- | --- |
| 自动化测试 | 测试代码入仓，测试名能读出被验证的故障模式；断言针对行为而非实现细节 |
| 故障注入记录 | 说明注入点、注入方式、观察到的系统行为，可由他人按记录复现 |
| 操作走查 | 编号步骤 + 每步预期与实际，覆盖失败路径而不只是成功路径 |
| 录屏 | 仅用于交互过程类验收（冲突选择、原地重新登录、离线提示），须包含失败发生与恢复完成两端 |
| 一致性快照 | 涉及文件与数据库双写的项，须给出两侧状态的对照快照 |

### 0.3 脱敏

证据不得包含剧本正文、用户上传内容、令牌、账号口令。文档内容一律以摘要或字符数代替原文。

### 0.4 梯队与并行

| 梯队 | 工作项 | 说明 |
| --- | --- | --- |
| 第 0 梯队 | T01、T10 | 使能项。T01 提供错误契约，T10 提供前端证据能力，两者互不依赖，可同时开工 |
| 第 1 梯队 | T02、T03、T04、T06、T08 | 五项互不依赖，可完全并行。T02 需要 T01 的错误契约 |
| 第 2 梯队 | T05、T07、T09 | 依赖第 1 梯队的请求核心与草稿层 |

## C1-IR-T01 服务端统一错误信封与用户视角文案

**覆盖故障模式**：FM-05（结构丢失）、FM-12（英文术语外泄）

**目标**：把已有的 `AgentExecutionError` 分类语义提升为全 API 的 HTTP 错误契约，使客户端能按类型决定行为，并使"写一句用户看得懂的说明"成为新增失败路径的硬要求。

**范围**：
- `apps/api/app/main.py`：注册统一异常处理器
- `apps/api/app/core/`：新增错误契约定义（错误码、类别、是否可重试、面向用户的说明、追踪号、可选明细）
- `apps/api/app/routers/`、`apps/api/app/services/`：改造现有 `HTTPException(detail=字符串)` 抛出点
- 复用 `apps/api/app/services/agent_runner.py:865-882` 的字段语义，不另起一套

**不属于本项范围**：前端如何呈现（T02）；重试策略（T02）；会话失效的处理流程（T07）。

**验收标准**（逐条二值判定）：
1. 任意接口的失败响应体形状一致，且含错误码、类别、是否可重试、面向用户的说明、追踪号五个字段。
2. `root_cause` 类内部信息不出现在响应体中，但出现在日志或审计记录中，且可用追踪号关联。
3. 现状基线 FM-12 列出的英文报错（`Project already has running job #N`、`Unsupported stage`、`Unknown stage`、`Stage file not found` 及同族）全部替换为用户视角中文说明，且说明中包含用户可执行的下一步。
4. 校验失败（当前经 `detail` 数组传递）在信封的明细字段中结构化传递，客户端无需从文案里解析。
5. 存在一项检查（测试或静态检查）能在新增裸字符串错误时失败，防止契约被绕过。

**证据要求**：
- 自动化测试：覆盖每一个错误类别至少一个用例，断言响应体字段完整、内部信息不外泄；
- 自动化测试：断言 FM-12 各条目的新文案；
- 故障注入记录：一次内部异常，展示日志侧 `root_cause` 与响应侧追踪号可对应；
- 静态检查演示：一段违规写法与它被拦截的输出。

## C1-IR-T02 前端请求核心：超时、取消、错误分类

**覆盖故障模式**：FM-04（无超时无取消）、FM-05（前端侧）；另承接架构方案中 D19 的部分成功呈现

**目标**：把 `api-client.ts` / `admin-api.ts` 共用的裸 `fetch` + `parseJson` 升级为请求核心，使每个请求有超时与取消，每个失败有类型。

**范围**：
- `apps/web/src/lib/api-client.ts`、`apps/web/src/lib/admin-api.ts`：改为经由请求核心发出
- `apps/web/src/lib/`：新增请求核心模块（分级超时、取消信号合并、错误信封解析、追踪号注入、只读请求有限退避）
- `apps/web/src/lib/server/backend.ts`：为服务端代理补逐跳超时（内层小于外层）与追踪号透传
- 批量操作的逐项失败改为分项呈现（现状 `batch-tasks-page.tsx:322` 把 `failures[]` 拼成一句红字）

**不属于本项范围**：幂等键生成与服务端去重（T03）；会话失效的重放（T07）；离线状态机（T09）。请求核心须为这三项预留接入位但不实现。

**依赖**：T01（错误契约）；T10（测试基座，用于产出证据）。

**验收标准**：
1. 读、写、上传三类操作各有独立超时预算，超时后请求被真正中断且界面退出"处理中"。
2. 组件卸载后在途请求被取消，且不再回写状态。
3. 服务端代理层有自己的超时，且小于浏览器侧同一操作的超时。
4. 失败对象携带类型信息，调用方可按类型分支；业务代码中不再存在从错误文案里截取子串再解析的写法（`app/workspace/page.tsx:193-208` 该写法被移除）。
5. 只读请求的有限退避重试符合声明的策略；写操作在任何情况下都不会被请求核心自动重发。
6. 批量操作的失败逐项展示，成功项不因存在失败项而被表述为失败。

**证据要求**：
- 自动化测试：超时触发中断、卸载触发取消、写操作不自动重发、只读退避间隔符合策略（用可控时钟）；
- 自动化测试：错误信封解析为类型化对象；
- 操作走查：上游无响应时界面的表现（含超时前后两端）；
- 代码检索证明：`api-client.ts` / `admin-api.ts` 中不再有直接调用裸 `fetch` 的路径。

## C1-IR-T03 幂等键通用化

**覆盖故障模式**：FM-03（重复项目与重复额度预留）

**目标**：把只服务外部 API 的幂等收据机制提升为通用能力，接入第一方提交类写操作，使超时重试与重复提交不产生第二个实体。

**范围**：
- `apps/api/app/routers/openclaw_api.py:117-215`：抽取幂等收据逻辑为可复用依赖
- `apps/api/app/db/session.py:518-523`：沿用现有表结构，如需扩展保持向后兼容
- 接入点（本项必须完成）：`POST /projects`（`routers/projects.py:272`）、批量任务创建（`routers/batch_tasks.py:95`）
- `apps/web/src/lib/`：在请求核心的预留接入位上生成并携带幂等键（键在用户意图产生时生成，显式重试沿用同键，用户修改输入后换新键）

**不属于本项范围**：Agent 任务创建（已由项目级单飞与并发上限保护，基线 B-01/B-04，不重复建设）。

**依赖**：T02 的预留接入位（可与 T02 并行，接口先行约定）。

**验收标准**：
1. 同一幂等键的两个并发创建请求只产生一个实体，两个响应体一致。
2. 首次请求执行中时，同键请求得到明确的"处理中"语义，而不是第二次执行或普通失败。
3. 同键但请求内容不同（指纹不匹配）时被拒绝，并给出用户可理解的说明。
4. 模拟"服务端已创建但响应丢失"后客户端重试：实体数量为 1，额度扣减次数为 1。
5. 用户修改表单内容后再次提交：视为新意图，正常创建。

**证据要求**：
- 自动化测试：上述 1–3、5 各一个用例；
- 故障注入记录：第 4 条的响应丢失注入方式与前后的实体数、额度流水对照；
- 一致性快照：额度流水在重试前后的对照。

## C1-IR-T04 编辑草稿不丢：本地持久化与离开保护

**覆盖故障模式**：FM-01（草稿只在内存）、FM-02（无离开保护）

**目标**：让"用户敲进去的内容"在刷新、崩溃、误关、误切换、会话过期之后仍然存在且可见。这是不变量一的落地项。

**范围**：

- `apps/web/src/components/workspace/markdown-workspace.tsx`：草稿恢复入口与状态呈现
- `apps/web/src/lib/`：新增草稿层（键按项目 + 阶段 + 基线内容摘要，见架构方案 §4 对 D4 的修正）
- 新建项目表单的输入保留（`components/workspace/new-project-form.tsx`）

**不属于本项范围**：冲突时的选择界面（T05）；离线状态呈现（T09）；远端草稿同步（架构方案已裁决不做）。

**验收标准**：
1. 编辑后不保存直接刷新页面：重新进入同一阶段时草稿仍在，且界面明示"有未保存的修改"。
2. 编辑后切换到其他阶段或其他项目：先出现确认，用户选择放弃才丢弃；选择返回则草稿完整。

4. 草稿的基线内容摘要与服务端当前内容不一致时，界面明示"服务器上的内容已变化"，且**不**自动丢弃草稿、**不**自动覆盖服务端。
5. 保存成功后草稿被清理，不残留过期草稿导致下次进入时出现假的"未保存修改"。
6. 新建项目表单填写中途刷新：已填内容仍在（上传的文件除外，须明示需重新选择）。

**证据要求**：

## C1-IR-T06 文档写入原子化与文件/数据库一致性

**覆盖故障模式**：FM-07（非原子写）、FM-08（双写无统一提交点）

**目标**：让每一次文档写入的结果可判定——要么完整生效，要么完全没发生；并让文件与数据库的分叉可被发现和追平。

**范围**：
- `apps/api/app/services/workspace_service.py:3410-3518`：主写入路径与回滚路径改用同文件已有的 `_atomic_write_text`（`:537-543`）
- 同文件其余直写目标文件的路径一并排查（`write_text` 在该文件共 27 处，需逐一判定哪些是目标文件直写）
- 明确文件写入与数据库记录的顺序与补偿方向（架构方案裁决 5：文件为事实源，索引追平）
- 新增一致性自检：能报出"文件内容与最新版本记录不一致"的阶段文档

**不属于本项范围**：引入版本号字段（架构方案裁决 1 已否决）；分块存储（已作废）。

**验收标准**：
1. 阶段文档的写入与回滚均经原子替换，目标文件不出现中间态。
2. 在文件已写入、数据库记录尚未提交的时点注入失败：文件与数据库处于可判定状态之一，且该状态能被一致性自检识别。
3. 一致性自检能在人为制造分叉时报出该阶段文档，在正常状态下无误报。
4. 写入过程中强制中断进程后，目标文件内容是"改动前完整内容"或"改动后完整内容"之一，不是截断内容。
5. 版本历史中不存在"文件已变但无对应版本记录"的空洞（由第 3 条的自检结论支撑）。

**证据要求**：
- 自动化测试：第 1、3 条；
- 故障注入记录：第 2、4 条的注入点、注入方式、每次注入后的文件字节数与数据库记录状态；
- 一致性快照：注入前后文件摘要与最新版本记录摘要的对照表。

## C1-IR-T07 会话过期不丢稿

**覆盖故障模式**：FM-06（会话过期即丢稿）、FM-14（多标签会话不同步）

**目标**：会话失效不再等于内容损失。用户在原地重新登录后能继续保存刚才写的内容，且不会把内容写进另一个账号。

**范围**：
- `apps/web/src/lib/`：请求核心的会话拦截——失效时挂起在途请求、单飞处理、成功后原样重放（幂等键不变）
- 前端新增原地重新登录层（不整页跳转、不卸载编辑器）
- 重放前校验当前登录者与内容归属一致，不一致则阻断写入并给出导出路径
- 登出与换号经浏览器标签间广播同步（架构方案对 D25 的修正）
- `apps/api/app/routers/auth.py`、`apps/api/app/core/security.py`：明确"会话失效"与"账号不匹配"两种语义的区分（不引入续期令牌机制，见架构方案 R4）

**不属于本项范围**：令牌续期机制；会话世代（已修正为广播 + 属主校验）。

**依赖**：T01、T02、T04（草稿须已落盘）。

**验收标准**：
1. 编辑过程中会话失效：界面出现原地重新登录，编辑器不被卸载，草稿完整。
2. 重新登录成功后，此前失败的保存请求被重放并成功；重放不产生重复实体（幂等键未变）。
3. 并发多个请求同时遭遇会话失效：只触发一次重新登录流程，全部请求在登录后完成。
4. 在另一账号下重新登录：写入被阻断，界面说明内容属于其他账号并提供导出方式，草稿不被静默写入新账号。
5. 一个标签页登出后，另一个标签页在下一次操作前即感知会话已结束，不出现"看起来还登录着但所有操作都失败"。

**证据要求**：
- 自动化测试：第 2、3 条（可控的会话失效注入）；
- 操作走查 + 录屏：第 1、4 条完整过程；
- 操作走查：第 5 条的双标签页步骤。

## C1-IR-T08 进展流心跳与重连契约

**覆盖故障模式**：FM-09（无心跳无重连契约）

**目标**：让长任务进展在网络与代理不稳定时仍然可信——要么在推进，要么明确告诉用户连接断了。

**范围**：
- `apps/api/app/routers/agent.py:322-352`：SSE 输出补事件标识帧、重连间隔提示与保活帧；降低数据库轮询频率（架构方案 R2）
- `apps/web/src/app/api/agent/jobs/[jobId]/stream/route.ts`：代理层保活，不缓冲
- `apps/web/src/components/workspace/agent-panel.tsx:909-936`：重连使用事件游标续读，明示"连接已断开，正在重连"
- 沿用已有的 `after_id` 事件游标（基线 B-05），不改事件存储

**不属于本项范围**：任务状态机（已满足，保持）；引入消息队列（架构方案 R2 已记入后续周期）。

**验收标准**：
1. 长时间无事件时连接不被中间层断开（保活帧生效）。
2. 断开重连后事件既不重复也不丢失，事件标识连续。
3. 连接处于断开状态时界面明示，不出现"进展停住但界面看起来正常"。
4. 任务在页面关闭期间完成：重新打开后进展与结果完整（此为已有能力，本项须证明未被破坏）。
5. 单个任务的进展查询频率下降，且不影响用户感知的进展及时性。

**证据要求**：
- 自动化测试：第 2 条（游标续读的不重不漏）；
- 故障注入记录：第 1、3 条（注入连接中断与长静默），含注入方式与观察到的界面状态；
- 操作走查：第 4 条；
- 前后对比数据：第 5 条的单位时间查询次数对照。

## C1-IR-T09 离线感知与保存状态可见

**覆盖故障模式**：FM-13（无离线感知）、FM-16（轮询无门控无退避）

**目标**：让用户随时知道"我的内容现在在哪"，并且断网期间不会在毫不知情的状态下继续写很久。

**范围**：
- `apps/web/src/lib/`：连接状态机（在线 / 降级 / 离线），以实际请求成败与心跳探测为准，浏览器在线标志仅作提示信号
- `apps/web/src/components/workspace/markdown-workspace.tsx:1574-1575`、`:1744-1745`：保存状态补齐离线态与失败态
- `apps/web/src/app/workspace/page.tsx:1162/1181/1288/1318`：轮询定时器接入可见性门控与失败退避
- 离线期间保住草稿（依赖 T04），恢复连接后提示用户保存；不做自动重放（架构方案对 D30 的修正）

**不属于本项范围**：本地写入队列自动重放；离线优先编辑模式。

**依赖**：T02（请求核心提供成败信号）、T04（草稿层）。

**验收标准**：
1. 断网后保存：界面明示当前处于离线且内容已在本地保留，不表述为普通失败。
2. 恢复连接后界面明示可以保存；用户保存后内容与本地草稿一致。
3. 连接状态判定以实际请求结果为准：浏览器报告在线但请求持续失败时，状态进入降级或离线。
4. 标签页隐藏时轮询暂停，重新可见后恢复。
5. 后端不可用期间轮询退避，不以固定频率持续重试。

**证据要求**：
- 自动化测试：第 3、4、5 条（可控的连接状态与可见性注入）；
- 操作走查 + 录屏：第 1、2 条完整过程（断网 → 提示 → 恢复 → 保存成功）；
- 前后对比数据：第 5 条在后端不可用期间的请求次数对照。

## C1-IR-T10 前端可靠性测试基座

**覆盖故障模式**：FM-15（前端无法回归）

**目标**：让 T02、T04、T05、T07、T09 的验收可以自动执行。没有这一项，前端侧的所有可靠性修复都只有一次性人工结论。

**范围**：
- `apps/web/package.json`：引入测试运行器，新增 `test` 脚本；根 `package.json` 的 `test` 串接 `test:web`
- 测试工具：可控时钟（超时与退避断言）、可编程的请求故障注入（延迟、失败、超时、畸形响应）、连接状态与页面可见性注入、本地存储沙箱
- 交互过程类验收（冲突选择、原地重新登录、离线提示）的端到端手段选型与最小骨架
- 一项静态检查：业务组件不得直接调用裸 `fetch`（固化基线 B-12 的现状，防止回退）

**不属于本项范围**：为其他工作项编写它们各自的测试（由各项自行负责）；后端测试基座（已有 39 个测试文件与 `npm run test:api`）。

**验收标准**：
1. `npm run test:web` 可运行并在根 `npm test` 中被串接。
2. 故障注入能按接口、按第几次调用编程控制。
3. 可控时钟能让超时与退避断言不依赖真实等待。
4. 静态检查对"业务组件直接调用裸 fetch"报错，且在当前代码上无误报。
5. 至少一个示例测试同时用到故障注入与可控时钟，可被其他工作项直接参照。

**证据要求**：
- 测试代码入仓（含第 5 条的示例测试）；
- 命令输出记录：`npm run test:web` 与 `npm test` 的执行结果；
- 静态检查演示：一段违规写法与它被拦截的输出。
