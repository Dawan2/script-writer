## 4. 两份增补的冲突裁定

两份增补对同一事实给出不同结论的六处，逐条落定。

### 4.1 知识库不可用：不阻断创作，但状态必须真实

增补的 `C1-W1-29` 验收第 1 条要求"知识库缺失时阶段状态不再判定为通过"，并入文档 3.3 裁定"不阻断"。

**裁定：不阻断，取并入文档口径。** 分工三处——

- `C1-W1-31`：`knowledge_status` 区分「已加载」「知识库不可用」「知识库为空」，取值来自真实加载结果；门禁不得因状态字面值为「已加载」而放行；「不可用」计入任务运行记录供运维排查。**阶段仍可完成**，但完成记录必须写明本次没有可用的创作原则与策略公式。
- `C1-W1-30`：无可用原则时清单只含 Skill 固定要求，不产生空的语义判定项，流程继续。
- `C1-W1-40`：用户在「本次依据」里看到"本次没有使用剧本库知识"，不显示空白区块。

理由：知识库是后台策展资产，缺失属运维问题，阻断会让用户的创作任务因为一件他无法处理的事而失败，而 Skill 固定要求仍能兜住格式与结构。真正不可接受的是当前这种"零原则却判定通过、用户与运维都看不到"的状态。

### 4.2 无引用 reference 的基线是 2 份

`C1-AG-T01` 记 6 份，`TA-03` 记 2 份。**裁定：取 2 份**，判定口径为"三类引用方都没有"——`SKILL.md` 直接引用、reference 之间的引用链、脚本或工具返回值里的动态注入。另 4 份有真实消费者，按 6 份执行会删掉能力。`C1-W1-34` 的检查须按同一口径实现，否则第一次运行就产出 4 条误报，而它的验收要求"无误报"。

### 4.3 第 0 梯队是 29、31、36

`C1-AG-T02` 的依赖声明与其 0.4 节梯队表矛盾。**裁定：以条目自身的依赖声明为准。** 第 0 梯队为 `C1-W1-29`、`C1-W1-31`、`C1-W1-36`；`C1-W1-30` 须在 29（清单结构）与 31（回归夹具）之后开工，提前开工只会返工。

### 4.4 `httpx` 落在 `requirements-dev.txt`

同一修复出现在两个分支：`cursor/w1-agent-intelligence-plan-058e @ 248c1f6` 加进 `apps/api/requirements.txt`；`cursor/w1-failure-path-contract-mapping-058e` 新建 `apps/api/requirements-dev.txt` 并在 README 补了安装说明。**裁定：取 `requirements-dev.txt`**，`httpx` 只被测试客户端需要，不属运行时依赖。集成槽并入时撤回对 `requirements.txt` 的改动。
