## 3. 需要裁定的五处

### 3.1 无引用方的 reference 是 2 份，不是 6 份

`C1-AG-T01` 验收第 3 条写「`references/` 下不存在未被任何 `SKILL.md` 引用的文件（当前 6 个，须归零）」，`TA-03` 只认 2 份。本槽在 `main @ abb779e` 上逐份核对了引用方：

| 文件 | 引用方 | 判定 |
| --- | --- | --- |
| `full_generate/references/全稿验收规则.md` | 无 | 无引用方 |
| `full_generate/references/剧本内容与格式规范.md` | 无 | 无引用方 |
| `novel_analysis/references/高光时刻剧本改编原则.md` | `trial_generate/scripts/get-episode-info.mjs:67` 在工具返回值里下发阅读指令 | 有引用方 |
| `outline_rewrite/references/小说剧情单元取舍原则.md` | `outline_rewrite/references/小说改编场景执行步骤.md:9`、`:19`，该文件由 `outline_rewrite/SKILL.md:25`、`:36` 引用 | 有引用方 |
| `foreign_review/references/review-scorecard.json5` | `init-foreign-review.mjs:27` 作为骨架模板读取 | 有引用方 |
| `trial_generate/references/trial.json5` | `init-trial.mjs:12`、`check-trial.mjs:25` | 有引用方 |

**裁定**：判定口径改为「无引用方」，引用方包含三类——`SKILL.md` 的直接引用、reference 之间的引用链、脚本或工具返回值里的动态注入。基线数从 6 改为 2，须归零。按 6 份执行会删掉或强行改造 4 份有真实消费者的文件，其中「工具返回值里下发阅读指令」是跨 Skill 按需供给知识的正确做法，删掉是能力倒退。

同时 `C1-W1-34` 的契约检查须按这个口径实现：只报「三类引用方都没有」的文件，否则第一次运行就会产出 4 条误报，而该项验收第 2 条要求「无误报」。

`G-06` 的严重度维持「低」，但覆盖范围从 6 份收窄为 2 份，另 4 份改为在清单里登记引用方，作为检查脚本的白名单依据。

### 3.2 `C1-W1-30`（原 `T02`）不属于第 0 梯队

`C1-AG-T02` 的「依赖」写明 T01、T03，而同文件 0.4 节把 T01、T02、T03 一起列为第 0 梯队并称「三项互相独立，可同时开工」。两处矛盾。

**裁定**：以条目自身的依赖声明为准。第 0 梯队为 `C1-W1-29`、`C1-W1-31`、`C1-W1-36` 三项；`C1-W1-30` 归第 1 梯队，须在 29 与 31 之后开工。理由是 30 要把原则的通过标准写进 29 建立的清单结构、并用 31 的夹具做回归，两者缺一它都无法给出验收证据。

### 3.3 知识库不可用时：不阻断主链路，但状态必须真实

`TA-01` 要求「不可用时按策略阻断或显式告警」，`C1-AG-T02` 验收第 6 条要求「没有可用原则时流程不中断」。

**裁定**：不阻断，改为「状态真实 + 用户可见」，三处分工——

- `C1-W1-31`：`knowledge_status` 区分 `loaded` / `unavailable` / `empty`；执行策略明确产出「本次没有可用的创作原则与策略公式」；验收门禁按真实状态判定，不再因状态字面值为 `loaded` 而放行；`unavailable` 计入任务运行记录供运维排查。
- `C1-W1-30`：知识库无可用原则时，清单只含 Skill 固定要求，不产生空的语义判定项，流程继续。
- `C1-W1-40`：用户在「本次依据」里看到「本次没有使用剧本库知识」，不显示空白区块。

理由：知识库是后台策展资产，缺失属运维问题；阻断会让用户的创作任务因为一件他无法处理的事而失败，而 Skill 固定要求本身仍能兜住格式与结构。真正不可接受的是当前这种「零原则却判定通过、用户与运维都看不到」的状态。

### 3.4 `httpx` 的落点取 `requirements-dev.txt`

同一处修复出现在两个分支：`cursor/w1-agent-intelligence-plan-058e` 把 `httpx==0.28.1` 加进 `apps/api/requirements.txt`；`cursor/w1-failure-path-contract-mapping-058e` 新建 `apps/api/requirements-dev.txt`（`-r requirements.txt` + `httpx`）并在 README 补了测试依赖安装说明。

**裁定**：取 `requirements-dev.txt`。`httpx` 只被 `fastapi.testclient` 需要，不属运行时依赖，混进 `requirements.txt` 会让生产镜像多装一个包。集成槽并入时撤回对 `requirements.txt` 的改动，保留另一分支的 `requirements-dev.txt` 与 README 说明。

连带影响：`C1-AG-T01…T14` 通用约定里的「领取时基线：API 454 项 4 失败」成立的前提是先装 `requirements-dev.txt`；不装则 `test_openclaw_api` 整个模块无法导入，只有 450 项可执行。领取表的测试基线条目须写明这一步。

`script_sync_service.py:2113` 的 `utc_now_iso` → `_utc_now_iso` 两个分支改的是同一行、内容完全相同，先并入哪个都可以，第二个分支该处改动作废。

### 3.5 Skill 计数口径

基线文档写「14 个 Skill」（只数 `.claude/skills/`），测绘写「25 份 SKILL.md」（`.claude/skills/` 14 个 + `skills/` 11 个）。本槽核对：`.claude/skills/` 下 14 个 Skill 目录加 `_shared`，`skills/` 下 11 个，`SKILL.md` 合计 25 份。两个数都对，指的不是一回事。

**裁定**：`C1-W1-34` 的检查与 `CLAUDE.md` 修正按「创作主链路 14 个」，因为 `CLAUDE.md` 是创作 Agent 的入口说明书，后台蒸馏 Skill 不由它路由。凡涉及全仓 Skill 规模的表述一律写「创作主链路 14 个 + 后台知识 11 个」，不写单一数字。
