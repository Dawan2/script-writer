## 1. 结论速览

1. **最严重的新发现是校验失败会把用户提交的内容原样回显给浏览器，包含口令**（FM-17）。`POST /auth/login` 少传一个字段，响应体里就带着刚才输入的密码原文。140 个接口里 138 个可触发这条路径。
2. **"失败必须带类型"这条不变量，后端其实已经做到了一大半，是在传递途中丢的**。Agent 任务落库时带 `error_code / error_category / error_retryable`，每个 HTTP 响应都带 `x-request-id` 追踪号——但前端类型定义里没有前三个字段，代理层不转发追踪号。缺的不是机制，是把已有信息接上（第 5 节）。
3. **后端整体不可用没有任何处理**：57 个代理路由中 55 个没有错误处理，后端连不上时返回**空响应体的 500**，用户看到"请求失败（500）"。
4. **会话过期后页面照常打开**：中间件只检查会话 Cookie 是否存在，Cookie 有效期（7 天）与令牌有效期（`access_token_expire_minutes`）是两个各自独立的常量。实测：带过期会话打开工作台返回 200，同一会话的每个数据请求返回 `Invalid token`。
5. **FM-03 已取得实测证据**：同一个新建意图并发提交三次，产生 3 个项目、3 个工作区目录。服务端会把目录名自动改成 `-2`、`-3`，说明它知道重名，仍然照建。
6. **`npm run test:api` 在干净克隆下无法通过**：450 项中 4 失败 9 错误。其中 8 项失败源于一个真实产品缺陷（剧本同步成功即报失败），1 项源于测试依赖缺失。两者本槽已修，补齐夹具后为 454 项全通过。

## 3. 对已有结论的更正

### 3.1 更正 A-01：生产环境的静默放行条件不是"知识库文件缺失"

Agent 测绘给出的证据链是"默认路径下文件不存在 → 返回空字符串 → 静默放行"。实测后这条链在生产环境不成立，但**结论本身成立，只是触发条件不同、覆盖面更大**：

- `agent_runner.py:3647`、`:3798`、`:4396` 在每次调起 Agent 时都显式传入 `ORCA_SCRIPT_KNOWLEDGE_DB_PATH`。显式路径下文件不存在时 `resolveKnowledgeDbPath()` 会**抛错**（并把服务器绝对路径带进错误文案），不会静默放行。"默认路径 + 文件缺失"只在有人直接跑脚本或跑测试时出现。
- 真正的生产静默放行条件是**库文件存在、表结构齐全、但没有任何 `status = 'active'` 的知识**。知识库就是主库 `data/workbench.sqlite3`，两张表由 `apps/api/app/db/session.py:639`、`:673` 随应用建表——**这正是全新部署后的默认状态**。
- 实测（`probe-knowledge-status.mjs`）：库可读、零条已启用知识时，`knowledge_status = "loaded"`、`principle_count = 0`、门禁 issues 为空，`执行策略.md` 写的是"当前没有已启用的世界观创作原则；仍须执行 Skill 中的固定质量、格式与准出要求"——读起来像一句正常说明。

差别是实质性的：按原证据链修（"文件缺失时报错"）解决不了新部署的默认状态；按实测条件修（状态如实反映查询结果）才行。TA-01 已按后者落地，见第 6 节。

### 3.2 更正 FM-05 / D10：追踪号已经存在，缺的是透传

架构方案把"追踪号贯穿"列为 T01 要建的能力。实测发现它已经有了：`apps/api/app/main.py:59-69` 的中间件给**每个响应**都写了 `x-request-id`，没有请求头时自行生成，并把它绑进审计上下文。

丢在两处：

- `apps/web/src/lib/server/backend.ts:36-41` 的 `proxyJson` 构造响应时只复制 `content-type` 一个响应头，追踪号在代理层被丢弃；
- 浏览器侧 `api-client.ts` 从不读响应头。

实测：同一个 404，后端响应带 `x-request-id`，代理层响应不带。所以 T01 在这一项上的工作量是"把已有的号透传并呈现"，不是"设计一套追踪号机制"。

另外这个中间件有一个自身的缺口：`response.headers["x-request-id"] = request_id` 写在 `call_next` 之后，未捕获异常会让 `call_next` 直接抛出，**最需要追踪号的 500 响应反而没有号**。

### 3.3 更正 FM-06 / T07：`Session expired` 不是会话过期的那条路径

`apps/api/app/dependencies.py:56-64` 的判定顺序是：

| 情况 | 返回文案 |
| --- | --- |
| 没带凭据 | `Not authenticated` |
| 签名不对**或令牌已过期** | `Invalid token` |
| 用户被停用 | `Inactive user` |
| `auth_version` 变了（改密码、强制下线） | `Session expired` |

`decode_access_token()` 对"签名错误"和"已过期"都返回 `None`，两者合并成 `Invalid token`。实测用一个 `exp` 已过期的合法签名令牌请求，得到的确实是 `Invalid token`。

也就是说：**最常见的 7 天自然过期，文案是 `Invalid token`；`Session expired` 只在改密码这类场景出现**。T07 要区分"会话失效"与"账号不匹配"，不能按现有文案分支，必须先让后端把这两种语义分开表达。

### 3.4 补充 GATE-01：把 33 条英文 `detail=` 改完，界面上的英文报错并不会归零

GATE-01 的判定命令只扫 Python 源码里的 `detail="..."` 字面量。校验失败的文案不是这样产生的——它由 Pydantic 生成，经 `api-client.ts:51-64` 的 `apiErrorMessage()` 拼成 `字段名：英文说明`。用户看到的是 `password：Field required`。

实测：140 个接口中 **138 个**在 OpenAPI 里声明了 422 响应。GATE-01 目标值达成后，这 138 个接口的校验失败仍然是英文。门槛需要补一条：校验失败的呈现文案不含英文与原始字段名。

## 4. 新增故障模式（FM-17 起）

严重度沿用 FM 系列定义：**严重**=用户产出丢失/重复计费/敏感信息外泄；**高**=用户被卡死或数据可能不一致；**中**=需要额外操作或信息缺失；**低**=资源浪费。

### FM-17 校验失败把用户提交的内容原样回显，包含口令 · 严重

FastAPI 的默认校验错误体带 `input` 字段，内容是本次提交的原始值。登录接口少传一个字段时，响应体里就是刚才输入的密码明文。这份响应体经代理层原样转发到浏览器，并进入前端的错误处理链路。

- 实测：`POST /api/auth/login` 提交 `{"password":"super-secret-value"}` → `{"detail":[{"type":"missing","loc":["body","username"],"msg":"Field required","input":{"password":"super-secret-value"}}]}`
- 影响面：140 个接口中 138 个可触发（`probe-http-errors.sh` 第 2 节）
- 叠加影响：`app/workspace/page.tsx:193-208` 会从错误文案里 `JSON.parse` 出 `issues` 并展示，回显内容因此可能出现在界面上；任何采集前端错误的手段都会一并采走

### FM-18 校验失败的文案是英文字段名加英文说明 · 高

`apiErrorMessage()` 把 422 的每一项拼成 `loc.join(".")：msg`。`loc` 是后端字段名（`password`、`target_region`），`msg` 是 Pydantic 的英文说明（`Field required`、`Input should be a valid integer`）。终端用户是编剧，这两样都读不懂，也不知道该改哪个输入框。

- 证据：`apps/web/src/lib/api-client.ts:53-64`
- 与 GATE-01 的关系见第 3.4 节：这条路径不在现有门槛的检测范围内

### FM-19 后端不可用时代理层返回空响应体的 500 · 高

57 个 `route.ts` 中只有 2 个有 `try`。`backendFetch` 在后端连不上时直接抛出，路由处理器没有兜底，Next 返回一个**没有响应体、没有 content-type 的 500**。`parseJson` 解析失败后回落到状态码文案，用户看到"请求失败（500）"。

- 实测：停掉 API 后请求 `/api/projects` 与 `/api/auth/login`，两者都是 `HTTP 500` + 空响应体
- 证据：`grep -rl "try {" apps/web/src/app/api --include=route.ts` 命中 2 个文件
- 后果：产品对"后端整体不可用"这一最常见的运维故障没有任何专门表述，与"某个项目不存在"共用同一句红字

### FM-20 会话过期后工作台照常打开，页面看起来正常但什么都做不了 · 高

`apps/web/src/middleware.ts:11-16` 只判断会话 Cookie 是否存在，不校验令牌。Cookie 的有效期写死在 `app/api/auth/login/route.ts` 的 `maxAge: 60 * 60 * 24 * 7`，令牌有效期写在 `apps/api/app/core/config.py:15` 的 `access_token_expire_minutes`——两个独立常量，任何一方改动都会让两者错位。

- 实测：带一个已过期的合法签名令牌打开 `/workspace` 得到 HTTP 200；同一会话请求 `/api/projects` 得到 `{"detail":"Invalid token"}`；完全不带 Cookie 时才会 307 跳登录
- 这是 U-04 / P-2 症状的机制层解释：不是"前端忘了处理 401"，而是**入口处的会话判定和实际的会话有效性是两回事**

### FM-21 追踪号在代理层被丢弃 · 中

见第 3.2 节。后端每个响应都带 `x-request-id`，`proxyJson` 只复制 `content-type`，浏览器侧拿不到任何可用于对账的标识。用户报障时无法提供定位线索，客服也无法反查。

### FM-22 Agent 任务的结构化失败信息在前端类型里不存在 · 高

后端 `agent_runner.py:865-882`、`:2520-2534` 把失败分类落库并随任务对象返回 `error_code`、`error_category`、`error_retryable`。

- 实测：一次真实失败的任务返回 `error_code=SCRIPT_PROFILE_RESOLUTION_FAILED`、`error_category=quality`、`error_retryable=true`
- 证据：`apps/web/src/lib/types.ts:582` 的 `AgentJob` 只声明了 `error_message`；全仓 `apps/web/src` 对这三个字段的引用为 **0 处**
- 后果：`retryable` 已经由后端判定好，界面却无法据此决定要不要给"重试"入口；架构方案裁决 3（"失败带 retryable 标记 → 界面给出显式重试按钮"）所需的数据早就在了

### FM-23 交付文件已生成，只因审计记录写入失败被整个丢弃 · 高

导出 Word 的代理路由在生成完文档后才写导出审计，写失败即抛错，被外层 `catch` 兜住，返回 500 并告诉用户"Word 文档生成失败"。

- 证据：`apps/web/src/app/api/projects/[projectId]/files/[stage]/download/route.ts:38-46`（`recordDownload` 失败即 `throw`）、`:73-76`、`:139-142`、`:207-210`（三个导出分支的 `catch` 都返回"生成失败"）
- 两重问题：已经算好的交付文件被丢掉；给用户的原因是错的——失败的是审计记录，不是文档生成
- 这条路径同时是全仓仅有的两处 `maxDuration` 之一（`:18` 为 60 秒），长剧本导出超时后的表现同样没有专门处理

### FM-24 剧本同步每次成功都以报错收场 · 严重（本槽已修）

`script_sync_service.sync_project_to_base()` 在成功返回时调用了未定义的 `utc_now_iso()`（同文件里的函数名是 `_utc_now_iso`）。这行在 `try/except` **之外**，所以：飞书记录已经写好、本地同步状态已置为"已同步"、成功审计已记录，然后函数抛 `NameError`，被任务运行器当成失败。

- 证据：修复前 `apps/api/app/services/script_sync_service.py:2113`；捕获点 `:1362-1379`
- 管理员看到的：同步任务失败，错误原文 `name 'utc_now_iso' is not defined`
- 这条路径让 `test_script_sync_service.py` 的 8 项测试在干净克隆下全部报错

### FM-25 幂等收据机制在干净克隆下没有任何可执行的测试覆盖 · 中（本槽已修）

`fastapi.testclient` 依赖 `httpx`，而 `requirements.txt` 没有它。按 README 装完依赖后，`test_openclaw_api.py` 整个模块**无法导入**。这是仓库里唯一验证幂等收据表 `(user_id, idempotency_key)` 行为的测试文件——也就是 C1-IR-T03 要提升为通用能力的那套机制，此前零可执行覆盖。

### FM-26 进展事件把服务器绝对路径送到浏览器 · 中

SSE 事件的 `raw_json` 原样透传服务端内部结构。实测抓到的帧里包含 `/workspace/Agents/workspaces/2026-08-27_tester_契约实验/runtime/jobs/1/world_view/执行规范.md` 这样的绝对路径。

- 证据：`agent_runner.py:1524-1534` 的 `public_event()` 原样透出 `raw_json`
- 与 C-4（活动列表暴露工具名与路径）是两处：C-4 是前端渲染时拼出来的，这条是**事件载荷本身**就带着，即使前端不渲染也已经发到浏览器

### FM-27 没有"按 id 读取单个项目"的接口 · 中

`/projects/{project_id}` 只有 `DELETE` 与 `PATCH`，没有 `GET`。实测 `GET /projects/1` 返回 **405 Method Not Allowed**。前端只能拉全量列表再在客户端筛。

- 影响 T-04（工作台状态进 URL）：分享链接与刷新恢复没有对应接口支撑，实现时必须先补这个接口，或接受"每次深链都拉全量列表"
- 405 而不是 404 也让"项目不存在"这条失败路径在客户端无法按状态码判定

### FM-28 工具失败时给出的下一步与失败原因不同源 · 中

Agent 工具脚本的失败出口用固定文案填 `next_action`，与实际的 `message` 无关。

- 证据：`Agents/.claude/skills/trial_generate/scripts/init-trial.mjs:133` 无论什么原因都返回 `next_action: "修复角色小传或剧本大纲后重新初始化。"`
- 实测到的组合：`message: "世界观不存在或不是有效 JSON"` + `next_action: "修复角色小传或剧本大纲后重新初始化。"`——把模型指向了错误的修复对象
- 与 A-03（全稿 Skill 引用了试稿的工具名）同类：**"完成时的指引"与"实际失败原因"不同源**。A-03 是个例，这条是所有 `init-*` / `check-*` 脚本共用的写法，建议按 `check-full.mjs` 已有的做法（按问题类型分派 `next_action`）统一

### FM-29 全稿阶段的 Skill 指引与校验工具互相矛盾 · 中（本槽已修）

五个创作阶段中，只有 `full_generate` 的"开始前准备"写着"当执行策略缺失时忽略"，另外四个写的是"执行策略缺失或失效时调用『执行策略』"。而 `check-full.mjs` 会在执行策略缺失时拦截并要求重新调用——**Skill 让忽略，校验工具不放行**，正是 `AGENTS.md` 原则 6 要求对齐的那类偏差，且落在最贵的阶段上。

同时，`full_generate` 是五个阶段里唯一**没有在工具清单声明"执行策略"工具**的（脚本 `get-execution-strategy.mjs` 存在，后台会在写手启动前自行调用一次）。正常路径能走通，但校验工具报出"执行策略已失效"时，模型没有可调用的恢复手段。

两处已按其余四个阶段的写法对齐，见 6.4。

## 5. 前后端契约裂缝

把第 3、4 节的发现按"信息在哪一层丢失"重排。共同特征是：**后端已经产出了正确的信息，它在传到用户眼前的路上被丢掉了**。这决定了工作量的性质——多数是接线，不是新建。

| 后端已有 | 丢在哪一层 | 用户实际看到 | 关联 |
| --- | --- | --- | --- |
| 每个响应的 `x-request-id` | 代理层 `proxyJson` 只复制 `content-type` | 无任何可对账的标识 | FM-21 |
| `error_code / error_category / error_retryable` | 前端类型定义里没有这三个字段 | 一句红字，没有重试入口 | FM-22 |
| 409 冲突判定 | 响应体只有一句话，不含服务端当前内容摘要 | "请刷新后再保存" | FM-10、T05 |
| 中文错误文案（331 条中 298 条） | 与英文文案、Pydantic 英文校验混在同一个 `detail` 字段里 | 中英文混杂 | FM-18、GATE-01 |
| 43 类执行事件 | 前端只识别 10 类，其余丢弃 | 通用话术反复轮换 | A-02、TA-04 |
| 结构化失败原因 | 与 `next_action` 不同源 | 模型被指向错误的修复对象 | FM-28 |

三处**形状不一致**，同一层的失败没有统一契约：

| 形状 | 出现场景 | 例子 |
| --- | --- | --- |
| `{"detail": "一句话"}` | 401 / 404 / 405 / 409 | `{"detail":"未找到项目"}` |
| `{"detail": [ {type, loc, msg, input}, … ]}` | 422 校验失败 | 带 `input` 回显（FM-17） |
| 空响应体 | 后端不可用时的代理层 500 | 无 content-type（FM-19） |

两处**判定不同源**，两侧各有一个常量：

| 事实 | 后端来源 | 前端来源 | 后果 |
| --- | --- | --- | --- |
| 会话有效期 | `config.py:15` `access_token_expire_minutes` | 登录路由的 `maxAge: 60*60*24*7` | 错位后出现"看起来登录着但什么都做不了"（FM-20） |
| 单集字数下限 | `screenplay-length.mjs` 按时长推导 | 审稿准入固定 240 字 | 同一平台两套标准（A-05） |
