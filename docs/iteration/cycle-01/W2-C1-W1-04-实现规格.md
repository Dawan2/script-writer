## 0. 前置裁定

### 0.1 失败路径实测

本槽在 `main` 与 `main + 02` 两个基线上逐个制造七种失效原因，直接调用 `current_user` 与登录接口取回真实结果。**本文所有错误码、文案与行号都取自这两次实测**。

| 场景 | `main @ abb779e` 给出的 | `main + 02 @ 58f1aaf` 给出的 | `code` | `category` |
| --- | --- | --- | --- | --- |
| 完全没带凭证 | `Not authenticated` | 还没有登录，暂时打不开这个内容。 | `AUTH_REQUIRED` | `auth` |
| **自然过期**（签名有效、`exp` 已过） | **`Invalid token`** | 登录状态已经到期。 | `SESSION_EXPIRED` | `auth` |
| 签名不对（令牌被改） | **`Invalid token`** | 登录状态无法识别。 | `SESSION_INVALID` | `auth` |
| 令牌不成形 | **`Invalid token`** | 登录状态无法识别。 | `SESSION_INVALID` | `auth` |
| 账号被停用 | `Inactive user` | 这个账号已经停用。 | `ACCOUNT_DISABLED` | **`permission`** |
| 别处改过密码（`auth_version` 前进） | `Session expired` | 这个账号在别处改过密码或被要求重新登录。 | `SESSION_SUPERSEDED` | `auth` |
| 登录时密码输错 | `Incorrect username or password` | 账号或密码不正确。 | `LOGIN_FAILED` | **`auth`** |

三条结论直接决定本包的范围：

1. **领取表验收第 1 条已由 02 全额兑现，且不止四条。** `main` 上最常见的自然过期与「令牌被改」共用一句 `Invalid token`，02 把它拆成 `SESSION_EXPIRED` 与 `SESSION_INVALID`，五个失效码全部带中文 `message` 与 `hint`。**本包不再中文化任何一条文案，只做防回退**（AT-01）。
2. **`ACCOUNT_DISABLED` 的 `category` 是 `permission` 而不是 `auth`**，因此 03 的钩子对停用账号不触发。这是对的——重新登录对停用账号没用——但它意味着停用账号必须走另一条路（§3 D2、勘误 E-04-2）。
3. **`LOGIN_FAILED` 的 `category` 是 `auth`**。03 的钩子按 `category === "auth"` 触发，于是「在登录面板里把密码打错」会触发会话拦截，等于在登录层上再开一层登录层。**本包必须按错误码白名单收窄，不能沿用 `category` 判定**（勘误 E-04-1）。

补一条实测：所有会话 401 都在 `dependencies.py` 的 `current_user` 里抛出（02 基线的 `:55`、`:59`、`:62`、`:65`），它是 FastAPI 依赖，**在路由处理函数之前执行**。全仓另外两处 401 是 `auth.py:31` 的 `LOGIN_FAILED` 与 `openclaw_api.py:52`（外部批量任务接口，走 HTTP 基本认证，`apps/web/src/app/api/` 下没有它的代理目录，浏览器到不了）。这条实测是 §3 D4「重放为什么安全」的全部依据。

### 0.2 本规格的边界

本规格只回答一件事：**会话在用户正在写东西的时候失效了，怎么让他原地登回来、刚才写的东西一个字不丢、也不会写进别人的账号**。不回答：错误横幅长什么样（`C1-W1-06`）、草稿怎么落盘与恢复（`C1-W1-01`）、长任务进度怎么算（`C1-W1-07`）、进展流断线怎么重连（`C1-W1-08`）、请求怎么发与什么时候停（`C1-W1-03`）、幂等键怎么生成（`C1-W1-09`）、离线态怎么表达（`C1-W1-12`）。逐项边界见 §9。

## 1. 问题事实（实测）

| 编号 | 事实 | 位置 | 后果 |
| --- | --- | --- | --- |
| F1 | 令牌 7 天硬过期，会话 cookie 的有效期也是 7 天，两者在同一次登录里一起写下 | `core/config.py:15`、`api/auth/login/route.ts` 的 `maxAge` | 冷启动时 cookie 与令牌一起消失，中间件能拦住；**危险的是标签页一直开着跨过那一刻**——cookie 还在，界面看着还登录着，每个请求都失败 |
| F2 | 会话 cookie 是 `httpOnly` | `lib/constants.ts:1`、`login/route.ts` | 浏览器脚本读不到令牌也读不到 `exp`，**失效只能由一次失败的请求发现**，不可能靠前端计时器预判 |
| F3 | 中间件只看 cookie 在不在，不看它还有效没有；跳转到 `/?login=1` 时把用户原来要去的地址丢掉 | `middleware.ts:11-16` | 令牌过期但 cookie 尚存时中间件一律放行；被拦下时登录后回不到原处 |
| F4 | 代理层只在 cookie 存在时才加 `Authorization` | `lib/server/backend.ts:23-25` | cookie 消失后后端收到的是「没带凭证」，即 `AUTH_REQUIRED` |
| F5 | 工作台有三个常驻轮询：额度 30 秒、通知 4 秒、评分卡 3 秒 | `workspace/page.tsx:1162`、`:1181`、`:1288` | 好消息：失效后最迟 4 秒就会被某个轮询撞出来。坏消息：**重新登录期间它们每 3–4 秒各发一次注定失败的请求** |
| F6 | 工作台的错误横幅 5 秒后自动清空 | `workspace/page.tsx:1318-1330` | 会话失效若走通用横幅，提示会自己消失，用户只剩一个什么都保存不了的界面 |
| F7 | 会话失效当前的处理是整页跳转，编辑器随之卸载 | `workspace/page.tsx:1155`（`getMe` 失败即 `location.href = "/login"`）、`preferences/page.tsx:187` | 这是「会话过期等于内容损失」的直接原因 |
| F8 | 管理台与批量任务是服务端组件，401 时 `redirect("/?login=1")` | `admin/page.tsx:8`、`batch-tasks/page.tsx:8` | 服务端渲染阶段没有浏览器侧闸门可用，只能靠回带原址补救 |
| F9 | 登录成功后一律 `window.location.href = "/workspace"`，不带项目与阶段 | `landing-page.tsx:680`、`:600` | 即便登录前在改某个阶段文件，登录后也只回到工作台首屏 |
| F10 | 地址栏只在「从通知跳转」这一条路径上写入 `project` / `stage`，普通切换项目不写 | `workspace/page.tsx:1073-1078` | 降级路径能回带的原址，多数时候只是一句 `/workspace` |
| F11 | 全仓 0 处 `BroadcastChannel`、0 处 `storage` 事件监听、0 处 `visibilitychange` | `apps/web/src` 全域 | 标签页之间没有任何互相知会的通路，登出后另一个标签页只能等下一次轮询失败 |
| F12 | 改密码会让 `auth_version` 前进，而改密码那一个标签页的 cookie 会被同步换新 | `services/auth_service.py:91`、`api/auth/change-password/route.ts` | **`SESSION_SUPERSEDED` 是本包最可能被真实触发的一条**：在偏好页改完密码，工作台标签页最迟 4 秒后开始全线失败，比等 7 天过期常见得多 |
| F13 | `/api/auth/session` 把 401 咽成 `{ user: null }` 加 200；`/api/auth/me` 用 `proxyJson`，401 原样透出 | `api/auth/session/route.ts:6-8`、`api/auth/me/route.ts` | `getSessionUser()` 永远不报错，不能当会话失效的探针；`getMe()` 会报错，是 F7 那条整页跳转的触发者 |

结论：本项的根因不是「缺一个重新登录界面」，而是**失效只能由失败的请求发现，而当前那次失败的处理方式是整页跳转**。因此改动面收在**一个新增的会话闸门 + 一个新增的重新登录层 + 请求核心的两个接入点**，工作台主文件零改动（判据见 §6 AT-13）。

## 3. 设计裁定

### D1 不卸载，就不需要「回到原处」

主路径一次导航都不发生：重新登录层是挂在根布局上的一层遮罩，React 树不动，编辑器实例不重建，草稿留在原本的状态里。领取表验收第 3 条「停留在原项目与原阶段文件」因此是构造上成立的，不靠任何位置记忆。

由此定下一条不变量：**会话失效路径上不允许出现整页跳转**。F7 的两行（`workspace/page.tsx:1155`、`preferences/page.tsx:187`）不需要删除——闸门在它们之前就把失败挡住了，它们的 `catch` 根本不会执行（D3）。这两个文件都是热点文件且本包不在其队列里，本包因此**不改它们一行**，判据用行为断言而不是检索（AT-13、勘误 E-04-6）。

降级路径只有一条：冷启动时 cookie 已消失，被中间件拦下。那种情况下这个标签页里没有正在编辑的内容，回带原址就够（D8）。

### D2 进闸门的是四个码，不是一个类别

| 错误码 | `category` | 进闸门 | 用户看到什么 |
| --- | --- | --- | --- |
| `SESSION_EXPIRED` | `auth` | 是 | 重新登录层，主路径 |
| `SESSION_INVALID` | `auth` | 是 | 重新登录层，同一套动作 |
| `SESSION_SUPERSEDED` | `auth` | 是 | 重新登录层，标题改成「别处改过密码」 |
| `AUTH_REQUIRED` | `auth` | 是 | 重新登录层（cookie 已消失，等价于失效） |
| `ACCOUNT_DISABLED` | `permission` | **否** | 交 `C1-W1-06` 呈现。重新登录对停用账号没有用，弹登录框是骗用户白填一次密码 |
| `LOGIN_FAILED` | `auth` | **否** | 留在登录表单里，就是当前的行为 |

**判定按错误码白名单，不按 `category`。** 03 的钩子以 `category === "auth"` 广播，落在它触发范围里的有五个码，其中 `LOGIN_FAILED` 必须排除、`ACCOUNT_DISABLED` 本来就不在（勘误 E-04-1、E-04-2）。本包不改 03 的钩子签名与触发条件，只在自己这一侧过滤。

停用账号有一条不能漏：用户可能正在编辑。**它虽然不进闸门，导出动作也必须可用**，否则「账号停用」变成一次内容损失。本包把导出做成闸门与 06 都能调用的独立动作（§5）。

### D3 闸门：挂起、单飞、按序重放

闸门有开合两态。合上之后：

| 情形 | 行为 |
| --- | --- |
| 已经在途、撞上失效码的请求 | **挂起**，promise 不结算，请求描述连同请求体一起留在队列里 |
| 闸门合上后新发起的请求 | **发出去之前就挂起**，一个注定失败的请求都不发（F5 的三个轮询会在重新登录期间发出几十个） |
| 读请求的挂起 | 按「方法 + 路径」去重，同一个键只留最后一个。轮询的旧结果没有意义 |
| 写请求的挂起 | 逐个保留，按发起顺序排队，不去重、不合并 |
| 请求体不可重放的（流式请求体） | 不挂起，直接以原失效码结束。全仓写请求的请求体都是 JSON 字符串或表单对象，都可重放；这条是防将来 |
| 重新登录成功且是同一账号 | 按原顺序逐个重发，请求头与请求体逐字不变 |
| 重新登录成功但换了账号 | 队列**不结算也不重发**，闸门进入「账号不匹配」终态（D6） |

**单飞是闸门自带的，不是额外机制**：闸门只有一个，第 2 个失效的请求看到它已经合上就直接入队，重新登录层只被打开一次（AT-05）。

**挂起期间不结算，顺带解掉一件事**：调用方那一大批「取 `error.message` 塞进错误状态」的兜底写法（03 规格 F12 记为 22 个文件共 114 处）在挂起期间根本不会执行，会话失效因此不会走通用横幅，F6 的 5 秒自动消失也影响不到它——领取表做法要点「401 单独成路径，不混入通用错误横幅」由此成立，不需要去改任何一个调用点。

### D4 重放为什么不会写重

03 的 D5 定得很硬：**写操作在任何情况下都不被请求核心自动重发，带幂等键也不重发**。本包的重放看着与它冲突，实为两件事：

| | 03 禁止的 | 本包做的 |
| --- | --- | --- |
| 触发 | 传输层失败、超时、网关 5xx | 会话 401 |
| 写有没有生效 | **不知道**。请求可能已经到达并执行 | **一定没生效**。§0.1 实测：五处会话 401 全在 `current_user` 依赖里，请求根本没进路由处理函数 |
| 因此 | 静默重发等于可能重复扣费、重复生成 | 重发是把一次被拒的请求重新递一次 |

两条规则并存，互不放宽：本包不碰 03 的传输层重试策略，AT-06 的第二项就是断言它没被放宽。

幂等键（`C1-W1-09`）在这里是安全带而不是承重件：重放沿用原请求对象，键值原样带回，`09` 未落地时该半条按「重放不产生第二个实体」实测判定（勘误 E-04-8）。

### D5 挂起的时间不算进预算

03 给每个请求发了预算：读 12 秒、写 45 秒、阶段保存 330 秒。一次重新登录轻易超过 45 秒。**如果挂起期间预算的计时器还在跑，被挂起的保存会在用户还在填密码的时候就以「等待太久已经中断」结束**，重放的对象直接没了。

因此定：**预算从请求真正发出的那一刻起算，挂起期间不计时。** 挂起的请求在重发时拿到一份全新的预算。这一条是本包与 03 之间唯一的行为耦合，缺它重放必然失败，判据是 AT-07。

### D6 属主校验：登回来的必须是同一个人

闸门记住「失效发生时活动的账号标识」——登录成功时与首次 `/auth/me` 成功时各写一次。重新登录成功后比对新的账号标识：

| 结果 | 行为 |
| --- | --- |
| 同一个账号 | 按 D3 重放，闸门打开，遮罩消失 |
| 换了账号 | 队列一个都不重发，闸门进入「账号不匹配」终态 |

「账号不匹配」终态下遮罩不消失，界面给三个动作，**在用户明确选择之前队列不结算**：

1. **导出内容**——把失效前的草稿写成一个文件下载，文件名带项目名与阶段名；
2. **用原来的账号登录**——回到登录表单再来一次；
3. **放弃这些修改并继续**——只有选这个，队列才以新增的客户端码 `SESSION_ACCOUNT_MISMATCH` 结算，随后整页刷新到工作台，让页面以新账号的身份重建。

第 3 个动作要用户明确点才发生，这条是为了 F7 那两行整页跳转：它们的 `catch` 只在队列结算后才可能执行，而那时用户已经拿到过导出机会。

`SESSION_ACCOUNT_MISMATCH` 的 `category` 取 `conflict`，**不取 `auth`**。取 `auth` 会让这个结算结果重新命中 03 的钩子，闸门刚给出终态就被自己重新合上。除了取值之外还加一条：闸门自己结算的失败不再走失败广播（双保险，AT-09）。

### D7 跨标签页：广播优先，存储事件兜底，轮询垫底

领取表验收第 6 条要的是「另一个标签页在下一次操作前即感知」。三条通路按可靠性排：

1. **`BroadcastChannel`**——登出、换号、会话恢复三个事件。同源标签页立即收到；
2. **存储事件**——广播不可用时改写一个约定键，靠 `storage` 事件跨页；
3. **轮询**——F5 的通知轮询 4 秒一次，两条通路都不可用时最迟 4 秒撞出来。

三条通路都收在一个薄模块后面，对外只有订阅与发布两个函数。**验收不依赖 `BroadcastChannel` 在 jsdom 里可用**：两条通路各一条用例，走的是模块接口（AT-11）。

登出会清掉同源共享的 cookie，所以另一个标签页的下一次请求本来也会失败；广播的价值是把「最迟 4 秒」变成「立刻」，并且能区分「这个账号退出了」和「令牌过期了」这两句不同的话。

### D8 降级路径：把原址带过去，并且只认站内地址

中间件被拦下时（F3）把原来的地址与查询串写进 `next`，登录成功后落到 `next` 而不是固定的 `/workspace`（F9）。服务端组件那两处 `redirect("/?login=1")`（F8）同样带上。

**`next` 必须校验**，否则这是一个开放跳转漏洞。三条判据全部满足才采用，任一不满足就落回 `/workspace`：以 `/` 开头、不以 `//` 开头、不落在 `/api/` 下（AT-12）。

工作台已经支持 `?project=&stage=` 深链（`page.tsx:1193-1194`），所以 `next=/workspace?project=12&stage=xxx` 不需要改工作台一行就能回到原处。但 F10 说明地址栏多数时候并没有这两个参数——**把项目与阶段写进地址栏要改 `page.tsx`，那是热点文件且队列里没有本包**，该项登记为余量，本包不做（勘误 E-04-6）。

### D9 登录面板抽出来共用，不复制一份

登录表单现在长在 `landing-page.tsx` 的落地页里（`:1094-1160` 的对话框），和落地页的状态绑在一起。抽成 `components/auth/login-panel.tsx`，落地页与重新登录层各用一次。**不复制第二份表单**——复制会让「账号或密码不正确」这类文案与无障碍行为在两处各自漂移。

抽取时保留 02 已经落地的行为：`handleLogin` 按 `LOGIN_FAILED` 分支，不再对错误文案做字符串匹配。面板的提交按钮文案由调用方给：落地页仍是「进入工作台」，重新登录层用「重新登录并继续」——**这一层不导航，说「进入工作台」是骗人**。

### D10 遮罩层的话按失效原因分，并且不显示服务端原文

| 场景 | 标题 | 正文 |
| --- | --- | --- |
| `SESSION_EXPIRED` / `AUTH_REQUIRED` | 登录状态已经到期 | 你刚才的修改都还在，重新登录后会接着保存。 |
| `SESSION_INVALID` | 登录状态无法识别 | 重新登录一次就能接着用，你刚才的修改都还在。 |
| `SESSION_SUPERSEDED` | 这个账号在别处改过密码 | 用新密码重新登录，刚才的修改都还在。 |
| 另一个标签页登出 | 这个账号已经退出登录 | 重新登录后可以接着用，这里的修改都还在。 |
| 账号不匹配 | 这些修改属于另一个账号 | 现在登录的是另一个账号。为了不把内容写错账号，刚才的修改没有保存。你可以先把它们导出，再用原来的账号登录。 |

遮罩层是阻断式的，没有关闭按钮，但**导出内容始终可用**——用户在任何时候都有办法把自己写的字留住。非阻断的常驻提示条形态属 `C1-W1-06`，本包不做。

无障碍按 `role="dialog"` 加 `aria-modal`，打开时焦点落在账号输入框，焦点不跑出遮罩。`role="alert"` 横幅是 06 的形态，本包不用。

02 落地后 `message` 与 `hint` 本身就是给用户看的中文，所以「不显示服务端原文」这条不是靠遮罩层过滤实现的，而是靠**表里这批话取代原文的位置**：遮罩层显示的是上表的话与注册表的 `hint`，不拼接 `error.message` 之外的任何东西，也不显示追踪号——追踪号属于失败详情，归 06。

### D11 新增一个客户端错误码，改一条 hint

| 改动 | 内容 |
| --- | --- |
| 新增 `client_codes.SESSION_ACCOUNT_MISMATCH` | `category: "conflict"`、`retryable: false`，中文 `message` 与 `hint` 各一条。改 `error_codes.json` 后运行 `npm run check:errors -- --write` 重新生成 `apps/web/src/lib/error-codes.ts`（该文件由生成器产出，不手改） |
| 改 `http_codes.SESSION_EXPIRED.hint` | 现值「重新登录一次就能接着用；正在编辑的内容请先复制备份。」本包落地后**后半句变成假话**：内容不需要用户手抄备份。改成不再要求用户自己备份的说法（勘误 E-04-3） |

注册表是 02 的持有文件，本包按接续持有改动。02 的用例只钉 `code` 不钉文案（`test_error_contract.py:412`），这条 hint 的改动不破坏 02 的任何验收；`check_error_registry.py` 对新码的要求是中文 `message` 与 `hint` 齐备、`category` 在八个取值内，两条都满足。

新码的界面文案在前端也要有一份镜像（03 规格 E-03-6 记下的手写常量问题），按 03 的 AT-11 同一套办法加一条逐字对比用例，不新造第二种防漂移手段。

## 10. 本规格登记的勘误

裁定 9.6 要求先登记再动手。以下八条均**不改上游文档正文**，编号用 `E-04-*`，与 `02` 的 `E-8…E-15`、`03` 的 `E-03-*`、`17` 的 `E-17-*`、`05` 的 `E-05-*` 不冲突。

| # | 内容 | 性质 |
| --- | --- | --- |
| E-04-1 | 03 规格 §5 接入位 3 把触发条件定为 `error.category === "auth"`。实测该类别下有五个码，其中 `LOGIN_FAILED`（`auth.py:31`）来自登录请求本身——按 `category` 判定会在用户于登录面板输错密码时再开一层登录层。**本包改按四码白名单判定，不改 03 的钩子签名与触发条件**（D2） | 阻塞验收 |
| E-04-2 | `ACCOUNT_DISABLED` 的 `category` 实测是 `permission` 而非 `auth`，因此 03 的钩子对停用账号不触发。这个取值是对的（重新登录对停用账号无用），但领取表验收第 1 条把它算进「401 的四种情形」，需明确它走 06 的呈现而不是本包的闸门；**且停用账号下用户仍在编辑的内容必须可导出**，否则这个例外变成一次内容损失（D2） | 高 |
| E-04-3 | `SESSION_EXPIRED` 的 `hint` 现为「重新登录一次就能接着用；正在编辑的内容请先复制备份。」本包落地后后半句变成假话。**本包改这一条 hint**；注册表是 02 的持有文件，按接续持有改动，02 的用例只钉 `code` 不钉文案（`test_error_contract.py:412`），不破坏其验收（D11） | 中 |
| E-04-4 | 领取表验收第 1 条「后端 401 的四种情形都返回带 `code` 的中文文案」已由 02 全额兑现且不止四条（§0.1 实测五个失效码）。本包对该条只做防回退。同条后半句「区分会话失效与账号不匹配」中的「账号不匹配」**不是后端 401**，而是重新登录成功后的前端裁定，需要新增一个客户端错误码（D6、D11） | 中，澄清归属 |
| E-04-5 | 领取表把 `C1-W1-01` 列为硬依赖并注明「草稿须已落盘，重放才有意义」。实测：主路径不卸载编辑器，草稿在 React 状态里就是完整的，01 只在「闸门打开期间用户主动刷新页面」这一条降级路径上必需。**本包据此把 01 从开工前置降为段乙前置**，段甲可在 03 交出请求核心后立即开工（§0.3、§2） | 中，解开排程 |
| E-04-6 | 领取表验收第 3 条「停留在原项目与原阶段文件」：主路径不导航即构造上成立；降级路径实测拿不到原位——地址栏只在「从通知跳转」一条路径上写入 `project` / `stage`（`page.tsx:1073-1078`），普通切换项目不写。本包补中间件的原址回带，**但不改 `page.tsx` 去补写地址栏**（热点文件，队列里没有本包），该项登记为余量（D8） | 中 |
| E-04-7 | 03 规格 D5 定「写操作在任何情况下都不被核心自动重发，带幂等键也不重发」，与本包的重放看似冲突。两者对象不同：03 禁止的是传输层失败后的重发（写有没有生效不知道），本包重放的是会话 401（实测五处会话 401 全在 `current_user` 依赖里，请求没进处理函数，写一定没生效）。**两条规则并存，AT-06 第二项是不放宽的防线**（D4） | 中，防误判 |
| E-04-8 | 领取表验收第 3 条要求「幂等键未变」，而幂等键由 `C1-W1-09` 生成。`09` 未落地时该半条没有对象可验。本包定：重放沿用原请求对象、键值原样带回，`09` 未落地时按「重放不产生第二个实体」实测判定（D4、AT-06） | 低 |
