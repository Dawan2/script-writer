## 3. 设计裁定

### D1 草稿层：一个新文件，键按「项目 + 阶段」，摘要存进值

新增 `apps/web/src/lib/stage-draft-store.ts`，是本包唯一的新增产品代码文件。

```ts
export type StageDraft = {
  content: string;
  baselineHash: string | null;
  updatedAt: string;
};

export function readDraft(projectId: number, stage: string): StageDraft | null;
export function writeDraft(projectId: number, stage: string, draft: StageDraft): boolean;
export function clearDraft(projectId: number, stage: string): void;
```

| 裁定 | 内容 |
| --- | --- |
| 存储键 | `orca-stage-draft:{projectId}:{stage}`。前缀沿用仓库既有约定（`orca-agent-transcript:`、`orca-workspace-…`） |
| **基线摘要不进键** | 上游写的是「键按项目 + 阶段 + 基线内容摘要划分」。摘要一旦进键，服务端内容变化后就再也检索不到这份草稿，领取表验收第 5 条（摘要不一致时明示并保住草稿）在结构上无法实现。摘要改存在值里的 `baselineHash`。见勘误 E-01-1 |
| 标签页 ID 不进键 | 沿用上游 D4 的原意：同一文档在两个标签页必须看到同一份草稿 |
| 摘要可空 | `content_hash` 是可选字段（F12）。服务端没给摘要时 `baselineHash` 为 `null`，此时只做「有未保存修改」的提示，不做「服务器已变化」的判定 |
| 存储介质 | `window.localStorage`。不引入 IndexedDB、不引入第三方存储库 |
| 写入时机 | `draft` 变化后 250ms 防抖写一次（与既有搜索防抖同量级）。三处必须同步补写一次再往下走，避免最后一次输入卡在防抖里：`beforeunload` 处理器内、切换阶段/项目之前、Agent 任务启动导致选中态跳转之前 |
| 写入失败 | `localStorage` 在隐私模式与配额耗尽时会抛异常。`writeDraft` 捕获后返回 `false`，**绝不向上抛**——编辑动作不能因为草稿存不下而中断。返回 `false` 时在文档区提示一次「这台设备暂时无法保留草稿，请及时保存」，同一阶段内不重复提示 |
| 清理时机 | 保存成功后清（`handleSave` 的成功分支）；用户主动「放弃修改」时清 |

**草稿层归本项，不推给后续。** `C1-W1-01` 是易用性 `T03` 与可靠性 `C1-IR-T04` 合并后的唯一领取单位（`W1-任务编号唯一裁定.md` 的编号表已把两套编号并到本项），`C1-IR-T04` 的范围里就写着「`apps/web/src/lib/`：新增草稿层」。后续四项都是**消费方**，不得各自再造一份：`C1-W1-04`（会话过期重放）、`C1-W1-10`（冲突三选一）、`C1-W1-12`（离线保住草稿）依赖本包交付的这三个函数；`C1-W1-18`（新建表单输入保留）自建表单侧的持久化，与本文件零交集（见 §5）。

| 动作 | 行为 |
| --- | --- |

### D4 五个入口挂守卫，内部流程不挂

守卫只拦**用户主动发起的离开动作**。做法是新增一层包装函数，原函数保持不变，内部调用继续走原函数。

| 入口 | 挂点 | 说明 |
| --- | --- | --- |
| 切阶段文件 | 文件栏 `onSelect`（`:2375`）改调 `requestSelectFile`，它在 `dirty` 时开弹窗、否则直接调 `handleSelectFile` | `handleSelectFile` 本身不加守卫，`:1596`（名称同步后重开文件）与 `:2032`（推进阶段后打开下一个文件）两处内部调用因此不受影响 |
| 切项目 | 项目栏 `onSelect`（`:2184`）与通知跳转 `handleNotificationSelect`（`:1074`）改调 `requestLoadProject` | `loadProject` 本身不加守卫，首屏加载（`:1206`）、深链（`:1201`）、删除后回落（`:1726`）、新建后打开（`:1786`）、取消新建后回落（`:1822`）五处内部调用不受影响 |
| 新建项目 | `handleStartCreateProject`（`:1794`）在 `dirty` 时先确认 | 它会 `setDocument(null)` + `setDraft("")`，是一条真实的覆盖路径 |
| 跨页跳转 | `app-nav.tsx` 的四条 `Link` 与头像菜单的「首页」`Link` | 见 D5 |
| 关标签 / 刷新 | `beforeunload` | 见 D6 |

**守卫必须排在设加载态之前**（`05` 规格 §5 的交接项）：`requestSelectFile` 与 `requestLoadProject` 在弹出确认之前不得调用 `setContentLoading`，用户选「取消」时界面不得闪一次加载态。判据是 AT-04。

- 用户选「保存后继续」或「放弃修改」后，由 `page.tsx` 用 `useRouter().push(href)` 完成跳转（`next/navigation`，仓库内 `login`、`admin`、`batch-tasks` 三页已在用）。

**为什么不用 `beforeunload` 覆盖跨页**：Next.js 的客户端路由切换不触发 `beforeunload`，只有关标签、刷新、跳外站才触发。两套机制各管一段，缺一不可。

### D6 `beforeunload` 只在脏态挂载

```ts
useEffect(() => {
  if (!dirty) return;
  const handler = (event: BeforeUnloadEvent) => {
    flushDraft();
    event.preventDefault();
    event.returnValue = "";
  };
  window.addEventListener("beforeunload", handler);
  return () => window.removeEventListener("beforeunload", handler);
}, [dirty, flushDraft]);
```

- `dirty` 为假时监听器根本不在，干净页面不会被拦（领取表验收第 2 条后半句）。
- 拦截文案由浏览器固定，前端给不了自定义文字，**不要试图传文案**，也不要在界面上解释这个弹窗。
- 先 `flushDraft()` 再拦截：即使用户选「离开」，草稿也已经落盘，下次进来还能恢复。

### D7 草稿恢复入口放在文档区，三种编辑器统一受益

打开某个阶段时，若 `readDraft()` 命中且草稿内容与服务端内容不同：`setDraft(草稿内容)`，并在文档区顶部渲染一条 `role="status"` 的提示条。

| 情形 | 文案 | 动作 |
| --- | --- | --- |
| `baselineHash` 与服务端 `content_hash` 一致，或摘要为空 | `这份文档有你未保存的修改，已经为你保留。` | `放弃修改` |
| 两者不一致 | `这份文档有你未保存的修改，已经为你保留。服务器上的内容在这期间发生了变化。` | `放弃修改` |

三条硬约束：**不自动丢弃草稿、不自动覆盖服务端、不自动保存**。「放弃修改」经二次确认（D3 的弹窗，此时只出「放弃修改」与「取消」两个动作），确认后 `clearDraft()` + `setDraft(document.content)`，提示条消失。

**提示条挂在 `page.tsx` 的文档区、编辑器组件之前，不挂在 `markdown-workspace.tsx` 里。** 上游把恢复入口写在 `markdown-workspace.tsx`，但文档区实际有三种编辑器：`novel_analysis` 走 `NovelAnalysisWorkspace`、`world_view` 走 `WorldViewWorkspace`、其余走 `MarkdownWorkspace`（`:2222-2296`）。挂在 `MarkdownWorkspace` 里会让前两个阶段「草稿存了但用户看不见」，比不存更糟。挂在 `page.tsx` 后，另外两个编辑器组件一行不改。见勘误 E-01-2。

渲染位置排在 `05` 定下的分支链之后：`05` 的顺序是一级加载 → 新建表单 → 二级加载 → 文档 → 空态，提示条落在「文档」这一支的内部顶端，**不改变 `05` 的分支顺序**，`05` 的 AT-04 与 AT-12 不回退。无障碍上，`05` 的加载态与本条提示条分属不同分支，不会同时播报。

### D8 后台刷新不再吃掉草稿

`refreshCurrentProject`（F7）刷新的通常就是用户正在看的那个阶段，`:1105` 的 `setDraft` 是一条真实的静默覆盖。改为：

- 目标阶段就是当前打开的阶段、且 `dirty` 为真：**更新 `document`，但不动 `draft`**。随后由 D7 的提示条按 `baselineHash` 与新的 `content_hash` 是否一致给出「服务器上的内容在这期间发生了变化」。
- 其余情况（不脏、或刷新的是别的阶段）：行为与现状完全一致。

`handleAgentJobStarted`（`:1117-1140`）是另一种情形：它会把选中态强制切到 Agent 的目标阶段。**这个切换行为本包不改**（属 Agent 面板的交互范围），本包只要求它在切走之前同步补写一次草稿（D1 的写入时机第三条），用户回到原阶段时由 D7 恢复。

这条不改任何轮询节奏、不新增加载态（`05` 的 F8/D1 明确后台刷新不进加载态，本包保持）。

### D9 保存状态两态常显，文案自己说清楚要手动保存

`markdown-workspace.tsx:1574-1579` 的条件从 `mode === "markdown" && !dirty && !saving` 改为 `!saving`，两种模式都显示，两种状态都显示：

| 状态 | 文案 |
| --- | --- |
| 无未保存修改 | `已保存` |
| 有未保存修改 | `有未保存的修改` |

### D10 「取消」补二次确认

`page.tsx` 三处 `onCancel={() => setDraft(document.content)}`（`:2235`、`:2249`、`:2272`）改为开 D3 的弹窗（「放弃修改」+「取消」两动作形态），确认后才 `clearDraft()` + 还原。确认逻辑全部留在 `page.tsx`，`novel-analysis-workspace.tsx` 与 `world-view-workspace.tsx` 因此一行不改。

`markdown-workspace.tsx:1535` 的 `handleCancelChanges` 需同步调整：现在它调完 `onCancel()` 就立刻 `setPreviewEditing(false)`，加了确认之后会变成「弹窗还没确认，编辑态已经退了」。改为把退出编辑态的动作交给 `dirty` 变化后的既有逻辑，`handleCancelChanges` 只负责调 `onCancel()`。

### D11 文案规则

- 弹窗与提示条一律用具体文件名（`StageFile.name` / `StageDocument.name`），如「《人物小传》有未保存的修改」；名称为空时退回「当前文档有未保存的修改」，不显示空书名号。
- 不在界面上显示阶段英文标识、存储键、摘要值、草稿时间戳等对用户无用的内容。
- 不出现「自动保存」「草稿已同步」这类会建立错误预期的说法——产品没有自动保存，也不做远端同步。
