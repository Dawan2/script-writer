## 0. 基线审查结论（重要前提）

截至本槽开工，仓库为空项目（仅 `README.md`）。因此不存在"对既有代码逐行审计"的对象；本文档执行的是**设计前置审查**：以 script-writer 的目标产品形态（AI 辅助脚本/剧本创作 Web 应用，含多步向导、长文档编辑、Agent 工具调用）为审查对象，逐维度识别风险、给出必须在首批代码中就位的可靠性机制，避免后续波次返工。

**产品形态假设**（若与 P1/其他槽的架构决策冲突，以先落地者为准，冲突项见 §5 阻塞）：

- A1：Web 前端（React/Next.js 一类 SPA/SSR 混合），有登录态。
- A2：后端提供 REST/RPC 风格 API + LLM Agent 编排服务（Agent 会调用工具：检索、大纲生成、分幕改写等）。
- A3：核心对象是"项目 → 脚本文档 → 幕/场/节拍"层级结构；存在多步创建向导（题材 → 大纲 → 角色 → 初稿）。
- A4：单用户为主，但同一用户可能多标签页/多设备同时打开同一文档；真正的多人实时协作放到后续波次。

## 1. 十二维度风险审查与设计裁决

每个维度给出：风险场景（针对本产品）→ 设计裁决（首批代码必须遵守）→ 对应任务。

### 1.1 竞态（Race Conditions）

**风险场景**

- R1：用户快速连续点击"生成大纲"，两个生成请求并发返回，后发先至覆盖新结果（响应乱序）。
- R2：自动保存定时器与用户手动保存并发，旧快照覆盖新内容。
- R3：向导中"上一步/下一步"快速切换时，上一步的异步校验回来后写坏当前步的状态。
- R4：多标签页同时写同一文档的本地草稿键。

**设计裁决**

- D1（请求序号护栏）：所有"读后写 UI"的异步请求必须携带单调递增的 `requestSeq`，响应落地时丢弃 `seq < latestSeq` 的结果；由统一请求层实现，不允许各组件手写。
- D2（in-flight 去重与替换）：同一逻辑操作（如"保存文档 X"）在途时，新请求要么合并（保存类：取消旧的、发最新快照），要么拒绝（提交类：按钮进入 pending 并禁用）。策略在 API 客户端按操作类型声明，不靠 UI 记得禁用按钮。
- D3（写路径串行化）：对同一文档的写操作在客户端经过单一串行队列（per-document mutation queue），队列内按序发送，天然消除 R2/R3。
- D4（本地存储键含标签页会话 ID + 文档版本）：草稿键为 `draft:{docId}:{fieldVersion}`，写入用 `navigator.locks`（或降级为时间戳比较）防多标签互踩。

**对应任务**：W1-P2-T01、T03、T04。

### 1.2 幂等（Idempotency）

**风险场景**

- 网络超时后重试"创建项目"，产生重复项目；重试"扣减配额/发起生成"，重复扣费或重复生成。

**设计裁决**

- D5（客户端幂等键）：所有非只读请求（POST/PUT/PATCH/DELETE 及 Agent 触发）必须携带客户端生成的 `Idempotency-Key`（UUIDv7，创建于用户意图产生时刻而非请求发出时刻，重试沿用同一键）。
- D6（服务端去重表）：服务端以 `(user_id, idempotency_key)` 唯一索引落库，命中时返回首次执行的持久化响应（不重新执行）；键保留 ≥24h。执行中收到同键请求返回 409/`in_progress`，客户端转入轮询。
- D7（天然幂等优先）：能用 PUT-by-client-generated-id 表达的创建（如草稿、向导会话）直接用客户端生成 ID + upsert，减少对去重表的依赖。

**对应任务**：W1-P2-T02。

### 1.3 错误恢复（Error Recovery）

**风险场景**

- 生成中途失败后用户只能刷新页面；错误信息是原始堆栈或 "Something went wrong"，用户不知道内容是否已保存、能否重试。

**设计裁决**

- D8（错误分类学）：统一错误信封 `{ code, category, retryable, userMessage, correlationId }`。category ∈ {`network`, `timeout`, `validation`, `conflict`, `auth`, `quota`, `agent_tool`, `server`}。前端根据 `retryable` 与 category 决定 UI：可重试的展示"重试"按钮并保留用户输入；不可重试的给出明确下一步。
- D9（恢复点不丢输入）：任何失败路径都不允许清空用户已输入/已生成内容；失败后的表单/编辑器状态必须与失败前一致。
- D10（correlationId 贯穿）：客户端为每个用户意图生成 correlationId，透传到后端与 Agent 步骤日志，用户可在错误提示中复制该 ID。

**对应任务**：W1-P2-T01、T05（错误 UX 部分）。

### 1.4 超时（Timeouts）

**风险场景**

- LLM 生成可能 30–120s；普通 CRUD 应在 2s 内。无分级超时会导致：短请求挂死 UI，长请求被过早掐断。

**设计裁决**

- D11（分级超时预算）：请求层按操作类型声明超时——CRUD 读 8s / CRUD 写 15s / 上传按体积 / Agent 生成不用同步 HTTP 长连接扛（见 D12）。所有 fetch 必须绑定 `AbortSignal.timeout(...)` 与组件卸载信号的组合（`AbortSignal.any`）。
- D12（长任务异步化）：任何预期 >15s 的操作（生成、批量改写）走"提交任务 → 立即返回 taskId → SSE/轮询取进展"的异步任务模型，杜绝依赖单个长 HTTP 请求的可靠性。
- D13（服务端逐跳超时）：网关 → 应用 → LLM/工具调用逐层设置递减超时，内层超时必须小于外层，避免外层已放弃而内层仍在烧钱。

**对应任务**：W1-P2-T01、T07。

### 1.5 重试（Retries）

**风险场景**

- 无差别重试放大故障（重试风暴）；对非幂等操作重试造成重复副作用；重试次数/间隔散落各处不可审计。

**设计裁决**

- D14（统一重试策略表）：仅在请求层做自动重试。默认：网络错误/408/429/5xx 且请求幂等（GET 或带幂等键的写）→ 指数退避 + 全抖动（base 500ms，倍率 2，上限 8s，最多 3 次）；429/503 优先遵循 `Retry-After`。400/401/403/404/409/422 一律不自动重试。
- D15（重试与幂等键绑定）：自动重试必须复用原幂等键；用户手动点"重试"同样复用（意图未变），只有用户修改了输入才换新键。
- D16（重试可观测）：每次重试打点（次数、原因、最终结果），CI 中的故障注入测试断言重试行为符合策略表。

**对应任务**：W1-P2-T01、T02、T10。

### 1.6 部分失败（Partial Failure）

**风险场景**

- "为 10 场戏批量生成对白"：第 6 场失败，前 5 场结果丢弃或用户不知道哪些成功；多步写（建项目 + 建默认文档 + 初始化向导会话）中途失败留下半成品数据。

**设计裁决**

- D17（批量操作逐项结果）：批量 API 返回 `{ succeeded: [...], failed: [{id, error}] }`，HTTP 207 语义；UI 保留成功项、仅对失败项提供"重试失败项"。
- D18（多步写用 Saga/Outbox 而非分布式事务）：跨资源写在服务端编排为可补偿步骤，或单库内用事务 + outbox；任何"半成品"状态必须能被后台清扫任务识别与回收。
- D19（前端呈现部分成功为一等状态）：设计系统中定义 partial-success 的 Toast/列表态，禁止把部分成功笼统报成"失败"。

**对应任务**：W1-P2-T08。

### 1.7 表单/向导中断（Form & Wizard Interruption）

**风险场景**

- 四步创建向导进行到第 3 步时刷新/断网/关标签页，全部作废；移动端切后台被杀进程。

**设计裁决**

- D20（向导即服务端会话）：向导状态建模为服务端资源 `wizard_session`（客户端生成 ID，upsert，见 D7），每步完成即持久化；刷新/换设备后可从 `GET /wizard-sessions?status=active` 恢复并提示"继续上次创建"。
- D21（本地毫秒级 + 远端秒级双写）：本地 IndexedDB 即时写（每次输入防抖 300ms），远端 5s 节流同步；恢复时取 `max(local.updatedAt, remote.updatedAt)` 并在差异大时让用户选择。
- D22（步骤前进校验、后退不丢）：后退不清空已填数据；校验失败停留原步并保留输入（呼应 D9）。

**对应任务**：W1-P2-T04。

### 1.8 会话一致性（Session Consistency）

**风险场景**

- Token 过期时正在编辑，保存请求 401，用户被踢到登录页且丢稿；多标签页一处登出另一处仍显示登录态；登录用户 A 后在另一标签切到用户 B，A 标签页把内容写进 B 的账户。

**设计裁决**

- D23（静默续期 + 单飞刷新）：401 触发 token 刷新，刷新请求全局单飞（single-flight），期间其他请求排队；刷新成功后原请求原样重放（含原幂等键）；刷新失败进入 D24。
- D24（登录墙不丢稿）：会话不可恢复时，弹出内嵌重新登录层（不整页跳转），编辑器内容保留在内存 + 本地草稿；重新登录后校验"当前用户 == 内容属主"，不一致则阻断写入并引导导出。
- D25（多标签页会话广播）：登录/登出/换号事件经 `BroadcastChannel` 广播，各标签页立即对齐会话态；每个写请求携带发起时的 `sessionEpoch`，服务端拒绝陈旧 epoch 的写。

**对应任务**：W1-P2-T06。

### 1.9 乐观更新回滚（Optimistic Update Rollback）

**风险场景**

- 重命名场景标题乐观生效，服务端 422 后 UI 与服务端不一致；连续两次乐观更新，第一次失败回滚时把第二次的成果也滚掉。

**设计裁决**

- D26（乐观更新白名单）：仅低风险、可精确逆操作的变更允许乐观（重命名、排序、开关类）；生成类、结构性删除、配额相关一律 pending 态。
- D27（基于服务端快照回滚，而非逆操作叠加）：回滚实现为"用失败时刻的服务端权威快照重放未确认队列"（React Query 的 rollback + 队列重放模式），避免逆操作在并发下的错序。
- D28（回滚必须可见）：回滚伴随明确 UI 通知（"重命名未保存：<原因>"），禁止静默还原。

**对应任务**：W1-P2-T03。

### 1.10 网络失败（Network Failure）

**风险场景**

- 弱网/断网下用户继续打字，保存静默失败十分钟后才发现；`navigator.onLine` 假阳性。

**设计裁决**

- D29（连接状态以真实探测为准）：连接指示器状态机 `online / degraded / offline`，由实际请求成败 + 心跳探测驱动，`navigator.onLine` 仅作提示信号。
- D30（写入 Outbox 队列）：断网期间的写操作进入本地 outbox（IndexedDB 持久化，含幂等键），恢复后按序重放；重放冲突走 §1.11 的冲突流程。
- D31（保存状态可见）：编辑器常驻保存指示器（已保存 / 保存中 / 未保存·离线 / 保存失败），任何未持久化状态离开页面时触发挽留提示。

**对应任务**：W1-P2-T09。

### 1.11 并发编辑（Concurrent Editing）

**风险场景**

- 同一用户两个标签页编辑同一文档互相覆盖（丢失更新）；W1 不做多人协作，但数据模型若不留版本字段，后续 CRDT 改造要动存储层。

**设计裁决**

- D32（版本前置条件写）：文档及其子资源全部带 `version`（单调整数）；写请求带 `If-Match: version`，不匹配返回 409 + 服务端当前内容摘要。
- D33（409 冲突 UX 三选一）：收到 409 时提供"以我的覆盖 / 采用远端 / 并排对比手动合并"，默认不自动覆盖；同用户多标签页场景优先经 BroadcastChannel 做标签间软锁提示（"该文档正在另一标签页编辑"）。
- D34（为协作预留）：内容存储按块（场/节拍）分片、每块独立 version，而非整文档一个 blob——这使后续波次引入 CRDT/OT 时不需要迁移存储模型（详见 §4 规格 S1）。

**对应任务**：W1-P2-T05。

### 1.12 Agent 工具调用失败路径（Agent Tool-Call Failure Paths）

**风险场景**

- Agent 多步运行（检索 → 大纲 → 逐场生成）第 4 步工具超时，整个 run 报废且不可续跑；工具返回畸形 JSON 使编排器崩溃；用户中途关页面，run 的结果无处安放；同一 run 被重复触发。

**设计裁决**

- D35（Run 与 Step 持久化状态机）：Agent 运行建模为持久化的 `run(id, status, steps[])`，status ∈ {queued, running, awaiting_tool, step_failed, paused, succeeded, failed, cancelled}；每个 step 落库输入/输出/错误，run 与页面生命周期解耦（关页面不影响 run，回来能取到结果）。
- D36（工具调用防御边界）：每个工具调用有独立超时与重试策略（幂等工具可自动重试 ≤2 次）；工具输出经 schema 校验，校验失败视为该步失败并把原始输出存证，不允许畸形数据流入下一步。
- D37（步级失败 ≠ run 级失败）：可选步失败可跳过（记录降级）；关键步失败使 run 进入 `step_failed`，支持"从失败步重试"而非整 run 重跑（上游已成功步骤的输出复用）。
- D38（run 触发幂等 + 并发上限）：触发 run 走幂等键（D5）；同一文档同类型 run 并发数为 1，重复触发返回在途 run 的 ID。
- D39（进展流可恢复）：进展经 SSE 推送，事件带单调 `eventSeq`；断线重连用 `Last-Event-ID` 续传，不重复不丢失。

**对应任务**：W1-P2-T07。

## 2. 架构方案（分层）

```
┌─────────────────────────────────────────────────────────┐
│ UX 层：保存指示器 / 冲突对话框 / 部分成功呈现 / 重试按钮      │
├─────────────────────────────────────────────────────────┤
│ 状态层：per-doc 写队列 · 乐观更新+快照回滚 · outbox ·        │
│         wizard_session · BroadcastChannel 会话/标签协调    │
├─────────────────────────────────────────────────────────┤
│ 请求层（唯一网络出口）：requestSeq 护栏 · 幂等键 · 分级超时   │
│   · 统一重试策略表 · AbortSignal 组合 · 错误信封解析 ·       │
│   · 401 单飞刷新重放 · correlationId 注入                  │
├─────────────────────────────────────────────────────────┤
│ 服务端：幂等去重表 · If-Match 版本写 · 批量 207 ·            │
│   Saga/Outbox · Agent run/step 状态机 · SSE(Last-Event-ID) │
└─────────────────────────────────────────────────────────┘
```

**核心原则**

1. **可靠性机制集中在两处**：客户端"请求层"与服务端"写路径中间件"。业务组件与业务 handler 不允许自带 fetch/重试/超时逻辑（Lint 规则强制，见 T10）。
2. **一切写操作三件套**：幂等键 + 版本前置条件 + 结构化错误信封。首批 API 即遵守，避免后补。
3. **长任务一律异步化**（D12）：同步 HTTP 只承载 <15s 的操作。
4. **本地持久化是恢复手段而非事实源**：服务端为权威，本地 IndexedDB 承担草稿/outbox/恢复，冲突时用户可见可选。
5. **可核验**：每条机制都有对应的故障注入测试（T10），验收不接受"人肉试了一下"。

### 任务明细

#### W1-P2-T01 统一请求层

- **目标**：提供全项目唯一网络出口模块，内建分级超时（D11）、重试策略表（D14）、AbortSignal 组合取消、requestSeq 乱序丢弃（D1）、in-flight 合并/拒绝（D2）、错误信封解析（D8）、correlationId 注入（D10）。
- **范围**：前端 `src/lib/api/` 模块 + 类型定义；不含具体业务端点。
- **验收**：
  1. 单测覆盖：超时触发 abort；仅幂等请求自动重试且退避间隔符合策略表；429 遵循 Retry-After；乱序响应被丢弃；组件卸载时在途请求被取消。
  2. 非法用法（组件内裸 fetch）被 Lint 拦截（与 T10 联动）。
- **证据类型**：单元测试（含 fake timers 的退避断言）+ CI 通过记录 + Lint 规则演示。
- **依赖**：P1 项目脚手架。

#### W1-P2-T02 幂等键端到端

- **目标**：所有变更请求携带幂等键（D5），服务端去重表保证同键不重复执行（D6），可 upsert 的创建改为客户端 ID（D7）。
- **范围**：请求层拦截器 + 服务端中间件 + 去重表 schema + 首批写端点接入。
- **验收**：
  1. 集成测试：同键并发 2 个创建请求，仅产生 1 条记录，两响应体一致；执行中同键请求得到 `in_progress`。
  2. 断网重试场景 e2e：模拟响应丢失后客户端重试，服务端不重复创建。
- **证据类型**：集成测试 + e2e（网络故障注入）+ CI 记录。
- **依赖**：T01、服务端脚手架。

#### W1-P2-T03 乐观更新与快照回滚

- **目标**：实现白名单式乐观更新（D26）、服务端快照回滚 + 未确认队列重放（D27）、回滚可见通知（D28）、per-doc 写队列（D3）。
- **范围**：状态层 mutation 框架（基于所选数据层，如 React Query 自定义封装）。
- **验收**：
  1. 竞态测试：连续两次乐观更新、第一次失败，第二次成果不被误滚。
  2. 快速连点保存仅产生一次有效写（合并策略）。
- **证据类型**:竞态单测（可控 Promise 时序）+ 交互录屏。
- **依赖**：T01。

#### W1-P2-T04 向导会话持久化与中断恢复

- **目标**：向导状态服务端化（D20）、本地/远端双写（D21）、后退不丢数据（D22）。
- **范围**：`wizard_session` 资源（API + 存储）+ 向导框架组件 + 恢复入口 UI。
- **验收**：
  1. e2e：第 3 步刷新页面 → 提示恢复 → 数据完整；断网下填写 → 恢复网络 → 数据同步。
  2. 双端时间戳冲突时出现选择 UI。
- **证据类型**：e2e（含 offline 模拟）+ 录屏。
- **依赖**：T01、T02。

#### W1-P2-T05 版本化写与 409 冲突 UX

- **目标**：全部文档写带 `If-Match`（D32），409 时提供三选一冲突 UX（D33），存储按块分片留 CRDT 余地（D34）。
- **范围**：服务端版本校验中间件 + 前端冲突对话框 + 内容分块存储 schema。
- **验收**：
  1. 集成测试：陈旧版本写被 409 拒绝并返回远端摘要。
  2. e2e：双标签页编辑同一场景 → 后写方看到冲突对话框，三个选项行为各自正确。
- **证据类型**：集成测试 + 双标签 e2e 录屏。
- **依赖**：T01。

#### W1-P2-T06 会话一致性

- **目标**：401 单飞刷新与原样重放（D23）、不丢稿登录墙与属主校验（D24）、多标签会话广播 + sessionEpoch（D25）。
- **范围**：请求层认证拦截器 + 会话广播模块 + 内嵌登录层组件 + 服务端 epoch 校验。
- **验收**：
  1. 单测：并发 5 个 401 仅触发 1 次刷新，全部重放成功且幂等键不变。
  2. e2e：编辑中 token 失效 → 重新登录 → 草稿仍在且成功保存；标签 A 登出后标签 B 的写被拒。
- **证据类型**：单测 + e2e 录屏。
- **依赖**：T01。

#### W1-P2-T07 Agent run/step 状态机与失败路径

- **目标**：run/step 持久化状态机（D35）、工具调用防御边界（D36）、步级重试续跑（D37）、触发幂等与并发上限（D38）、SSE 断线续传（D39）。
- **范围**：服务端 run 编排存储与 API + 前端 run 进展面板 + SSE 客户端。
- **验收**：
  1. 集成测试：注入第 N 步工具超时 → run 进入 step_failed → 从失败步重试成功，前序步骤未重复执行（以工具调用计数断言）。
  2. 集成测试：工具返回畸形 JSON → 该步失败、原始输出存证、编排器进程不崩。
  3. e2e：run 进行中关闭页面，重新打开后进展与结果完整；SSE 断线重连不丢事件（eventSeq 连续）。
  4. 并发触发同类型 run 返回在途 run ID，未新建。
- **证据类型**：故障注入集成测试 + e2e 录屏 + 事件序列日志。
- **依赖**：T01、T02、Agent 编排基础（其他槽产出）。

#### W1-P2-T08 批量部分失败协议与 Saga 清扫

- **目标**：批量端点 207 逐项结果（D17）、多步写 Saga/Outbox 化（D18）、半成品后台清扫、前端部分成功一等呈现（D19）。
- **范围**：批量 API 约定 + 服务端编排 + 清扫任务 + 前端"重试失败项" UI。
- **验收**：
  1. 集成测试：10 项批量中注入 3 项失败 → 响应逐项准确；重试仅重发失败 3 项（幂等键复用）。
  2. 多步创建在第 2 步注入崩溃 → 清扫任务在阈值时间内回收半成品。
- **证据类型**：故障注入集成测试 + 清扫日志。
- **依赖**：服务端脚手架。

#### W1-P2-T09 离线检测、Outbox 与保存指示器

- **目标**：三态连接状态机（D29）、持久化 outbox 重放（D30）、常驻保存指示器与离开挽留（D31）。
- **范围**：连接监测模块 + IndexedDB outbox + 编辑器指示器组件。
- **验收**：
  1. e2e（offline 模拟）：断网编辑 → 指示器转"未保存·离线" → 恢复网络自动重放 → 服务端数据与本地一致。
  2. outbox 重放遇 409 走 T05 冲突流程而非静默覆盖。
- **证据类型**：e2e 录屏 + outbox 内容快照。
- **依赖**：T01、T03（重放冲突还依赖 T05 的冲突 UX）。

#### W1-P2-T10 可靠性测试设施

- **目标**：让上述所有验收可以在 CI 中自动执行：HTTP 故障注入代理（延迟/丢包/5xx/超时/畸形响应）、可控时序竞态测试工具、e2e offline/throttle 预设、"禁止裸 fetch/自带重试" Lint 规则。
- **范围**：测试基础设施包 + CI 配置 + Lint 插件配置。
- **验收**：
  1. 故障注入可通过测试内 API 按端点/次数编程控制。
  2. Lint 规则对违例代码 CI 报错（附反例演示）。
  3. T01 的全部验收用例跑在该设施上。
- **证据类型**：CI 配置与通过记录 + 反例 Lint 输出。
- **依赖**：T01（同步启动，互相验证）。

## 4. 后续波次功能规格（本槽只出规格，不实现）

### S1：多人实时协作编辑（建议 W4+）

- **目标**：同一脚本文档多人同时编辑，字符级合并，无锁。
- **方案要点**：在 D34 的分块存储上引入 CRDT（Yjs 一类），每块一个 CRDT 文档；服务端做 awareness（在线光标）与更新中继 + 定期快照压缩；权威快照仍落主库，保持与非协作路径（Agent 写入、版本化 REST 写）互通——Agent 产出以"协作参与者"身份写入 CRDT 而非绕过。
- **验收草案**：双客户端并发插入/删除收敛一致（property-based 收敛测试）；断线 5 分钟后重连自动合并；快照回放与 CRDT 状态一致。
- **依赖**：T05（分块 + 版本模型）、T07（Agent 写入路径）。
- **风险**：CRDT 文档体积增长需压缩策略；与幂等键/If-Match 模型的边界要在设计评审中裁决（协作块内不再走 If-Match）。

### S2：Agent 长任务断点续跑与结果暂存箱（建议 W3–W4，与 T07 衔接）

- **目标**：用户可暂停/恢复/取消 run；run 产出进入"暂存箱"（staging），用户逐项采纳/拒绝进正文，拒绝可撤销。
- **方案要点**：在 T07 状态机上加 `paused` 语义与用户审阅态；产出以 proposal 对象存储（引用目标块 + 补丁），采纳即对目标块执行版本化写（复用 T05），天然获得冲突处理。
- **验收草案**：暂停后 24h 恢复可续跑；采纳补丁遇正文已变化时走冲突 UX；全链路无"采纳成功但正文未变"或反之。
- **依赖**：T05、T07。

### S3：离线优先创作模式（建议 W5+）

- **目标**：地铁/飞行场景完整离线编辑，回线自动同步。
- **方案要点**：T09 的 outbox 升级为全量本地副本（Service Worker + IndexedDB 镜像），同步协议基于每块 version 向量；只对纯文本编辑开放，Agent 功能离线降级隐藏。
- **验收草案**：完全断网冷启动可打开最近 10 个文档并编辑；72h 离线修改回线同步成功率 100%（冲突走 UX，不静默丢）。
- **依赖**：T05、T09、S1（若已上 CRDT 则同步协议改走 CRDT）。
