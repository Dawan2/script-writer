## 1. 设计前提与总体原则

### 1.1 前提（来自基线，不重复论证）

1. 空仓：无代码、无依赖清单、无测试、无 CI。
2. 技术栈未选型（BLK-W1-01）、模型供应商与凭据未定（BLK-W1-02）、无 CI（BLK-W1-03）。
3. C 维度升级验收口径已定：L1 = 模型调用模块入库 + 一次真实调用脱敏记录（GOAL-W1-03）；
   L2 = 提示词工程化 + 输出格式受控 + 失败兜底；L3 = 结合剧本上下文（人物/情节/前文）产出连贯建议 + 抽检记录。

### 1.2 总体原则（后续实现波次必须遵守）

| 编号 | 原则 | 含义 |
|------|------|------|
| P-1 | 证据优先 | 每个智能化模块从第一版起就产出可存档的运行证据（对应 E4/E5），否则 W5 无法核验 |
| P-2 | 输出受控 | 模型输出一律经 schema 校验后才进入业务逻辑；不受控输出只能作为"草稿"呈现给用户 |
| P-3 | 草稿不覆盖 | Agent 对剧本正文的一切写操作先落草稿+差异预览，用户采纳后才生效；杜绝静默覆盖用户内容 |
| P-4 | 栈中立契约 | 本文以目录结构、数据 schema、接口语义为契约；文件扩展名与具体语言由实现波次按选型结果确定 |
| P-5 | 预算显式 | 每次 Agent 运行有显式步数/Token/时长预算，超限即停并保留断点，不允许无界循环 |
| P-6 | 一次一级 | 实现顺序严格对齐量表：先满足 L1 再做 L2 的事，禁止跳级堆功能 |

## 2. 八个子系统设计

### 2.1 工具描述（Tool Registry）

**职责**：向模型声明"它能对剧本做什么"，并在执行前拦截非法调用。工具描述质量直接决定模型调用的准确率，因此描述本身按代码同等标准管理（评审、版本化）。

**工具描述 schema**（每个工具一份，机器可读，单一事实来源，供运行时与文档双向生成）：

```json
{
  "name": "read_scene",
  "version": "1",
  "description": "读取指定场号的场景全文与元数据。用于改写/续写前获取权威原文。",
  "params": {
    "scene_id": {"type": "string", "required": true, "desc": "场号，如 'S12'"}
  },
  "returns": {"type": "object", "schema_ref": "prompts/schemas/scene.json"},
  "side_effect": "none",
  "preconditions": ["剧本已存在且包含该场号"],
  "failure_modes": ["SCENE_NOT_FOUND"],
  "cost_hint": "cheap"
}
```

强制字段规则：

- `side_effect` 枚举 `none | draft_write | destructive`。`destructive` 工具第一波**不提供**；一切写操作都以 `draft_write`（生成草稿）实现，落实原则 P-3。
- `description` 必须写"何时该用"，不只写"是什么"；每个失败码在 `failure_modes` 中枚举，供自修复层（§2.4）映射策略。
- 注册表加载时校验 schema 合法性，非法工具直接拒载（fail fast）。

**首批工具清单**（按实现优先级排序）：

| 工具 | side_effect | 用途 | 优先级 |
|------|-------------|------|--------|
| `read_scene` | none | 按场号读场景原文 | 第一批 |
| `list_scenes` | none | 列出分场结构（场号/地点/时间/一句话概要） | 第一批 |
| `get_bible_entry` | none | 读设定集条目（人物/地点/伏笔） | 第一批 |
| `write_scene_draft` | draft_write | 写入场景草稿并返回差异预览 | 第二批 |
| `upsert_bible_draft` | draft_write | 提议设定集条目变更（同样走草稿） | 第二批 |
| `search_script` | none | 关键词/人物名检索剧本正文 | 第二批 |
| `consistency_check` | none | 对指定范围跑一致性规则（§5 SPEC-P3-01） | 第三批 |
| `format_lint` | none | 剧本格式规范检查（场头/角色名/对白缩进等） | 第三批 |

### 2.2 规划分解（Planner）

**职责**：把用户目标拆成可执行、可核验的步骤序列，并在执行中允许基于新信息修订计划。

**计划数据结构**（运行时对象，同时全量落入 trace）：

```json
{
  "plan_id": "run-20260827-001",
  "goal": "把第12场从室内改到雨夜街头，保持情节功能不变",
  "budget": {"max_steps": 8, "max_llm_calls": 12, "max_tokens": 60000},
  "steps": [
    {"id": 1, "action": "tool:read_scene", "args": {"scene_id": "S12"}, "status": "done"},
    {"id": 2, "action": "tool:get_bible_entry", "args": {"entry": "李梅"}, "status": "done"},
    {"id": 3, "action": "skill:rewrite_scene", "depends_on": [1, 2], "status": "running"},
    {"id": 4, "action": "tool:consistency_check", "depends_on": [3], "status": "pending"},
    {"id": 5, "action": "human:review_draft", "depends_on": [4], "status": "pending"}
  ]
}
```

设计要点：

1. **两种生成方式**：预定义工作流（§2.6）直接实例化静态计划；开放请求由"规划技能"（一次受控 LLM 调用，输出符合 plan schema 的 JSON）生成，生成后经 schema 校验与工具存在性校验才可执行。
2. **步骤类型只有三种**：`tool:*`（确定性执行）、`skill:*`（一次受控 LLM 调用）、`human:*`（等待用户输入/确认，计划挂起可续跑）。
3. **修订规则**：只允许在步骤失败或新证据出现时"追加/替换未执行步骤"，已执行步骤与其产物不可篡改（trace 完整性）。修订次数计入预算。
4. **最小版本（L2 前）**：不做开放规划，只跑静态工作流；开放规划在 C 维度达 L2 后再引入（见 §4 实施顺序）。

### 2.3 记忆上下文（Memory & Context Assembler）

**职责**：解决剧本创作的核心痛点——模型上下文远小于整部剧本，且"人物设定、伏笔、前文事实"必须一致。

**四层记忆模型**：

| 层 | 内容 | 存储 | 写入方 | 生命周期 |
|----|------|------|--------|----------|
| M1 权威层 | 剧本正文（分场存储） | 剧本文件（P1 范围） | 仅用户采纳草稿后写入 | 永久 |
| M2 结构层 | 设定集 Story Bible：人物卡、地点、时间线、伏笔登记 | `story-bible/` 结构化文件（YAML/JSON） | 用户直接编辑 + Agent 草稿提议 | 永久 |
| M3 会话层 | 本次任务目标、澄清问答结果、已生成草稿引用 | 运行时状态 + trace | Orchestrator | 单次运行 |
| M4 偏好层 | 作者风格偏好（语言、节奏、忌讳） | `story-bible/preferences` | 用户编辑为主 | 永久 |

**Story Bible 人物卡最小 schema**（示例，完整 schema 由 TASK-P3-06 定稿）：

```yaml
id: li-mei
name: 李梅
role: 女主角
facts:                    # 不可违背的既定事实，一致性检查的依据
  - "左撇子"
  - "S03 起知晓父亲身份"
voice: "话少，句子短，习惯反问"
arc: "从回避冲突到主动对峙"
first_appearance: S02
```

**上下文组装器（Context Assembler）**：每次 `skill:*` 调用前按预算表拼装上下文，顺序与配额固定、可审计：

| 槽位 | 内容 | 预算占比（默认） |
|------|------|------------------|
| rules | 硬规则（§2.8） | 5% |
| skill | 技能模板 | 10% |
| bible | 相关设定集条目（按任务涉及的人物/地点检出） | 20% |
| script | 相关正文：目标场景全文 + 相邻场景概要 | 45% |
| session | 会话层：目标、澄清结果 | 10% |
| output_spec | 输出 schema 与格式要求 | 10% |

检索策略分两级演进：**v1 确定性检出**（按场号/人物名精确取，无向量检索，行为可预测、可测试）；v2 在正文规模超出确定性检出能力后再评估向量/摘要检索。组装结果（各槽位实际内容的引用与 token 数）写入 trace，保证"模型看到了什么"可复盘——这是 L3 验收（结合上下文产出连贯建议）的直接证据。

### 2.4 失败自修复（Repair Loop）

**职责**：把"模型/工具会失败"当作常态设计，每类失败有确定性的处置策略，杜绝无界重试。

**失败分类与策略表**（策略表本身是配置，落 `src/agent/orchestrator/repair-policy`）：

| 码 | 失败类型 | 检测方式 | 处置策略 | 上限 |
|----|----------|----------|----------|------|
| F1 | 输出格式不合规 | schema 校验失败 | 携带校验错误信息重试同一调用 | 2 次，仍失败则降级为"纯文本草稿+需人工确认"标记 |
| F2 | 工具参数非法 | 注册表前置校验 | 把校验错误反馈给模型重试 | 1 次，仍失败则该步骤置 `failed` 并触发计划修订 |
| F3 | 供应商错误/超时 | 网关捕获 HTTP/超时 | 指数退避重试；配置了备用模型则切换 | 3 次退避；切换 1 次 |
| F4 | 预算超限 | Orchestrator 计数 | 立即停止，输出已完成部分 + 断点句柄（可续跑） | 不重试 |
| F5 | 内容自检不过（一致性冲突/敏感内容） | `consistency_check` / 规则过滤 | 不自动改写，标注冲突点交人审 | 不重试 |

设计要点：

1. **修复动作也计入预算**（P-5），修复循环总次数受 `max_llm_calls` 硬顶约束。
2. 每次修复在 trace 中记录 `repair_event`（失败码、策略、结果），这是 L2 验收"失败调用有兜底"的直接证据，也是后续 E5 指标（兜底触发率）的数据源。
3. **兜底的最终形态永远是"把可用部分交给用户 + 明确说明失败原因"**，而不是静默吞错或返回空。

### 2.5 意图澄清（Clarifier）

**职责**：在执行前消除会导致返工或误操作的歧义；在"多问惹人烦"与"猜错更糟"之间用确定性规则取舍。

**触发规则**（按序判定，命中即触发）：

1. **必填槽位缺失**：技能声明的必填输入（如改写任务的 `scene_id`）无法从请求与会话层解析出来 → 必须澄清。
2. **破坏面大**：请求影响多场景或设定集条目（如"把男主改名"）→ 必须澄清确认范围。
3. **歧义评分**：规划技能输出 `ambiguity` 字段（模型自评 0–1 加显式歧义点列表），≥0.6 时澄清。

**澄清预算**：单次任务最多 2 个澄清问题、一轮往返。超出预算则采用**显式默认假设**继续执行，并把假设写进结果头部（"我假设你指第12场，如不对请指出"）——配合草稿机制（P-3），猜错的代价被限制在"丢弃草稿"。

**澄清问题的形态**：优先给选择题（枚举可能解释），其次才是开放问题；问题与答案都落 M3 会话层与 trace。

### 2.6 多步工作流（Workflow Engine）

**职责**：把高价值、步骤固定的创作流程固化为静态计划模板，用户一键发起，中途有人审节点。工作流引擎是 Planner 的特例（计划来自模板而非模型生成），因此**先于开放规划实现**，风险低、收益高。

**工作流模板 schema**：模板即 §2.2 计划结构去掉运行时字段，外加 `inputs` 声明（必填/可选槽位，供 Clarifier 校验）与 `human:*` 节点位置。

**首批工作流**：

| ID | 名称 | 步骤概要 | 对应规格 |
|----|------|----------|----------|
| WF-01 | Logline → 分场大纲 | logline 澄清 → 故事梗概（人审）→ 分幕结构（人审）→ 分场大纲草稿（人审采纳） | SPEC-P3-02 |
| WF-02 | 场景改写 | 澄清目标 → 组装上下文 → 草稿 → 一致性检查 → 差异预览（人审采纳） | SPEC-P3-03 |
| WF-03 | 一致性巡检 | 全本扫描 → 冲突报告 → 逐条修复建议（只报告不改写） | SPEC-P3-01 |

**断点续跑**：`human:*` 节点挂起时，计划状态序列化（含已产出草稿引用）；用户回复后从挂起步骤继续。挂起状态存于 M3 + trace，进程重启不丢。

### 2.7 可观测性（Observability）

**职责**：让每次 Agent 运行可复盘、可计量、可作为 W5 核验证据。观测不是附加件，是 L1 起步就要有的最小能力（GOAL-W1-03 的 E4 证据即来源于此）。

**Trace 结构**（JSONL，每行一个事件，按 `run_id` 聚合）：

```json
{"run_id": "run-20260827-001", "ts": "…", "kind": "llm_call",
 "skill": "rewrite_scene@2", "model": "…", "prompt_tokens": 4200,
 "completion_tokens": 800, "latency_ms": 3100, "finish_reason": "stop",
 "context_slots": {"bible": ["li-mei"], "script": ["S11#summary", "S12#full"]}}
```

事件类型：`run_start / run_end / plan_created / plan_revised / step_start / step_end / llm_call / tool_call / repair_event / clarify_event / human_gate`。

规则：

1. **脱敏**：API Key 等凭据永不落盘；剧本正文在 trace 中默认只存引用（场号+哈希），全文存档需显式开关（供调试）。对外归档（`docs/evidence/`）一律用脱敏摘要。
2. **成本与延迟**：每次 `llm_call` 记录 token 与延迟，按 `run_id` 汇总；这是 L4 验收（成本延迟受控）的数据基础，从第一天就采集、后期才达标。
3. **存放**：运行期写 `runs/*.jsonl`（gitignore）；作为核验证据时，把指定 run 的脱敏摘要固化到 `docs/evidence/`（衔接 BLK-W1-03 的 CI 归档方向）。

### 2.8 提示 / 技能 / 规则（Prompt Store）

**职责**：提示词按代码同等标准管理——版本化、可评审、可回溯到具体一次运行。

**三层结构**：

| 层 | 位置 | 性质 | 示例 |
|----|------|------|------|
| 规则 Rules | `prompts/rules/` | 硬约束，所有技能共享，不可被任务指令覆盖 | 输出语言、剧本格式规范、"不得虚构设定集之外的既定事实"、安全边界 |
| 技能 Skills | `prompts/skills/` | 可复用提示程序：一个技能=一类任务的模板+输入槽位+输出 schema 引用 | `rewrite_scene`、`generate_outline`、`plan_task` |
| 任务实例 | 运行时组装 | 用户请求+会话上下文填入技能槽位 | —— |

**技能文件格式**：Markdown + 元数据头：

```markdown
---
id: rewrite_scene
version: 2
inputs: {scene_id: required, instruction: required, tone: optional}
output_schema: prompts/schemas/scene-draft.json
---
（技能提示词正文，含槽位占位符 {{scene_full}} {{bible_entries}} {{instruction}} …）
```

规则与要求：

1. **版本显式**：技能改动必须递增 `version`；trace 中的 `skill: rewrite_scene@2` 使每次运行可精确回溯到提示词版本——这是"提示词工程化管理"（C-L2 准入条件）的核验证据。
2. **注册即校验**：加载时校验元数据完整、`output_schema` 存在、槽位与模板占位符一致。
3. **规则前置**：上下文组装固定把 rules 放最前（§2.3 槽位表），技能与任务实例不得声明与 rules 冲突的要求。

## 5. 重点智能化功能规格

以下三个功能是本方案判断"对创作体验改善最大"的智能化能力，各自成为后续实现波次的立项单元。规格只约定行为契约与验收，不含实现代码。

### SPEC-P3-01 设定集一致性守卫（Consistency Guard）

- **用户价值**：长剧本最常见的质量事故是前后矛盾（人物年龄、既定事实、时间线）。人工排查成本随篇幅超线性增长，是 Agent 相对人工优势最大的场景之一。
- **行为契约**：
  1. 输入：检查范围（全本 / 场号区间 / 单场草稿）。
  2. 过程：对范围内每场，抽取涉及的人物与事实断言，与 Story Bible `facts` 及更早场次的断言比对；比对结论由受控输出（冲突列表 schema）承载。
  3. 输出：冲突报告，每条含 `场号 / 冲突描述 / 依据（bible 条目或前文场号）/ 置信度 / 修复建议`。**只报告，不自动改写**（F5 策略）。
  4. 挂接点：独立发起（WF-03），或作为 WF-02 场景改写的自动后置步骤。
- **失败与兜底**：单场抽取失败跳过该场并在报告中标注"未检查"；整体失败按 F1/F3 策略处理，绝不输出"未发现冲突"的假阴性结论（未完成检查 ≠ 无冲突）。
- **验收标准（二值）**：构造含 ≥3 个已知矛盾的测试剧本，运行后报告命中全部预埋矛盾（E3/E4，记录存档）；对无矛盾文本不产生高置信度误报 >1 条。
- **依赖**：TASK-P3-05（工具）、TASK-P3-06（Story Bible）。

### SPEC-P3-02 Logline 到分场大纲的引导式工作流（WF-01）

- **用户价值**：从一句话创意到可动笔的分场大纲是新用户最大的"冷启动"障碍；引导式分步生成 + 每步人审，比一次性长输出可控且采纳率高。
- **行为契约**：
  1. 输入：logline（一句话故事前提）；可选：类型、篇幅、结构偏好（三幕/五幕等，缺省三幕）。
  2. 步骤：`澄清（≤2 问，按 §2.5 规则）→ 故事梗概草稿（人审：可改可重生成）→ 分幕结构草稿（人审）→ 分场大纲草稿（人审采纳）`。每步输出走受控 schema（梗概、幕结构、分场列表各有 schema）。
  3. 采纳后效果：分场大纲写入剧本结构（经草稿机制），主要人物自动生成 Story Bible 人物卡草稿一并供采纳。
  4. 断点续跑：任一人审节点可挂起，回来继续。
- **失败与兜底**：某步 F1 降级时，把纯文本草稿交用户手工修订后继续下一步，工作流不整体作废。
- **验收标准（二值）**：从一条测试 logline 出发，全流程走通并产出 ≥10 场的大纲与 ≥2 张人物卡草稿，全程 trace 完整（E4 走查记录存档）；中途挂起后续跑成功 1 次。
- **依赖**：TASK-P3-07（工作流引擎）、TASK-P3-03（受控输出）、TASK-P3-09（澄清）。

### SPEC-P3-03 场景改写助手（WF-02）

- **用户价值**：改写（换场景氛围、调对白节奏、改视角）是高频创作动作；核心体验是"Agent 懂上下文、改动可预览、不弄丢我的原稿"。
- **行为契约**：
  1. 输入：`scene_id` + 自然语言改写指令；缺 `scene_id` 触发澄清。
  2. 过程：组装上下文（目标场全文 + 相邻场概要 + 涉及人物卡）→ `rewrite_scene` 技能产出受控草稿 → 自动 `consistency_check`（有冲突则在预览中标注）→ 差异预览。
  3. 输出：并排/内联差异 + 改动说明（改了什么、为何满足指令、保留了哪些既定事实）。用户可采纳、部分采纳（后续版本）、丢弃。
  4. 原稿安全：任何路径都不修改 M1 权威层，直到用户显式采纳（P-3 的具象化）。
- **失败与兜底**：按 §2.4 策略表；一致性冲突（F5）不阻断交付，以警示形式随差异呈现。
- **验收标准（二值）**：对含既定事实的测试场景执行改写指令，产出的草稿保留全部 `facts` 相关事实且体现指令要求（人工判定，记录存档，E4）；连续 3 次运行流程无崩溃、原稿哈希不变（E4）。
- **依赖**：TASK-P3-05/06（工具与上下文）、TASK-P3-03（受控输出）。
