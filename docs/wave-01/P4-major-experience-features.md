## 4. 功能明细

### F1 `sw check` —— 剧本一致性检查器（内容级 lint）

- **问题**：结构化剧本项目会随修改产生内容漂移：大纲列了第 7 场但 `scenes/` 没有对应文件（或反之）；台词署名了从未建卡的角色；场景编号断档/重复；模板占位符忘了填。SPEC-03 只管 CLI 运行错误，`sw doctor`（T08）只管项目文件与环境完整性，**没有任何机制检查剧本内容本身**。这类问题现在只会在导出后由人眼发现，返工成本最高。
- **方案**：新增 `sw check [--fix] [--format json]`。规则引擎 + 规则注册表（沿用 SPEC-03 的注册表模式，编码段 `SW-Cxxx`，与错误码 `SW-Exxx` 同库同 lint），每条规则含 severity（error/warn/info）、定位（文件+行）、三段式说明与文档锚点。初版规则集 8–10 条：大纲↔场景双向漂移、编号断档/重复、空场景、未建卡角色署名（依赖 F3 数据，未建卡时降级为 warn）、模板占位残留、导出前必查项。`--fix` 仅对白名单规则生效且默认 dry-run。退出码：有 error 为 1，供 CI 与 `sw export --check` 前置使用。
- **影响面**：新增 `src/app/check/`（规则引擎与注册表）；CLI 子命令；SPEC-03 注册表增加 `SW-Cxxx` 段与文档生成；依赖内容索引层（T01）。不触碰既有 SPEC 的接口。
- **工作量**：M。引擎本体小（遍历索引 + 查表），主要成本在规则实现与测试夹具（每条规则需正例/反例项目夹具各一）。
- **验收**：① 初版 ≥8 条规则，每条有正反例夹具测试；② 输出经 SPEC-03 渲染层，符合三段式 + 锚点；③ `--fix` 只触碰白名单且 dry-run 默认，`--fix --write` 后再跑 `sw check` 全绿；④ 50 场规模夹具执行 < 1s；⑤ 退出码语义有测试。
- **与后续代码贴合点**：消费 core 领域模型与内容索引层；输出复用 SPEC-03 `fail()/hint()`；与 `sw doctor` 形成「文件层 / 内容层」双检查，命令输出互相引荐、docs 互链；作为 F6 重排操作后的自动回归手段。

### F2 `sw snapshot / history / diff / restore` —— 版本快照与场景级对比

- **问题**：写作是探索性劳动，作者需要「大胆改，改坏了能回来」。P1 §5.1 说项目「可 git 版本化」，但 A1 的目标用户（编剧）普遍不掌握 git；P2 的版本化写（D32/T05）解决的是并发冲突，不提供创作者可用的「命名快照/时间线/回滚」。缺这一层，用户会以 `scene-final-final2.md` 式副本自救，直接破坏 P1 定下的 IA。
- **方案**：
  - `sw snapshot [label]`：创建全项目命名快照（含 project.yaml、outline、scenes、characters）。
  - `sw history [scene-id]`：项目级/单场级时间线（时间、label、涉及文件摘要）。
  - `sw diff <snap-a> [snap-b] [--scene id]`：场景粒度对比，按「台词/动作行」渲染而非原始行级补丁，80 列终端可读。
  - `sw restore <snap> [--scene id]`：全项目或单场恢复；恢复前自动创建安全快照；恢复走 SPEC-02 原子写事务。
  - 存储：`.sw/history/` 内容寻址存储（文件按内容哈希去重 + `index.yaml` 元数据）。**不内嵌 git**：项目目录很可能已在用户自己的 git 仓中，嵌套仓/子模块会制造惊吓；内容寻址实现小且可控。
- **影响面**：`src/infra/history/`（快照存储适配器）、`src/app/history/`、4 个 CLI 子命令；`.gitignore` 模板加 `.sw/`（快照属本地存档，不强推进用户 git）；project.yaml **不**存历史（见 §5.2 张力处置）。
- **工作量**：M–L。内容寻址快照与恢复事务为主体（复用 SPEC-02 原子写）；场景级 diff 渲染是主要 UX 打磨点。
- **验收**：① 快照→恢复往返字节一致；② 单场恢复不影响他场，恢复后 `sw doctor` 与 `sw check` 全绿；③ 恢复前自动安全快照可在 history 中查到；④ 写入中 kill -9 不产生半成品（原子性测试）；⑤ diff 输出有快照测试（锁结构不锁全文）；⑥ 删除 `.sw/` 后所有主工作流命令行为不变（只丢历史，验证「存档非状态」边界）。
- **与后续代码贴合点**：存储适配器归 infra 层（P1 §5.1 分层）；错误码入 SPEC-03 注册表（建议段 `SW-E05x`）；为 F6 提供操作前安全快照原语；历史存储的读取接口为 P2 S3（离线优先）与未来 Web 时间线预留同一数据面。

### F3 `sw character` —— 角色卡与出场连续性索引

- **问题**：角色是剧本的第二核心实体（P1 领域模型 Beat/Line 天然挂角色），P1 IA 已规划 `characters/` 目录，但 T01–T10 无任何角色功能任务。没有角色卡与出场索引，长剧本必然出现角色名拼写漂移（「李雷」vs「李磊」）、角色无故消失（前 3 场的重要角色后文再未出现）等连续性问题；F1 的角色类检查规则也没有数据来源。
- **方案**：`sw character add <name> / list / show <name>`。角色卡为 `characters/<slug>.md`（YAML frontmatter：姓名、别名表、简介 + Markdown 正文自由发挥）；内容索引层解析场景中的台词署名与角色提及，生成**出场矩阵**（角色 × 场次）；`sw character show` 输出角色卡 + 出场场次 + 台词行数；别名表归并称谓变体。台词署名的 Markdown 语法约定需与模板任务（W1-P1-T07）对齐——这是一个明确的跨槽对齐点，已写入任务依赖。
- **影响面**：`src/core/model/character.ts`（core，零 IO）、`templates/*/characters/` 示例卡、CLI 子命令组、内容索引层的署名解析规则。
- **工作量**：M。解析器规则简单，成本在与模板语法对齐及别名归并的边界情形。
- **验收**：① add/list/show 全链路测试；② 出场矩阵与人工标注夹具一致；③ 别名归并正确（含大小写/全半角）；④ 未建卡角色出现在署名时 F1 产出 warn（联动测试）；⑤ 空 `characters/` 走 SPEC-03 `hint()` 空态（含可复制的 `sw character add` 命令）。
- **与后续代码贴合点**：领域模型进 core；为 F1 提供角色数据；为未来 AI 辅助（A2）提供「角色上下文打包」取数接口——W1-D 维度 C 的 L3 准入条件（Agent 结合人物上下文）将直接消费此索引。

### F4 `sw stats` —— 写作统计与节奏视图

- **问题**：`sw status`（SPEC-02）回答「流程走到哪」，不回答「剧本本身长什么样」：总字数与预计时长、每场长短分布（节奏）、对白/动作占比、角色戏份分布。这些是修改期（五步工作流的 revise 步——当前工具面最薄弱的一步）的核心决策输入，目前只能人肉数。
- **方案**：`sw stats [--scene id] [--by character]`。项目级摘要（字数、场数、预计时长——screenplay 按页/分钟折算、short-video/podcast 按语速折算，**折算参数由模板声明**而非硬编码）；每场长度终端条形图；`--by character` 输出戏份分布（依赖 F3 出场矩阵）。纯读命令，不引入任何新状态。
- **影响面**：`src/app/stats/`（计算核心为纯函数，可下沉 core）、CLI 子命令、模板 schema 增加折算参数字段（与 W1-P1-T07 对齐）。
- **工作量**：S–M。纯函数计算 + 终端呈现，无新存储、无新状态。
- **验收**：① 夹具项目统计值与人工计算一致；② 三种模板折算参数各有测试；③ 输出 80 列可读且有结构性快照测试；④ 空项目/空场景走 `hint()` 空态；⑤ `--by character` 与 F3 出场矩阵一致性测试。
- **与后续代码贴合点**：纯消费内容索引层；补齐 revise 步的工具面；统计核心为纯函数，未来 Web 仪表盘（P2 语境）零改动复用。

### F5 专业导出管线 v2 —— Fountain 完整实现 + PDF 版式 + 标题页

- **问题**：T05 的 export 明确只做 Markdown 单格式，且 P1 §8 把多格式列为可砍项——这在 MVP 期正确。但「交出行业可用的成片脚本」是 A1 工具的价值终点：编剧的下游（导演、演员、平台）要的是标准 screenplay 版式（场景标题行、角色名居中、对白缩进）、Fountain 纯文本或 PDF。缺专业导出，工具止步于自娱，维度 A（功能易用性）无法越过 L3。
- **方案**：
  - 导出管线插件化：定义 `Exporter` 接口（core 领域模型 → 目标格式字节流），注册表模式管理（与 SPEC-03 注册表同构，降低心智负担）；T05 的 Markdown 导出迁移为第一个插件（迁移属重构，不改行为）。
  - v2 交付两个插件：**Fountain**（完整语法映射：Scene Heading / Action / Character / Dialogue / Parenthetical / Transition）与 **PDF**（US Letter/A4 标准 screenplay 版式；标题页由 project.yaml 元数据生成）。
  - `settings.export.presets` 支持命名预设（格式 + 纸型 + 是否含标题页）；`sw export --preset <name>`。
  - FDX（Final Draft XML）列为后续插件，本波不做。
- **影响面**：`src/app/export/`（管线与注册表）、`src/infra/export/{fountain,pdf}/`、project.yaml `settings.export` schema 扩展、CLI `--format/--preset` 旗标。PDF 渲染库选型是唯一重外部依赖决策，实现槽先做 spike + 补充 ADR。
- **工作量**：L。Fountain 映射规则明确但细节多（需与 F3/模板的台词标记约定一致）；PDF 版式是主要打磨点。拆为 T06（插件化 + Fountain）与 T07（PDF + 标题页）两个任务，可分槽交付。
- **验收**：① Fountain 输出经第三方解析器 round-trip 校验结构等价；② PDF 版式对照标准样张做量化断言（页边距、对白缩进列位）；③ 标题页字段完整来自 project.yaml；④ md/fountain/pdf 并存，默认格式由模板声明；⑤ 导出失败错误走 SPEC-03（建议段 `SW-E06x`）；⑥ T05 的 Markdown 插件迁移后原验收用例全绿（不回退）。
- **与后续代码贴合点**：是对 SPEC-02 export 的**深化**——把 T05 明确砍掉的范围升级为插件化任务；插件注册表与 SPEC-03 注册表模式同构；Fountain 作为纯文本格式天然适配「项目文件即接口」原则（P1 §5.1）。

### F6 `sw move / renumber / remove` —— 场景重排与结构重构事务

- **问题**：修改期最常见的结构操作是调场次、插场、删场。P1 IA 用文件名编号（`010-opening.md`），手工重排要同时改**文件名、大纲引用、`progress.scenes_done`** 三处，漂移风险高——F1 要查的漂移，相当一部分正来自手工重排。工具不接管这个事务，等于把最易错的操作留给用户。
- **方案**：
  - `sw move <id> --before/--after <id>`：单场移位，间隔编号策略（010/020/030）下尽量不连锁改名。
  - `sw renumber`：编号重整化（间隔重置为 10），输出改名清单。
  - `sw remove <id> --archive`：移入 `.sw/trash/` 而非物理删除，可恢复。
  - 所有操作为**三处一致性事务**：文件重命名 + 大纲结构化引用同步 + progress 更新原子完成（复用 SPEC-02 原子写）；操作前自动调用 F2 安全快照。大纲中的自由文本引用不强改，改为 F1 出 warn 提示人工确认（初版边界，避免误伤）。
- **影响面**：`src/app/structure/`、CLI 子命令组；依赖 F2 快照原语与 SPEC-02 事务语义。
- **工作量**：M。核心是一致性事务与大纲同步策略；「结构化引用同步、自由文本告警」的边界已把最难的自然语言理解排除在初版之外。
- **验收**：① move/renumber/remove 后 `sw check` 与 `sw doctor` 全绿；② 操作中 kill -9 无半成品；③ `--archive` 后可从 trash 恢复且 progress 一致；④ 操作前安全快照存在于 history；⑤ 间隔编号下单场 move 不触发无关文件改名（最小扰动断言）。
- **与后续代码贴合点**：与 F1（漂移检查）、F2（安全快照）构成「结构安全网」三件套；事务语义直接复用 SPEC-02；为未来 Web 的拖拽排序提供同一结构变更核心。

### 5.3 与 P2 机制的兼容性

P2 按 Web 形态假设撰写，且自声明「与 P1 冲突时以先落地者为准」；本槽按 P1 的 A3（CLI 优先）执行，两者不冲突而是分形态适用：P4 功能的**计算核心**（规则引擎、统计、导出映射、结构变更）形态无关，未来 Web 化时由 P2 的请求层/版本化写承载其写路径；F2 历史存储读取接口与 P2 S3 的本地副本方案共享数据面。P4 不引入任何与 D1–D39 相抵触的机制（本地单进程 CLI 无并发写场景，事务原子性由 SPEC-02 的临时文件 + rename 保证）。

### 5.4 依赖核验（对 P1 任务的前置关系）

所有 P4 任务的公共前置：W1-P1-T02（ADR 定栈）→ T03（脚手架）→ T05（引擎与领域模型）、T06（错误框架）。P4 内部前置：T01 内容索引层是 F1/F3/F4/F6 的公共地基；F6 依赖 F2 的快照原语。跨槽对齐点唯一且已显式登记：**台词署名的 Markdown 语法**须在 W1-P1-T07（模板）与 W1-P4-T05（角色解析）、T06（Fountain 映射）间对齐，建议由先开工者在补充 ADR 中定案。
