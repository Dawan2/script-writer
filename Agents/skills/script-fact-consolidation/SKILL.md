本 Skill 的目的，是将全部分段事实整理成一份可以支撑案例卡的全剧事实索引。

## 工作流程

1. 确认输入中的 `covered_chunk_ids` 已覆盖本轮全部证据块，保留未解决疑点。
2. 识别人物同一性，合并重复人物、事件、关系和规则，并保留全部来源证据。
3. 用“原因 → 选择 → 反制 → 后果 → 新压力”整理全剧时序和因果链，保证前一阶段的出口状态能被下一阶段继承。
4. 整理主要人物、关系、世界规则和回报链，只保留会影响后续剧情的状态。
5. 从分段写法中筛选真正解决了创作问题的选择，重新编为 `E01` 格式的具体写法记录。
6. 按调用方提供的 JSON Schema 返回完整对象，然后按本 Skill 的准出标准自检。

## 人物归并

合并错两个人会污染所有后续关系和事件，因此存疑时保留为两个对象。

- 全名、常用名可以在明确同指时合并。
- 绰号只能在同位说明、括号别名、文中改名或明确指代成立时合并。
- “红衣女子”“那个人”等描述性称谓不能触发合并。
- “队长”“家主”“院长”等头衔或职务不能触发合并。
- 名称相似、戏剧功能相似或“读起来像同一人”都不是同指证据。
- 合并后使用的人物名必须逐字来自输入事实记录。不得根据读音、字形或剧情猜测更改人名。

## 全剧事实的整理方法

### 时序与因果

- `chronology` 只保留会改变后续选择的事件，不把所有小动作按时间抄一遍。
- `cause` 说明人物为什么此刻选择这样做；`consequence` 说明该选择如何改变权力、信息、关系、资源、风险或代价。
- 相邻事件只有时间先后，却没有因果时，不得伪造连接。
- 若某个结果没有被后续继承，先检查是否遗漏事件、分阶段错误或原文本身矛盾，不要自行修复剧情。

### 人物

- `dramatic_role`：该人物如何向主线施加行动，例如追求目标、制造阻力、提供筹码或迫使选择；不是“男主”“配角”这类空标签。
- `desire`：人物持续想改变的东西，需要能解释其关键选择。
- `pressure_or_misbelief`：正在限制人物的现实压力，或使其反复做出有代价选择的误信。
- `resources_and_information`：人物能用于行动的能力、证据、资源、身份、关系和知情范围。
- `opening_state` 与 `ending_state`：必须使用可比较的知识、权力、关系、资源或行动状态，不只写性格形容词。
- `decisive_actions`：使人物路径发生不可自动撤销变化的选择。

### 关系

- `opening_state`：双方初始的权力、信任、债务、承诺、误解或知情差。
- `change_chain`：按“一方行动 → 另一方回应 → 关系新状态”整理。只有单方感受没有双方行动时，不得轻易宣称关系已改变。
- `ending_state`：结局时双方能够或不能够对彼此做什么，以及尚未消除的债务与边界。

### 世界规则

- `rule`：反复或关键性影响人物选择的规定、能力、身份或资源机制。
- `resource_or_limit`：规则向人物提供的行动手段，或对行动施加的限制。
- `violation_cost`：绕过、违反或使用该规则的实际代价。
- `story_function`：该规则实际促发了什么选择、阻力或后果。

### 回报链

不要把揭示、反转、回报和钩子混为同一件事：

- 揭示：人物或观众获得了新信息。
- 反转：新信息或行动迫使当前方向、判断或策略改变。
- 回报：前面建立的具体等待得到释放，并且产生了剧情后果。
- 钩子：当前结果制造了一个会迫使下一步行动发生的未解危险、决定或问题。

`payoff_chains` 按“铺垫 → 加压 → 释放 → 剧情后果”整理。只有身份公开、现场惊讶或一句反问，却没有改变后续行动时，不得夸大为完整回报。

### 具体写法

`craft_observations` 只保留真正改变后续剧情的选择，不保留单纯热闹或题材常见的桥段。每条必须说明：

1. 面对的创作问题。
2. 选择之前的人物、信息、权力和观众状态。
3. 文本实际采取的写法。
4. 它带来的可见故事变化。
5. 可能的观众效果，且明确为假设。
6. 该写法的前提或失效边界。

## 准出标准

- 事实索引按原文顺序覆盖全部证据块，关键内容同时覆盖开篇、中段和结局。
- 事件链有原因、选择、后果和新压力，不是“然后又发生”的流水账。
- 人物别名合并有明确同指依据，不能确认的对象保留分开并记录疑点。
- 人物、关系和剧情阶段的进入与出口状态连续。
- 回报链同时具有铺垫、加压、释放和真实剧情后果。
- 具体写法可回查、有创作问题和边界，但尚未越级抽象为公式或原则。
- `source_terms` 只能从输入事实记录中逐字复制。可以去重，不得改字、造词或合并不连续的词。

## 硬性输出要求

- 只返回 Schema 中的字段，所有字段都必须存在。`covered_chunk_ids` 必须覆盖输入中的全部证据块，不重不漏，并按数字升序返回。
- 部分合并任务至少返回 1 条时序、1 个人物、1 组关系、1 条回报链、1 条具体写法和 1 个原文专名。
- 最终全剧任务需要：`story_summary` 40-1600 字符；`chronology` 3-40 条；`characters` 2-16 人；`relationships` 1-16 组；`world_rules` 0-12 条；`payoff_chains` 2-16 条；`craft_observations` 3-20 条。
- 全剧原文达到 1000 个非空白字符时，`source_terms` 至少 4 项；较短原文至少 1 项，最多 30 项。`open_questions` 最多 16 项。
- 时序的 `phase` 为 2-40 字符，`event` 为 8-700 字符，`cause` 和 `consequence` 为 4-600 字符。人物的说明字段至少 4 字符，`decisive_actions` 为 1-8 项且每项至少 4 字符。
- 关系的 `parties` 为 2-4 人，`change_chain` 至少 8 字符；每条具体写法的 ID 使用不重复的 `E01` 格式，六个说明字段都为 8-600 字符。
- 每条时序、人物、关系、规则、回报链和具体写法至少引用 1 个输入中真实存在的证据编号。最终结果的内容证据必须同时落在全剧前四分之一、中间区间和后四分之一。
- `characters.name`、`chronology.characters`、`relationships.parties` 和 `source_terms` 中的专名都必须逐字来自输入事实记录，不得猜字或改字。
