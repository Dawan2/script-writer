本 Skill 的目的，是使用各生成阶段的同一套业务标准，审查案例卡、公式候选和原则观察是否可以入库。

## 工作流程

1. 先核对事实索引与案例卡，确认人物、关系、事件、规则、结局和证据没有冲突。
2. 检查案例卡是否解释了故事运转，而不只是剧情摘要和泛泛评价。
3. 对每条公式做调用边界、阶段粒度、去专名、迁移、执行和可检查性审查。
4. 对每条原则做跨题材、阶段归属、适用边界和准出标准审查。
5. 只报告会影响事实正确性、知识复用或入库边界的问题。每个问题指定最早需要返修的阶段，并给出可执行的修复要求。
6. 没有阻断问题时返回 `approved: true`；存在问题时返回 `approved: false` 和问题列表。按调用方的 JSON Schema 返回，不直接重写完整结果。

## 案例卡验收

出现以下任一情况时，返修 `case_card`：

- 标签不代表全剧主要内容，只来自剧名或单个桥段；主要时代互斥；受众与主要回报明显矛盾。
- `logline` 缺少主角、压力、核心行动或结果；`audience_promise` 只写爽、甜、虐等情绪词，没有观众等待的具体回报。
- 故事引擎没有初始困境、持续目标、有能力的阻力、失败代价、可重复冲突回路或结局终止性变化。
- 世界规则只是背景说明，没有资源或限制、违反代价和剧情作用。
- 人物只有身份和性格标签，没有欲望、压力/误信、筹码、关键选择和起止状态。
- 关系只写“从对立到爱情”等结论，没有双方行动、权力、债务、误解与变化链。
- 叙事阶段按集数平均切分，阶段之间没有不可逆状态变化或上下一致的交接。
- 回报没有铺垫、加压、释放或释放后的剧情后果，或把揭示、反转、回报和钩子混为同一件事。
- 关键写法没有创作问题、原剧选择、状态变化、观众效果假设和边界，或已越级写成通用公式。
- 优点和局限是无证据的通用评语，或与事实索引冲突。

## 公式验收

对每条公式候选做以下检查：

1. 仅阅读适用阶段、使用场景和公式名称，Agent 是否就能判断是否需要打开它？
2. 它是否只服务一个创作粒度，没有横跨世界观、故事、人物和剧本写作？
3. 它是否区分了调用前的不适用情况，以及选对公式后的常见失效方式？
4. 它是否用简明的核心公式表达了不变因果链？
5. 它是否说明使用前确认、可替换内容和至少两步使用方法？
6. 它是否解释方法为什么会改变人物选择、故事状态或观众期待？
7. 它是否有可在当前阶段产出中直接检查的完成标准？
8. 它是否分别说明改写与新创作的用法，并能换成新人物、新关系和新题材执行？

任一核心问题的答案为否时，返修 `formula`。特别阻断以下内容：

- 换名剧情、题材口号、固定桥段或一句话技巧。
- 保留原剧专名或不可拆分的连续情节。
- 为补齐分类而生成的空话。
- 使用场景堆叠了多个前提、症状和问题，无法单独用于调用判断。
- 同一张公式同时指导世界运行、故事结构、人物设计和场景写作。
- 无论采用什么写法都必须满足，实际上应归入创作原则。
- 没有引用真实关键写法，或证据与关联写法没有交集。
- 只因题材、背景或受众标签不同就重复拆卡，而创作决策、关键步骤和生效机制并没有变。

## 原则验收

对每条原则观察做以下检查：

1. `statement` 是否写明“当什么条件出现时，应该满足什么要求”？
2. 它是否可以跨题材、面向同一创作阶段使用？
3. `rationale` 是否说明了它保护的因果、人物可信度、观众理解或交付可用性？
4. 适用条件和失效/换法条件是否能清楚区分？
5. 每条准出标准是否都能在新文本中直接检查？
6. 本剧与原则的 `supports`、`bounds`、`counters` 或 `proposes` 关系是否与证据一致？

任一核心问题的答案为否时，返修 `principle`。特别阻断以下内容：

- 原则复述公式的条件、变量和执行步骤。
- 原则依赖特定题材、角色设定、桥段或观众标签。
- 只写“节奏要快”“冲突要强”等无法审稿的口号。
- 把单剧结论当作已经证明的通用事实，或将候选直接标为正式原则。
- 关联了不存在的公式候选或证据编号。

## 审稿边界

文字风格不同、存在另一种合理概括、公式或原则数量少，都不阻止入库。宁可没有候选，也不要用空话补数量。

## 硬性输出要求

- 只返回 `approved`、`summary`、`issues`，不得增加其他字段。`approved` 必须是布尔值，`summary` 为 8-500 字符，`issues` 为 0-8 条。
- `approved: true` 时 `issues` 必须为空数组；`approved: false` 时至少返回 1 条问题。
- 每条问题的 `stage` 只能是 `case_card`、`formula`、`principle` 之一，并指向需要最早返修的阶段。`problem` 和 `repair_instruction` 各为 8-600 字符。
- `evidence_references` 为 0-12 项，有引用时只能使用输入中真实存在的 `C0001` 格式编号。
