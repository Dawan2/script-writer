本 Skill 的目的，是将单剧原则观察归入尽可能少且稳定的公共原则，同时保留新的边界和反例。

## 工作流程

1. 对每条观察，仅比较该观察 `retrieved_principles` 中的原则。其他观察的候选不属于当前观察。
2. 依次比较创作阶段、触发条件、必须满足的要求、成立原因、适用条件、失效边界和准出标准。
3. 已有原则准确覆盖时选 `support`；当前观察补充了适用或失效条件时选 `bound`；当前观察在明确特殊条件下构成反例时选 `counter`；没有已有原则能解释时才选 `propose`。
4. 多条观察指向同一原则时，放入同一个操作。
5. 按调用方要求返回 `operations` JSON。

## 合并判断

- 只有文字相似，但创作阶段、触发条件或保护目标不同时，不是同一条原则。
- 同一质量要求在不同题材、背景和受众中出现时，应当合并为同一原则，不按标签新建。
- `support` 需要当前观察的条件、要求、成立原因和准出标准都被已有原则覆盖。
- `bound` 必须明确指出已有原则需要收紧或放宽的条件，不能只说“补充了新案例”。
- `counter` 必须说明违背原则却仍然成立的特殊条件，不能把低质量例外当作反例。
- `propose` 必须是跨题材、面向明确阶段、并且可以直接审稿的新质量判断，不是新的公式、桥段或题材经验。

## 执行规则

- `support`、`bound` 和 `counter` 的 `principle_id` 必须在该观察的 `retrieved_principle_ids` 中。不得因为其他观察出现了更相似的原则就跨观察引用；当前候选都不覆盖时应选 `propose`，且不得填写目标原则 ID。
- 收到校验修复要求时，必须根据其中指明的观察、非法 ID 和允许 ID 修改对应操作，然后重新返回完整 JSON。
- 单部剧本只能增加支持、边界、反例或待审核候选，不得自动改写已有原则，不得把候选发布为正式原则。
- 原则是跨题材的阶段质量要求，不得把公式的具体写法、某个题材的回报或某段剧情直接命名为原则。
- 理由必须说明当前观察与已有原则在条件、成立原因和准出标准上的关系，不得只写“内容相似”。

## 硬性输出要求

- 只返回 `{"operations": [...]}`。每个输入 `observation_id` 必须且只能出现一次。
- 每个操作的 `observation_ids` 为 1-6 项，`action` 只能是 `support`、`bound`、`counter`、`propose`，`reason` 为 12-600 字符。
- `support`、`bound`、`counter` 的 `principle_id` 必须是该操作中所有观察的 `retrieved_principle_ids` 共同包含的已有原则。`propose` 的 `principle_id` 必须为空字符串，并返回 4-80 字符的 `title`。
- 多条观察只有在创作阶段、触发条件和质量要求都一致时才能合并；不得为了减少操作数而合并不同原则。
